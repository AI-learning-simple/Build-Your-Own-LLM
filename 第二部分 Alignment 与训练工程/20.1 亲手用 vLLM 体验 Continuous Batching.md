## 二、方式A：朴素的逐个生成（模拟没有Continuous Batching 的系统）

```python
import time
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

# 模拟 8 个用户几乎同时发来的不同请求
prompts = [
    "介绍一下人工智能的发展历史。",
    "什么是 Transformer？",
    "写一首关于秋天的诗。",
    "解释一下什么是递归。",
    "推荐三本机器学习入门书籍。",
    "简单介绍一下量子计算。",
    "什么是区块链？",
    "解释一下 TCP 和 UDP 的区别。",
]

def generate_naive(prompt):
    messages = [{"role": "user", "content": prompt}]
    text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tokenizer(text, return_tensors="pt").to(model.device)
    output = model.generate(**inputs, max_new_tokens=100, do_sample=False)
    return tokenizer.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

start = time.time()
for p in prompts:
    # 关键问题：这里是完全串行的，前一个请求必须彻底生成完，才能开始下一个
    generate_naive(p)
naive_time = time.time() - start

print(f"逐个处理 {len(prompts)} 个请求耗时: {naive_time:.2f}s")
```

这种方式的问题在于：**每个请求必须等前一个请求完全生成结束才能开始**，GPU 在等待、拼接、调度上浪费了大量时间，真正用于计算的比例并不高。

## 三、方式B：用 vLLM 一次性批量处理

```python
from vllm import LLM, SamplingParams

# gpu_memory_utilization 控制 vLLM 最多使用多大比例的显存来存放 KV Cache
llm = LLM(model=model_name, gpu_memory_utilization=0.85, max_model_len=1024)
sampling_params = SamplingParams(temperature=0, max_tokens=100)

chat_prompts = []
for p in prompts:
    messages = [{"role": "user", "content": p}]
    chat_prompts.append(tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True))

start = time.time()
# 一次性把全部 8 个 Prompt 交给 vLLM，内部调度器会自动做 Continuous Batching
outputs = llm.generate(chat_prompts, sampling_params)
vllm_time = time.time() - start

print(f"vLLM 批量处理 {len(prompts)} 个请求耗时: {vllm_time:.2f}s")
print(f"速度提升: {naive_time / vllm_time:.2f}x")
```

vLLM 内部的调度器会把这8 个请求**同时**放进一个动态维护的 Batch 里，利用 PagedAttention 管理各自长度不同的 KV Cache，GPU 几乎不会有空闲——这正是第20章讲的 Continuous Batching 的真实效果。

## 四、模拟"源源不断"到来的请求（更接近真实线上场景）

```python
import threading
import queue

def simulate_online_requests(llm, prompts, arrival_interval=0.3):
    results = queue.Queue()

    def worker():
        for p in prompts:
            time.sleep(arrival_interval)         # 模拟请求不是同时到达，而是陆续到达
            output = llm.generate([p], sampling_params)
            results.put(output[0].outputs[0].text)

    t = threading.Thread(target=worker)
    start = time.time()
    t.start()
    t.join()          # 等待模拟线程处理完全部请求
    return time.time() - start

online_time = simulate_online_requests(llm, chat_prompts[:4])
print(f"模拟请求陆续到达（每0.3s 一个）总耗时: {online_time:.2f}s")
```

真实的 vLLM Server（用 `vllm serve` 命令启动）会在后台维护一个持续运行的调度循环，新请求随时可以插入正在进行的 Batch，不需要等待其它请求结束——这一点用简单的 Python 脚本很难完全模拟，但已经能感受到"陆续到达的请求"和"一次性提交的请求"在处理逻辑上的本质区别。

## 五、启动一个真实的 vLLM Server 体验并发

```bash
# 启动一个 OpenAI 兼容的推理服务
vllm serve Qwen/Qwen2.5-1.5B-Instruct --port 8000 --gpu-memory-utilization 0.85
```

在另一个终端里，用简单的并发请求测试真实吞吐：

```python
import concurrent.futures
import requests
import time

def call_api(prompt):
    # 用标准的 OpenAI Chat Completions 接口格式发请求，vLLM Server 完全兼容
    response = requests.post(
        "http://localhost:8000/v1/chat/completions",
        json={
            "model": "Qwen/Qwen2.5-1.5B-Instruct",
            "messages": [{"role": "user", "content": prompt}],
            "max_tokens": 100,
        },
    )
    return response.json()

start = time.time()
# 用线程池同时发出 8 个请求，模拟真实的并发场景
with concurrent.futures.ThreadPoolExecutor(max_workers=8) as executor:
    list(executor.map(call_api, prompts))
concurrent_time = time.time() - start

print(f"8 个并发请求通过 vLLM Server 处理总耗时: {concurrent_time:.2f}s")
```

对比这个耗时和"方式A"里逐个处理的耗时，你会看到明显的差距——**这正是 Continuous Batching 在真实并发场景下发挥作用的地方**。
