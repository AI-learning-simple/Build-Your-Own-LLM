# 20. 从今天开始：一个普通开发者如何进入 Agent 时代

前面五个部分，我们已经完成了一次从底层技术到产业未来的完整推演：

```text
神经网络
 ↓
Transformer
 ↓
LLM
 ↓
Agent
 ↓
Agent Runtime
 ↓
AgenticOS
 ↓
数字劳动力
 ↓
Agent Enterprise
 ↓
Agent Economy
 ↓
Agent Infrastructure
```

但到这里，如果只停留在理解层面，这本书就失去了最初的意义。

因为我们真正想回答的问题一直是：

> **一个普通开发者，今天到底应该怎么进入这个时代？**

不是等模型变得更强。

不是等某家公司发布所谓“下一代 Agent 平台”。

也不是先花几个月研究一个庞大的框架。

而是：

> **今天就开始构建。**

---

# 20.1 不要从“做一个超级 Agent”开始

这是学习 Agent 最容易犯的错误。

很多人一开始就想：

```text
我要做一个：
全自动
多 Agent
长期记忆
自主规划
自动浏览网页
自动写代码
自动执行任务
```

然后：

```text
LangGraph
+
MCP
+
Vector DB
+
Browser
+
Memory
+
RAG
+
多个 Agent
+
多个 Model
```

最后得到：

> 一个自己都不知道为什么能工作的系统。

这不是好的学习方式。

---

# 20.2 正确的方法是从最小闭环开始

我们真正需要的是：

```text
User
 ↓
Goal
 ↓
Agent
 ↓
One Tool
 ↓
Result
```

只有五个东西。

例如：

> “帮我计算两个数字的和。”

Agent：

```text
理解任务
 ↓
调用 calculator
 ↓
得到结果
 ↓
返回
```

看起来非常简单。

但它已经包含了：

```text
Intent
Tool
Decision
Execution
Result
```

这就是 Agent 的最小闭环。

---

# 20.3 Agent 的最小定义

到现在，我们可以给 Agent 一个非常工程化的定义：

> **Agent = Model + State + Goal + Capability + Execution**

其中：

```text
Model
```

负责：

> 理解与推理。

```text
State
```

负责：

> 保存当前任务状态。

```text
Goal
```

负责：

> 定义要完成什么。

```text
Capability
```

负责：

> 能够做什么。

```text
Execution
```

负责：

> 真正采取行动。

---

# 20.4 一个最小 Agent

因此，一个最小 Agent 完全可以是：

```text
┌──────────────────────┐
│        Agent         │
│                      │
│ Goal                 │
│   ↓                  │
│ Model                │
│   ↓                  │
│ Tool Selection       │
│   ↓                  │
│ Tool Execution       │
│   ↓                  │
│ Result               │
└──────────────────────┘
```

甚至不需要：

```text
Vector Database
RAG
Multi-Agent
Workflow Engine
```

---

# 20.5 第一阶段：先学会调用模型

如果一个开发者还没有真正理解 LLM：

第一步不是学习 Agent Framework。

而是：

> **直接调用一个模型。**

最简单的流程：

```text
Input
 ↓
LLM API
 ↓
Output
```

需要理解：

```text
Prompt
Token
Context
Temperature
Max Tokens
System Message
```

这些东西。

---

# 20.6 不要把模型 API 当成黑盒

至少应该知道：

```text
User Input
 ↓
Tokenizer
 ↓
Tokens
 ↓
Transformer
 ↓
Logits
 ↓
Probability
 ↓
Next Token
```

前面机器学习部分已经解释了：

> 模型本质上是在不断预测下一个 Token。

Agent 则是在这个模型之上增加：

> **状态与行动。**

---

# 20.7 第二阶段：理解 Tool Calling

LLM 本身只能：

```text
Generate Text
```

它不能天然：

```text
打开文件
执行程序
查询数据库
发送邮件
控制机器人
```

因此我们需要：

> **Tool。**

---

# 20.8 Tool 是 Agent 的手

这是我们前面反复使用过的一个非常重要的类比：

```text
LLM
=
大脑

Tool
=
手

Memory
=
记忆

Agent Runtime
=
神经系统

Environment
=
现实世界
```

没有 Tool：

> LLM 只能说。

有 Tool：

> Agent 才能做。

---

# 20.9 第一个 Tool 应该非常简单

例如：

```text
add(a, b)
```

输入：

```text
2
3
```

输出：

```text
5
```

这看起来没有任何技术含量。

但它可以帮助我们理解：

```text
Model
 ↓
Tool Selection
 ↓
Structured Arguments
 ↓
Tool Execution
 ↓
Tool Result
 ↓
Model
```

这就是 Agent 的核心循环之一。

---

# 20.10 Tool Calling 的真正意义

用户说：

> “帮我算一下 12345 × 67890。”

模型可以决定：

```text
需要计算器
```

然后产生：

```text
tool = calculator
arguments = {
    a: 12345,
    b: 67890,
    operation: multiply
}
```

Runtime 执行：

```text
calculator(...)
```

然后：

```text
result
 ↓
LLM
 ↓
Final Answer
```

这就是：

> **模型负责决定，Runtime 负责执行。**

---

# 20.11 这是一个非常重要的边界

千万不要让模型直接拥有：

> 任意执行权限。

应该始终存在：

```text
LLM
 ↓
Intent
 ↓
Tool Request
 ↓
Runtime
 ↓
Policy
 ↓
Tool
```

而不是：

```text
LLM
 ↓
直接操作系统
```

这正是我们前面讨论 AgenticOS 时：

> 为什么必须存在 Capability 和 Policy。

---

# 20.12 第三阶段：理解 State

一个 Agent 如果只能完成：

> 一个请求。

它其实只是：

> 工具调用（Tool Calling）。

真正的 Agent 需要状态。

例如：

```text
Task:
帮我规划一次东京旅行
```

状态可能包括：

```text
destination = Tokyo
date = October 10
budget = 1000
hotel = unknown
flight = unknown
```

---

# 20.13 State 是 Agent 的“工作记忆”

可以理解成：

```text
Current Task State
```

例如：

```text
{
  goal: "plan Tokyo trip",
  destination: "Tokyo",
  budget: 1000,
  hotel: null,
  flight: null
}
```

Agent 每执行一步：

```text
State
 ↓
Action
 ↓
Observation
 ↓
State Update
```

---

# 20.14 这就是 Execution Trajectory

我们之前已经讨论过：

```text
State₀
 ↓
Action₁
 ↓
Observation₁
 ↓
State₁
 ↓
Action₂
 ↓
Observation₂
 ↓
State₂
```

最终：

```text
Stateₙ
 ↓
Goal Achieved
```

这就是：

> **Agent Execution Trajectory。**

---

# 20.15 第四阶段：让 Agent 能规划

到这里：

```text
Goal
 ↓
Tool
 ↓
Result
```

还是不够。

真正复杂的任务需要：

```text
Goal
 ↓
Plan
 ↓
Step 1
Step 2
Step 3
...
```

例如：

> “帮我分析一家公司的经营情况。”

Agent 可能需要：

```text
1. 获取公司基本信息
2. 获取财务数据
3. 获取行业数据
4. 分析趋势
5. 形成结论
```

---

# 20.16 Planning 不一定需要复杂算法

刚开始学习时，完全可以：

```text
Goal
 ↓
LLM
 ↓
Plan
```

例如：

```text
{
  "steps": [
    "search company information",
    "collect financial data",
    "analyze revenue trend",
    "generate report"
  ]
}
```

然后 Runtime 顺序执行。

---

# 20.17 这就是最简单的 Planner

```text
┌───────────────┐
│     Goal      │
└───────┬───────┘
        ↓
┌───────────────┐
│    Planner    │
└───────┬───────┘
        ↓
┌───────────────┐
│     Plan      │
├───────────────┤
│ Step 1        │
│ Step 2        │
│ Step 3        │
└───────┬───────┘
        ↓
    Executor
```

这已经是一个非常有价值的 Agent Demo。

---

# 20.18 Planning 和 Execution 必须分开

这是我们前面 Agent 架构讨论中非常重要的结论。

不要：

```text
LLM
 ↓
不断思考
 ↓
不断执行
 ↓
不断重新规划
```

而应该尽可能：

```text
Goal
 ↓
Planning
 ↓
Execution
 ↓
Evaluation
```

必要时再：

```text
Replanning
```

---

# 20.19 为什么要分开

因为 Planning 和 Execution 是两种不同的问题。

Planning：

> 我要怎么完成？

Execution：

> 现在具体执行什么？

Evaluation：

> 执行结果怎么样？

Replanning：

> 当前情况发生变化后怎么办？

这四个概念应该明确区分。

---

# 20.20 第五阶段：建立 Executor

Executor 是整个 Agent Runtime 最核心的模块之一。

输入：

```text
Action
```

输出：

```text
Observation
```

例如：

```text
Action:
search("Tesla revenue 2025")
```

Executor：

```text
调用搜索工具
```

得到：

```text
Observation:
...
```

然后将 Observation 写回 State。

---

# 20.21 Executor 的基本结构

```text
Executor
├── Validate Action
├── Check Policy
├── Resolve Capability
├── Execute
├── Capture Result
├── Update State
└── Record Trajectory
```

注意：

> Executor 本身不负责决定“最终应该做什么”。

它负责：

> **可靠地执行已经决定的 Action。**

---

# 20.22 第六阶段：Evaluation

Agent 最大的问题之一是：

> 它可能认为自己完成了任务。

但实际上：

> 根本没有完成。

例如：

```text
Goal:
找到最低价格的酒店
```

Agent：

> 找到了一家酒店。

但：

> 它是不是最低价？

这就是 Evaluation。

---

# 20.23 Evaluation 是 Agent 的“眼睛”

我们之前说：

```text
Tool
=
手
```

那么：

```text
Evaluation
=
眼睛
```

Agent：

```text
Plan
 ↓
Act
 ↓
Observe
 ↓
Evaluate
```

没有 Evaluation：

> Agent 很容易自我欺骗。

---

# 20.24 Evaluation 可以有多种形式

最简单：

```text
Rule-based
```

例如：

```text
price < budget
```

更复杂：

```text
LLM-as-Judge
```

甚至：

```text
Human Evaluation
```

以及：

```text
Automated Test
```

---

# 20.25 第七阶段：Memory

当 Agent 能够：

```text
Plan
Execute
Evaluate
```

下一步才是：

> Memory。

Memory 不应该一开始就加入。

否则开发者很容易把：

```text
State
Memory
Context
History
```

混在一起。

---

# 20.26 State 和 Memory 的区别

简单来说：

```text
State
=
当前任务需要知道什么
```

而：

```text
Memory
=
未来可能还需要知道什么
```

例如：

```text
State:
当前正在规划东京旅行
```

Memory：

```text
用户喜欢靠近地铁
用户不喜欢红眼航班
用户预算通常较低
```

---

# 20.27 Memory 不是“聊天记录”

这是一个非常重要的认识。

如果把：

```text
过去所有聊天
```

全部塞进去：

> 不叫 Memory。

那只是：

> History。

真正的 Memory 应该：

```text
Extract
 ↓
Compress
 ↓
Store
 ↓
Retrieve
 ↓
Use
```

---

# 20.28 第八阶段：加入 Policy

到这里，我们已经有：

```text
Model
Goal
State
Plan
Executor
Tool
Evaluation
Memory
```

接下来必须加入：

> **Policy。**

因为 Agent 开始真正拥有行动能力了。

---

# 20.29 Policy 决定“允许做什么”

例如：

```text
允许：
读取公开网页

允许：
创建日历事件

需要确认：
发送邮件

禁止：
删除重要文件

禁止：
转账超过 $1000
```

于是：

```text
Action
 ↓
Policy
 ↓
Allow / Deny / Approval
```

---

# 20.30 这时 Agent 才开始接近生产级

一个简单 Agent：

```text

 ↓
LLM
 ↓
Tool
```

一个生产 Agent：

```text

 ↓

 ↓
Planning
 ↓

 ↓

 ↓
Observation
 ↓
Evaluation
 ↓
Trajectory
 ↓

```

这已经是一个真正的：

> **Agent Runtime。**

---

# 20.31 第九阶段：加入 Observability

接下来需要知道：

> Agent 到底做了什么？

记录：

```text
Task ID
Agent ID
Plan
Action
Tool
Arguments
Result
Latency
Cost
Policy Decision
Evaluation
```

这就是：

> Agent Trace。

---

# 20.32 为什么一定要记录 Trace

因为 Agent 是非确定系统。

今天：

```text
Plan A
```

明天：

```text
Plan B
```

如果没有 Trace：

> 根本无法解释差异。

有了 Trace：

```text
Task
 ↓
Plan
 ↓
Action
 ↓
Observation
 ↓
Decision
```

就可以：

> Debug。

# 20.36 不要凭感觉评价 Agent

# 20.40 第一个完整 Agent 的架构

可以把我们的第一个实践目标定义成：

```text
                    User
                      │
                      ↓
                   Goal
                      │
                      ↓
              ┌──────────────┐
              │    Agent     │
              ├──────────────┤
              │    Model     │
              │    State     │
              │    Memory    │
              └──────┬───────┘
                     ↓
                  Planner
                     ↓
                  Policy
                     ↓
                 Executor
                     ↓
              ┌──────┼──────┐
              ↓      ↓      ↓
            Tool   Tool   Tool
              │      │      │
              └──────┼──────┘
                     ↓
                Observation
                     ↓
                 Evaluation
                     ↓
                  Result
                     ↓
                 Trajectory
```

---

# 20.41 这个 Agent 不需要任何复杂框架

第一版甚至可以只使用：

```text

+

+

+

```

就足够了。

这也是本书实践路线非常重要的原则：

> **先理解原理，再使用框架。**

---

# 20.42 为什么不建议一开始就上框架

因为如果直接使用：

```text
LangGraph
CrewAI
AutoGen
某某 Agent SDK
```

很容易变成：

```text
Node
 ↓
Node
 ↓
Node
 ↓
Node
```

但你不知道：

> 为什么需要这些 Node。

等理解了：

```text

Planner
Executor
Policy
Evaluation
```

之后，再使用框架：

> 才真正知道框架在帮你解决什么问题。

---

# 20.43 框架应该是加速器，不应该是知识本身

这是整个实践部分的一个基本原则：

> **先自己实现最小版本，再使用成熟框架。**

自己实现：

```text
Agent Loop
Tool Calling
State
Planner
Executor
Evaluation
```

哪怕只有几百行代码。

然后再比较：

```text
你的实现
vs
Agent Framework
```

学习效率会高很多。

# 20.54 为什么小模型反而适合学习

如果一个 Agent：

> 只有大模型才能跑。

你很难知道：

> 到底是架构有效，还是模型太强。

如果使用小模型：

> Agent 架构的问题会暴露得非常明显。

这反而更有助于理解：

```text
Planner
Executor
Memory
Policy
Evaluation
```

```text
if "天气" in input:

    call_calculator()
```

```text

 ↓

 ↓

```

```text

```

替换成：

```text
LLM Intent
```

# 20.56 这是一条非常重要的学习方法

不要：

> 一开始就把所有智能交给模型。

而应该：

```text
确定性系统
 ↓
理解架构
 ↓
局部引入模型
 ↓
观察变化
 ↓
逐步增加自主性
```

这样才能真正理解：

> **模型到底给系统增加了什么。**


真正复杂的是：

```text

Memory
Tools
Policy

Evaluation
Observability
Recovery
```

所以：

> **Agent Engineering 本质上是系统工程。**
