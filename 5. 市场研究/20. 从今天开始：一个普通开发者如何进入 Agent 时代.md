# 20. 从今天开始：一个普通开发者如何进入 Agent 时代

> **研究更新日：2026-11-25。** 本章是基于产业证据的学习与产品验证路线，不是新框架教程，也不承诺固定收入或提效。实现细节对接本书已有实践章节。

## 20.1 从任务开始，而不是从超级 Agent 开始

企业采用 AI 的广度已经提高，但采用并不等于可靠部署和回报。[1] 对开发者，最有意义的起点是找到一个真实使用者反复遇到的问题。

合适的第一个任务应满足：

- 输入能够在授权范围内获得；
- 有人能定义什么叫完成、什么叫错误；
- 可以先在只读或测试环境验证；
- 失败不会直接造成高后果损失；
- 使用频率与价值足以支撑持续维护。

例如：带来源的内部文档问答、服务工单材料核对、设备手册检索、采购报价字段比较。不要一开始就让系统任意操作真实账户、资金或物理设备。

## 20.2 先判断是否真的需要 Agent

如果步骤固定，用脚本或工作流即可；如果只是查资料，用检索与生成可能足够。只有需要根据中间反馈选择动作时，Agent 才可能增加价值。

多 Agent、长期记忆和浏览器控制都不是必选项。增加一个组件之前，先回答它解决了哪个已观察到的失败。

**本章建议的最小架构：**一个明确任务、少量受控工具、持久任务状态、独立结果检查，以及人工处理出口。

## 20.3 六个验证阶段

以下顺序是建议，不是固定工期。前一阶段未解决的问题，不应靠增加自主性掩盖。

| 阶段 | 交付物 | 通过条件 |
|---|---|---|
| 需求与基线 | 任务说明、人工流程与成本 | 使用者确认问题和验收标准 |
| 只读原型 | 检索、提取或分析结果 | 来源和计算可核对 |
| 受控工具 | 明确输入输出的工具接口 | 参数错误与无权限可阻断 |
| 状态与恢复 | 任务状态、检查点、超时 | 中断不会丢失关键状态 |
| 评测与回归 | 固定案例、错误分类、版本记录 | 改动后的质量和成本可比较 |
| 小范围试用 | 有责任人的真实工作流 | 总收益达到用户接受标准 |

进入生产前，应根据业务风险设定阈值。本章不提供“成功率达到某个百分比就普遍安全”的规则；高风险错误不能被平均成功率掩盖。

## 20.4 评测集比演示视频更重要

测试不仅要有正常输入，还要包含：资料缺失、过期版本、同名对象、工具超时、权限撤销、重复请求和互相矛盾的证据。

记录至少包括：

- 最终结果是否合格、由谁判断；
- 是否有无依据的关键事实；
- 是否正确拒绝无法完成或未授权任务；
- 人工复核与返工时间；
- 总耗时、模型与工具成本；
- 失败之后有没有重复产生副作用。

METR 的 2026 年更新提醒我们：开发者的主观感受和实际生产率可能不同，新实验也会受选择偏差影响。[2] 因此，不要用“自己感觉快了”代替任务记录，也不要照搬研究里的百分比作为产品收益。

## 20.5 工具和运行时的工程底线

### 工具

接口需要明确输入类型、权限、只读与写入的区别、超时和错误语义。写操作应支持幂等或等效的重复执行防护。

### 状态

LangGraph 等框架提供持久化机制，但具体后端、恢复点和保留策略仍需设计。[3] 检查点不保证外部操作恰好发生一次；异常恢复必须测试。

### 安全

把外部文档视为数据，不执行其中夹带的指令；凭据放在受控运行环境而不是提示词；敏感操作由服务端校验，并在需要时绑定明确审批。

### 版本

固定模型、SDK、工具和协议版本，记录升级前后的测试结果。MCP 等规范会演进，不要让生产实现隐式跟随 `latest`。[4]

## 20.6 从技术作品走向可购买产品

在真实试用中，向使用者核对五个问题：

1. 以前由谁做，每次总共花多少时间？
2. 最麻烦和最昂贵的错误是什么？
3. 谁决定采购，预算属于哪里？
4. 新系统是否真的减少了总工作，而不是转移给别人？
5. 能否服务第二个客户，而不需要完全重写？

收费可以按席位、用量、任务或服务约定设计，但必须解释成本和责任。尚未有稳定质量与验收方法时，不应承诺“只按成功结果收费就必然盈利”。

对外发布前，清楚说明数据使用、限制、人工参与和售后处理，不把受监督原型宣传成完全自主产品。
