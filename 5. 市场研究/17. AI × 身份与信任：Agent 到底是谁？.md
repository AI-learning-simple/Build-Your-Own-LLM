# 17. AI × 身份与信任：Agent 到底是谁？

上一章我们把 Agent 从企业内部的“数字员工”进一步推向了商业网络。

当 Agent 开始：

* 购买商品；
* 选择供应商；
* 签订合同；
* 调用服务；
* 支付费用；
* 管理预算；
* 与其他 Agent 协商；

一个看似简单、实际上非常底层的问题就出现了：

> **Agent 到底是谁？**

如果一个 Agent 说：

> “我是 ACME 公司的采购 Agent。”

我们必须继续追问：

```text
谁创建了它？
谁拥有它？
谁授权它？
它能代表谁？
它能做什么？
它不能做什么？
它做错了谁负责？
```

因此，Agent Economy 的真正基础并不是支付。

而是：

> **Identity + Trust + Authority。**

那么，为什么这个问题在 Agent 时代会变得特别困难？

传统软件的行为通常是固定的：

```text
User
 ↓
Application
 ↓
固定程序逻辑
 ↓
System Call
 ↓
Resource
```

开发者提前定义了输入、逻辑、输出、权限，因此系统可以比较明确地回答：“这个程序能够做什么？”例如 Chrome 拥有网络访问、文件读取、GPU 权限，边界相对清晰。

而 Agent 完全不同：

```text
User
 ↓
Goal
 ↓
Agent
 ↓
LLM
 ↓
Dynamic Decision
 ↓
Tool
 ↓
Resource
```

最大的变化是：

> **执行路径不是完全预先确定的。**

Agent 可能根据当前环境在决定 A、决定 B、决定 C 之间选择。因此传统的“这个程序有什么权限”开始变得不够。如果 Agent 只是回答问题、生成文本、推荐内容，这个问题并不严重；但如果 Agent 可以修改数据库、购买商品、转账、控制机器人、发布代码、签署合同、操作生产设备，那么“信任”就不再是一个附加功能，而会成为 Agent 社会能够运行的基础。

---

# 17.1 人类社会为什么需要身份

人类社会中的交易之所以能够运行，是因为我们能够回答：

> “你是谁？”

例如：

```text
张三
 ↓
身份证
 ↓
银行账户
 ↓
合同
 ↓
法律责任
```

身份把一个现实中的人连接到了：

```text
财产
信用
权利
义务
责任
```

---

# 17.2 Agent 也需要类似结构

一个企业 Agent：

```text
Procurement Agent
```

未来可能需要：

```text
Agent Identity
        │
        ├── Owner
        ├── Organization
        ├── Role
        ├── Capabilities
        ├── Authority
        ├── Credentials
        └── Reputation
```

它不再只是：

> 一段运行中的代码。

而是：

> **一个拥有明确身份和权限的数字执行主体。**

---

# 17.3 Agent Identity 不等于 Agent Name

很多系统会简单地给 Agent 一个名字：

```text
sales-agent-01
```

这远远不够。

真正的身份至少应该回答：

```text
Who?
Owned by whom?
Created by whom?
For what purpose?
Authorized to do what?
Valid until when?
```

所以：

> **Identity 是关系，而不是字符串。**

# 17.9 Ownership 和 Authority 不是一回事

这是 Agent 身份体系中一个非常容易混淆的问题。

例如：

```text
ACME Corp
 ↓
Procurement Agent
```

ACME 拥有 Agent。

但 Agent 的权限可能只有：

```text
单笔采购 ≤ $10,000
```

因此：

> **Ownership ≠ Authority。**

```text
 ↓
```


---

# 17.11 Delegation Chain

例如：

```text
CEO
 │
 │ $1M procurement authority
 ↓
CFO
 │
 │ $100K procurement authority
 ↓
Procurement Manager
 │
 │ $20K procurement authority
 ↓

```

Agent 最终拥有的权限：

> 不能超过授权链允许的范围。

---

# 17.12 为什么 Delegation 很重要

如果 Payment Agent 转账：

```text
$50,000
```

系统不能只记录：

```text
Payment Agent → Bank
```

还必须能够追溯：

```text
CEO
 ↓
CFO
 ↓
Payment Agent
 ↓
Transaction
```

否则：

> 出现争议之后，责任链无法建立。

---

# 17.13 Least Authority

Agent 系统应该遵循一个非常重要的安全原则：

> **Least Authority。**

即：

> Agent 只获得完成任务所必需的最小权限。

例如：

```text
客服 Agent
```

需要：

```text
读取订单
修改配送地址
创建退款申请
```

不应该拥有：

```text
读取公司财务
删除用户
修改商品价格
```

---

# 17.14 Capability 和 Authority 也不同

这也是前面 Agent 架构中非常重要的区别。

Capability：

> Agent **能做什么**。

Authority：

> Agent **被允许做什么**。

例如：

```text
Capability:
TransferMoney
```

并不意味着：

```text
Authority:
TransferMoney($1M)
```

---

# 17.15 Capability × Authority

真正的执行权限可以表示为：

```text
Effective Permission
=
Capability
∩
Authority
∩
Policy
∩
Context
```

也就是说：

> Agent 即使拥有能力，也不代表任何时候都能使用。

---

# 17.16 第五层：Intent

这是 Agent 和传统程序最大的区别之一。

传统权限：

```text
Who
+
What
```

Agent 还需要：

```text
Why
```

也就是：

> **Intent。**

---

# 17.17 一个简单例子

```text

```

```text

```

```text

```

可能允许。

如果目的：

```text

```

则应该拒绝。

因此：

> **同一个 Capability，在不同 Intent 下可能产生不同的安全结论。**

# 17.20 Context-aware Authorization


# 17.36 Trust Score


```text

```

核心思想是：

> **信任是动态的。**

---

# 17.37 Trust Decay

可以理解为：

```text
Trust(t+1)
=
Trust(t)
+
Positive Evidence
-
Negative Evidence
```

例如：

```text

→ Trust ↑

→ Trust ↓

模型更换
→ Re-evaluation

权限扩大
→ Re-evaluation
```

---

# 17.38 Reputation 与 Trust 的区别

两者也不能混为一谈。

Reputation：

> **过去表现如何。**

Trust：

> **现在是否应该信任。**

例如：

```text
Agent A
过去履约率 99%
```

Reputation 很高。

但今天：

```text
Credential 被盗
```

Trust 应该立即下降。

---

# 17.39 Trust 是上下文相关的

同一个 Agent：

```text
金融交易
```

可能：

> Trust 95%。

但执行：

```text
医疗诊断
```

可能只有：

> Trust 70%。

因此：

> **Trust 不是 Agent 的固定属性。**

# 17.96 行业实践：协议里的身份字段

本章的概念体系——Identity、Authority、Delegation——在 2025 年的协议层已经有了具体的工程对应物。

在 A2A 协议中，每个 Agent 必须发布 Agent Card，其中包含身份与能力描述、以及认证端点。这意味着“Agent 是谁”第一次有了机器可读的标准答案——协作的前提是双方能互相验证身份。

在 MCP 生态中，2025 年的规范更新引入了基于 OAuth 2.1 的授权体系：Agent 访问工具与数据时，不再直接持有长期密钥，而是通过标准化的授权流程获取受限令牌——这正对应本章讨论的 Least Authority 与 Delegation：

```text
用户授权 Agent 代表自己
 ↓
Agent 获得 scoped token（限定范围、限定时长）
 ↓
工具方验证 token 与其声明的权限
 ↓
全程可审计
```

传统 IAM（Okta、Entra 这类身份系统）管的是“人的账号在哪些系统里有什么权限”。而 Agent 身份的新问题是三层结构：

```text
Principal（人）
 ↓ on behalf of
Agent（代表）
 ↓ scoped authority
Action（具体行动）
```

每一层都需要可验证、可撤销、可审计——这是现有 IAM 体系没有设计过的。

受影响的人群：

* CISO 与安全团队：攻击面从“账号被盗”扩展到“授权被滥用”与“Agent 被冒充”，需要重建信任模型；
* 身份厂商（Okta、Microsoft Entra 等）：正在竞逐“Agent 身份目录”这个新市场；
* 平台方：Agent Store、Agent Registry 的运营者将成为新的事实上的发证机构；
* 每一个授权 Agent 的普通人：你在给 Agent 权限的那一刻，就是本章讨论的委托链的起点。

身份这一章的启示：协议层的工程实践（Agent Card、OAuth 授权）正在把本章的理论框架变成默认设置——未来每个开发者构建 Agent 时，都会被迫回答“这个 Agent 是谁、代表谁、能做什么”，而答案必须是机器可验证的。
