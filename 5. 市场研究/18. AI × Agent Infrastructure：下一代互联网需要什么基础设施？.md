# 18. AI × Agent Infrastructure：下一代互联网需要什么基础设施？

上一章我们讨论了：

> **Agent 到底是谁。**

我们建立了：

```text
Identity
 ↓
Authority
 ↓
Capability
 ↓
Action
 ↓
Audit
```

但如果把视角进一步拉高，会发现一个更大的问题：

> **如果未来世界真的存在几十亿甚至上百亿 Agent，今天的互联网基础设施够用吗？**

答案很可能是：

> **不够。**

今天的互联网，是围绕：

```text
Human
 ↓
Website / App
 ↓
Information
```

建立起来的。

而 Agent 时代需要的是：

```text
Agent
 ↓
Capability
 ↓
Action
 ↓
Outcome
```

因此，下一代互联网需要从：

> **Information Infrastructure**

逐渐演化成：

> **Agent Infrastructure。**

当一个企业开始拥有 100 个、1000 个甚至 10000 个 Agent，这些 Agent 不可能依靠几个 API 和几张数据库表长期运行。它们需要新的基础设施。

---

互联网早期：

所以真正变化的不是：

> 网络速度。

> **网络上的主体发生了变化。**

# 18.4 从 URL 到 Capability

传统：

```text

```

> 一个资源在哪里。


因此：

而未来的：

> Capability Identifier

可能描述：

> **可执行能力。**

---

# 18.53 Intent-aware Security

例如：

Agent 请求：

```text
读取客户数据库
```

传统权限：

> Agent 有权限。

但 Agent 当前意图是：

> 生成销售分析。

允许。

如果当前意图是：

> 将客户数据发送给外部服务。

即使 Agent 本身有数据库读取权限：

> 仍然可能应该拒绝。

因此：

> **权限不应该只判断“谁”，还要判断“为什么”。**

# 18.99 行业实践：MCP、A2A 与正在成型的协议栈

本章描述的 Agent Infrastructure，在 2025 到 2026 年间经历了从论文到事实标准的跃迁。三个协议值得记住。

MCP（Model Context Protocol）：Anthropic 于 2024 年 11 月开源，为“模型如何连接工具与数据”定义了标准接口。它是历史上被采用最快的协议之一——发布一年内，OpenAI、Google、Microsoft 先后宣布兼容，工具生态爆发式增长。本章说的“Capability 接口”，MCP 是第一个大规模落地版本。

A2A（Agent-to-Agent）：Google 2025 年 4 月发布（详见上一章），解决 Agent 之间的发现与协作。

AG-UI：面向 Agent 与前端界面的交互协议，让“人监督 Agent 执行”有了标准化的事件流。

合起来，Agent 时代的协议栈雏形是：

```text
应用层：各行业的 Agent 产品
  ↓
协作层：A2A（Agent 间协议）
  ↓
工具层：MCP（能力连接协议）
  ↓
交互层：AG-UI（人机界面协议）
  ↓
传输与安全：HTTP / OAuth / 审计日志
```

对照互联网的历史阶段：1990 年代的 Web 靠 HTTP + HTML 统一了信息分发，2000 年代靠 API + OAuth 统一了服务连接，这一轮 Agent 协议要做的是统一“行动的委托与执行”。

为什么传统中间件（ESB、API 网关）无法承担这个角色？

因为它们的假设是静态的：接口预先注册、权限预先配置、调用关系预先约定。而 Agent 基建的核心假设是动态的：能力需要被发现、权限需要按次协商、组合需要运行时决定。这是目录服务与能力市场的区别。

受影响的人群：

* 基础设施工程师：下一代运维对象从“服务与容器”变成“Agent 与能力”，Agent Ops 正在成为新学科；
* 中间件与集成软件厂商：ESB 时代的位置正在被协议原生的方案侵蚀；
* 开发者：为 MCP 服务器贡献能力，正在成为类似“给 npm 提包”的生态位；
* 每家企业：Agent 基建的选择（自建 vs 平台）将像 2010 年代的云决策一样影响十年。

基建这一章的启示：历史上每一次计算范式的迁移，价值都会在基础设施层沉淀一次——PC 时代的操作系统、互联网时代的协议与云、移动时代的 App Store。Agent 时代的这一层，正在眼下成型。
