# 11. AI 编程与开发者工具

> **更新基准：2026-11-26。** 本章覆盖终端、IDE、仓库级 Agent、代码上下文和审查工具。公开仓库可能只发布客户端、插件或反馈入口，不能据此认定模型和整个服务都开源。

## 11.1 产品地图

| 类型 | 代表产品／项目 | 核心职责 |
|---|---|---|
| IDE 助手 | Cursor、GitHub Copilot、Windsurf、CodeBuddy 等 | 补全、编辑、代码上下文和交互 |
| 终端 Agent | Claude Code、Codex CLI、Gemini CLI、OpenCode、Aider | 在仓库和命令环境中执行任务 |
| 编辑器扩展 | Cline、Continue 等 | 把模型与工具嵌入既有编辑器 |
| 仓库级执行 | OpenHands 等 | 沙箱、任务、代码修改和验证 |
| 上下文整理 | Repomix、代码搜索与语义工具 | 选择模型真正需要的代码 |
| 审查与质量 | PR 审查、静态分析、测试工具 | 独立发现问题并检查变更 |

商业工具放在 21 的官方入口索引，公开软件按仓库 ID 计数；同一产品的 SaaS 名称不重复增加千项数量。

## 11.2 编程 Agent 的最小闭环

理解问题 → 定位代码 → 制定变更 → 修改 → 运行适当验证 → 检查 diff → 报告结果。仓库搜索、类型信息、测试与版本控制往往比更长的自由推理更重要。

上下文不应机械塞入整个仓库。根据符号、调用关系、接口和失败案例定位，既节省资源，也减少无关指令影响。代码中的注释、测试数据和第三方文件都是资料，不自动拥有修改任务的权限。

## 11.3 对权限与环境的要求

允许读文件、编辑、执行测试、安装依赖、访问网络、提交和发布，应分别授权。测试命令也可能运行任意项目代码，因此来自不可信仓库时需要沙箱与最小权限。

Agent 不应擅自提交、推送、改密钥、改全局配置或执行破坏性操作。自动模式的价值是减少可预期步骤的操作，不是取消所有边界。

## 11.4 如何评价编码能力

- 正确解决真实需求，而不是只让已有测试变绿。
- 不随意删除失败测试、降低断言或绕过检查。
- 控制无关改动，保持接口和风格一致。
- 说明实际运行了哪些验证，哪些未运行。
- 记录人工审查、返工和维护成本。
- 比较相同任务和权限下的总交付时间。

公开软件修复基准有价值，但不能直接代表大型私有仓库、前端交互或跨团队需求。工具更迭很快，历史“提效百分比”不应作为永久承诺。

## 11.5 选择时看什么

模型可选性、代码索引、编辑精度、终端控制、沙箱、审批、上下文管理、恢复、团队数据边界和费用。尤其要区分“支持某个模型 API”和“该模型在所有工具模式中可靠工作”。

Skills、规则和提示模板是重要知识资产，但本版不把每份提示或配置拆成一个独立框架来凑数量。它们应配合真实测试和明确触发条件，而不是假设加一段提示就能解决全部工程问题。
