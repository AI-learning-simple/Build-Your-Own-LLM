# 9. Agent 框架、记忆与工作流

> **更新基准：2026-11-26。** 框架封装的是执行与组织方式，不会自动使模型正确。固定工作流、动态 Agent、多 Agent 和长期运行系统应分别选择。

## 9.1 五种产品形态

| 形态 | 代表生态 | 适合解决的问题 |
|---|---|---|
| 模型与工具组件库 | LangChain、Semantic Kernel 等 | 统一调用、工具和数据组件 |
| 状态图／持久执行 | LangGraph、工作流系统 | 中断、分支、审批与恢复 |
| 轻量 Agent SDK | OpenAI Agents SDK、Google ADK、Pydantic AI、Agno | 组织工具调用、状态与结果类型 |
| 多 Agent 协作 | CrewAI、AutoGen 历史方案等 | 明确独立职责与协作实验 |
| 记忆与上下文 | Letta、Mem0、Cognee 等 | 长期信息、更新和检索 |

类型化输出约束了格式，不证明内容事实正确。多 Agent 互相同意也不构成独立验证。

## 9.3 运行闭环比角色名字重要

任务输入 → 读取状态 → 选择下一动作 → 权限与参数校验 → 工具执行 → 获取真实观察 → 保存状态 → 验收或继续。每一步都需要错误语义、预算和终止条件。

把角色命名为“专家”“审核员”不会自动获得专业能力。应通过不同证据源、独立工具和人工抽检建立实际检查，而不是只增加对话轮数。

## 9.4 记忆不只是向量检索

区分会话历史、任务状态、用户偏好、外部知识、事件记录与反思摘要。它们的生命周期、可信度和删除要求不同。

记忆写入应关联来源、时间、对象、权限和失效条件。新信息与旧信息冲突时，不能只检索相似度最高的旧文本；需要更新与遗忘机制。更长上下文也不能自动解决过时事实和授权变化。

2026 年 Memora、MemGym、SAM 等研究分别关注失效记忆、长任务记忆评测和状态自适应召回，见 22。它们是研究线索，不是已证明通用方案。

## 9.5 单 Agent 还是多 Agent

适合拆分的情况：任务可并行、数据权限不同、执行环境独立、某个角色有专门工具或评价方法。反之，如果多个角色只是重复调用同一模型讨论，可能只增加费用和错误传播。

需要比较相同预算下的单 Agent、多 Agent 和确定性工作流，记录总调用、重试、人工介入和结果质量。不要只比较最好一次演示。

## 9.6 生产选型清单

检查任务状态是否持久、恢复会重做哪些操作、工具权限在哪一层执行、如何处理结果未知、是否能取消长任务、是否记录版本与成本，以及框架升级如何回归。

选择最能暴露真实状态和错误的框架，而不是隐藏一切细节的封装。关键任务需要可审计、可迁移的业务状态，不应只存在于厂商黑盒记忆中。
