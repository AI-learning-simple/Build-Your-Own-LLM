# 2. 推理框架与模型服务——从 vLLM 到端侧运行时

> **更新基准：2026-11-26。** 推理选型是模型、硬件、负载、质量和服务目标的联合问题，不存在脱离测试条件的“最快框架”。模型运行时、集群服务、API 网关与聊天应用必须分层理解。

## 2.1 先区分五个对象

| 对象 | 职责 | 示例 |
|---|---|---|
| 算子／编译后端 | 执行矩阵计算和优化内核 | CUDA、ROCm、Triton、TensorRT、OpenVINO |
| 模型执行引擎 | 加载模型、管理 KV、执行生成 | vLLM、SGLang、TensorRT-LLM、llama.cpp |
| 分布式服务协调 | 路由、缓存、阶段分离、实例组织 | Dynamo、llm-d、Ray Serve、KServe |
| API 网关 | 提供统一接口、认证、限流与计费 | LiteLLM 等网关与自建服务 |
| 用户应用 | 会话、检索、文件和交互 | Open WebUI、AnythingLLM 等 |

兼容 OpenAI API 只说明部分请求格式相近，不保证工具调用、流式事件、计费、错误语义和模型输出完全一致。

## 2.2 GPU 服务的主流选择

### vLLM

vLLM 围绕高吞吐模型服务组织分页 KV 管理、连续批处理、前缀缓存、分块预填充、推测解码、量化和并行等能力。[1] 当前文档还涉及不同模型类型与硬件插件。

优先检查实际支持矩阵，而不是仅看“支持某家 GPU”：模型架构、精度、量化方法、注意力后端、多模态和并行方式需要一起兼容。`latest` 文档可能是开发预览，不能自动当作当前安装包的说明。

### SGLang

SGLang 以结构化生成与模型服务起家，当前文档包含 RadixAttention、缓存、并行、工具调用及多模态等能力，也有扩散生成方向。[2] 本次旧文档域名 `docs.sglang.ai` 跳转到 `docs.sglang.io`。

共享前缀多的工作负载值得测量其缓存行为，但不能由某项设计推断所有 Agent 请求都更快。缓存命中、并发、提示长度和服务调度共同决定结果。

### TensorRT-LLM

TensorRT-LLM 与 NVIDIA 软件和硬件生态深度结合，适合愿意为特定模型和硬件进行优化的部署。应区分不同执行后端和版本路径，不把历史“所有模型都必须离线编译”的描述永久套在新版本上。

模型支持、量化、引擎构建和运行配置应匹配所用版本；最终比较必须计算工程维护成本，而不是只比较最理想的吞吐结果。

### 其他服务引擎

LMDeploy、KTransformers、ONNX Runtime、OpenVINO 以及各硬件专用运行时提供不同的模型和设备路径。通用推理运行时还覆盖视觉、音频、嵌入和传统模型，不能只用 LLM 生成功能评判它们。

## 2.3 本地与端侧不是缩小的云集群

- **llama.cpp**：围绕本地和多硬件模型执行，常与 GGUF 和量化权重配套。模型格式、转换脚本与运行时支持仍要匹配。
- **Ollama**：更偏模型分发、管理和本地服务体验，不应与底层执行内核完全等同。
- **MLX／MLX-LM**：关注 Apple silicon 上的数组、模型和训练推理路径；统一内存不是无限内存，带宽和并发仍有限制。
- **ONNX Runtime／OpenVINO／LiteRT／ExecuTorch／Core ML**：分别在通用、CPU、移动和特定设备生态提供不同部署能力。
- **WebGPU／WebLLM／Transformers.js**：把部分推理移到浏览器，受下载体积、设备能力、浏览器和隐私设计约束。

离线运行不自动保证隐私：应用仍可能启用遥测、联网工具、云端嵌入或同步。要按实际数据流审查。

## 2.4 维护状态也是选型条件

本次 TGI 仓库页面显示其于 **2026-03-21** 归档、只读；README 仍有历史“维护模式”表述，并指向 vLLM、SGLang、llama.cpp 和 MLX 等方向。[3]

因此 TGI 仍值得作为存量系统和历史架构参考，但不应无说明地列成“所有新项目的主推方案”。迁移要验证 API、模型、量化、工具调用和运维差异，不能只替换容器名字。

自动表格保留重要归档锚点，并明确状态；其他项目“未归档”也不等于持续获得支持。

## 2.5 从单引擎到分布式推理

**NVIDIA Dynamo** 当前官方仓库是 `ai-dynamo/dynamo`，负责多 GPU／节点推理的协调，包括阶段分离、KV 感知路由和缓存等；它可以衔接 vLLM、SGLang、TensorRT-LLM，不取代这些引擎。[4]

**llm-d** 围绕 Kubernetes 上的分布式模型服务组织路由、缓存与预填充／解码协调，本次 README 的新闻记录包含 2026 年 10 月 v1.0；其中某些调度能力仍标为实验性。[5] 项目版本成熟不表示所有模型、网络和硬件组合都已验证。

**Ray Serve** 管理服务副本、请求处理和应用组合；底层大模型执行可以由专门引擎承担。**KServe** 提供 Kubernetes 模型服务相关资源和部署能力。两者的职责与推理内核不同。

## 2.6 性能名词速查

| 术语 | 含义 | 需要警惕 |
|---|---|---|
| TTFT | 请求到首个输出 Token 的时延 | 排队、网络、检索是否计入 |
| TPOT／ITL | 后续 Token 的生成或到达间隔 | 客户端与服务端测法不同 |
| 吞吐 | 单位时间合格处理量 | 输入／输出 Tokens、请求数不可混用 |
| Goodput | 满足 SLO 的有效吞吐 | 快但大量超时不等于好服务 |
| Continuous batching | 动态加入和移出生成请求 | 长短请求公平性与尾延迟 |
| Prefix caching | 复用相同前缀的计算状态 | 命中率、租户隔离、缓存成本 |
| Speculative decoding | 用候选生成与校验减少串行成本 | 接受率、额外内存和模型配对 |
| PD 分离 | 预填充与解码分别部署 | KV 传输、路由和负载不均 |
| 量化 | 用低位表示减少资源需求 | 权重、激活、KV 是不同对象 |

Prefill 和 Decode 的资源特征不同，但不是绝对的“一个只算力、一个只带宽”。批量、模型结构、并行与硬件都会改变瓶颈。

## 2.7 采购或迁移前的测试清单

1. 固定模型、权重 revision、分词器、模板和生成参数。
2. 固定硬件、驱动、引擎版本、精度与并行配置。
3. 准备真实长度分布、多轮、工具调用与多模态样本。
4. 同时测冷启动、预热后、缓存命中与未命中。
5. 从低并发逐级增加，观察 p50／p95／p99、拒绝与超时。
6. 检查输出质量、结构化格式、停止条件和截断。
7. 测 OOM、worker 失败、模型升级和服务回退。
8. 核算单位合格输出成本，包含空闲、冗余、缓存与运维。

量化前后不必逐 Token 相同，但必须满足任务质量目标。服务端宣称请求成功，不代表长响应已经完整送达用户。
