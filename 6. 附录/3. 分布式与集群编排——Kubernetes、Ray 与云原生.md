# 3. 分布式与集群编排——Kubernetes、Ray 与云原生

> **更新基准：2026-11-26。** 本章保留用户指定的“分布式与 Kubernetes”主题。后续分类从 4 开始。“能启动多台机器”不等于获得高性能、容错或多租户安全。

## 3.1 分布式系统有三个不同平面

- **计算平面**：模型、张量、数据和通信实际执行在哪里。
- **控制平面**：谁分配资源、启动任务、保存状态、恢复失败。
- **服务平面**：用户请求怎样认证、排队、路由和得到结果。

训练的 all-reduce、集群的 Pod 调度、在线服务的负载均衡都是“调度或通信”，但处在不同层次。排查问题时首先判断是哪一层。

## 3.2 Kubernetes 解决什么

Kubernetes 使用声明式资源和控制器协调容器生命周期。Pod、Deployment、StatefulSet、Job、Service、存储和网络组件可以承载 AI 负载，但默认并不理解参数分片、训练 step 或 KV Cache。

| 能力 | 常见组件 | 边界 |
|---|---|---|
| 容器执行 | containerd、CRI-O | 镜像与依赖仍需管理 |
| 设备暴露 | Device Plugin、DRA、GPU Operator | 不自动保证模型可使用该设备 |
| 作业表达 | Job、JobSet、训练相关 CRD | 并行拓扑与恢复语义要验证 |
| 配额与准入 | Kueue 等 | 与 Pod 放置不是同一层 |
| 批调度 | Volcano、YuniKorn、调度插件 | 策略须匹配资源和工作负载 |
| 在线服务 | KServe、Ray Serve、网关与路由 | 不替代底层模型执行 |
| 观测 | Prometheus、OpenTelemetry、Grafana | 系统指标不等于模型质量 |
| GitOps 与部署 | Argo CD、Flux、Helm | 自动发布仍需评测门禁 |

表中通用基础设施是 AI 系统的支撑组件，不宣称它们本身是 AI 框架。

## 3.3 Kueue、Volcano 和 Kubernetes scheduler

**Kueue** 主要回答“作业何时可以被准入”：队列、资源配额、优先级、公平共享和抢占等。**Kubernetes scheduler** 负责把可调度的 Pod 放到具体节点。**GPU 切分或共享机制**则处理实际设备资源，不由 Kueue 自动完成。[1]

Gang scheduling 强调一组 worker 协同获得资源。Kueue 的作业级准入和 Pod 就绪机制，与严格原子化的成组调度不是同一个保证。Volcano 等批调度方案有自己的队列和成组调度设计，不能仅因为都支持 AI 作业就认为可以无成本互换。

常见失败是：每个训练作业启动一部分 worker 后占住资源，剩余 worker 无法启动。解决它需要理解准入、放置、超时回收和优先级的组合，而不是简单增加副本数。

## 3.4 Ray 与 Kubernetes 的组合

Ray 负责分布式任务与 Actor 执行；KubeRay 把 Ray 的集群和应用生命周期接入 Kubernetes。[2]

| KubeRay 资源 | 主要用途 | 典型场景 |
|---|---|---|
| RayCluster | 管理 head／worker Pod 与集群生命周期 | 持续计算环境 |
| RayJob | 管理任务提交、执行与可选清理 | 批量数据、训练和评测 |
| RayService | 组织 Ray Serve 应用及集群 | 长期在线服务 |

Ray 的逻辑资源调度、Kubernetes 的物理容器调度以及节点扩缩容要协调。内层扩大 worker 需求，不表示外层立刻存在足够 GPU；扩容时还受到镜像、模型下载、设备初始化和存储吞吐影响。

Ray Train 的训练行为见 1，Ray Serve 与推理引擎的分工见 2。不要把 Ray Serve 的副本扩容等同于任意分片模型可以在线增减 GPU。

## 3.5 Slurm、Dask、Spark 和工作流系统

- **Slurm**：在 HPC 和共享集群中常用于资源分配、作业排队和批执行；不要求先引入 Kubernetes。
- **Dask**：面向 Python 数组、表格与任务图的并行计算，适合相应数据和计算工作负载。
- **Spark／Flink**：大规模数据处理与流式计算生态；不是用来替代模型训练反向传播的默认工具。
- **Airflow／Dagster／Prefect**：编排数据与业务任务依赖，关注运行、重试和资产；不是 GPU collective 通信库。
- **Temporal**：持久工作流与状态恢复的另一种工程路径，外部副作用仍需要业务幂等。

选型应遵循已有团队能力和任务类型。所有系统一起部署，不会自动形成更先进的平台，反而可能形成多个互相不了解的调度器。

## 3.6 AI 负载对基础设施的特殊要求

### 设备与拓扑

相同数量的 GPU 不一定提供相同通信性能。需要了解同节点互连、跨节点 RDMA／以太网、NUMA 和拓扑放置。MIG、时间切片、共享服务与完整设备分配，也有不同的隔离和性能边界。

### 存储与网络

训练数据、模型权重、检查点和 KV 传输的访问模式不同。小文件元数据、共享存储拥堵或检查点写入暂停都可能拖慢计算。不要因为 GPU 利用率低就首先更换训练框架。

### 长任务与失败恢复

worker 退出可能要求整个并行组恢复。要明确检查点频率、恢复点目标、数据游标、随机状态和优化器状态。Pod 重新启动，只恢复了进程，不保证训练语义正确恢复。

### 在线服务

冷启动、模型加载、请求排队、并行组健康和缓存热度决定用户体验。按 CPU 利用率自动扩容通常不能充分刻画 LLM 服务负载。Dynamo 和 llm-d 等专门服务层处理的是这部分问题，不取代整个集群管理。[3]

## 3.7 多租户与成本

Namespaces 是组织边界的一部分，但不是完整安全边界。仍需 RBAC、网络策略、工作负载身份、秘密管理、镜像验证和数据访问控制。

配额需要分别考虑 GPU、CPU、内存、存储、并发和模型使用费用。抢占可以改善利用率，但也可能增加检查点和重启损失；短任务公平与大型训练作业完成时间可能发生冲突。

成本报告应包含闲置、失败、冗余和等待资源，不只展示 GPU 单价。吞吐提高而服务尾延迟恶化，也未必符合业务目标。

## 3.8 从小到大的部署路线

1. 单机脚本：先建立可复现运行与日志。
2. 单机多卡：验证并行和检查点。
3. 固定小集群：验证网络、存储和失败恢复。
4. 多团队共享：引入配额、队列、身份和审计。
5. 弹性服务：加入准入、路由、负载测试与升级回退。

每一层都应解决已出现的问题，而不是提前复制大公司的全部组件。
