# 1. 主流模型训练框架——从 PyTorch 到 Ray

> **更新基准：2026-11-26。** 训练框架不是一层软件。必须先区分张量计算、模型定义、分布式并行、训练配方、作业编排和实验管理。Ray 是本章重点，但它不是 PyTorch 的同层替代品。

## 1.1 一张职责地图

| 层次 | 核心问题 | 代表项目 | 常见误解 |
|---|---|---|---|
| 张量与自动微分 | 如何表达和计算梯度 | PyTorch、JAX、TensorFlow | 选定底层框架就完成训练平台选型 |
| 模型与组件 | 如何实现网络和加载权重 | Transformers、Keras、Flax、timm | 所有权重都能无损互换 |
| 分布式并行 | 参数、梯度、激活怎样跨设备 | DDP、FSDP2、Megatron Core、DeepSpeed | 多进程启动等于高效模型并行 |
| 训练配方 | 如何微调、对齐和组织实验 | TRL、PEFT、LLaMA-Factory、Axolotl、torchtitan | 配方工具就是新的自动微分引擎 |
| RL／Agent 后训练 | 如何协调生成、奖励与更新 | verl、OpenRLHF、slime 等 | rollout 和训练可以任意混用版本 |
| 集群执行 | worker 怎样获得资源并恢复 | Ray Train、KubeRay、Slurm、Kubernetes | 作业调度器负责梯度同步算法 |

选择技术栈时可以组合这些层，而不是要求一款产品包办所有职责。

## 1.2 三种底层生态

### PyTorch

PyTorch 的核心是张量、自动微分和模块系统，配合 `torch.compile`、`torch.distributed` 与庞大的模型生态。研究代码容易修改不代表分布式成本自动很低，编译命中、动态图边界、检查点和内核兼容仍需测量。

- **DDP**：每个数据并行 rank 通常持有模型副本，主要同步梯度；适合模型在单卡可容纳的场景。
- **FSDP／FSDP2**：对参数、梯度和优化器状态做分片；FSDP2 的组合方式与旧接口不同，不能直接照搬旧配置。
- **DTensor／DeviceMesh**：表达张量布局与设备拓扑，帮助组合张量、数据等并行方式；它们本身不是完整训练配方。
- **torchtitan**：PyTorch 原生的大模型训练平台。本次 README 已覆盖预训练、SFT／LoRA、TitanRL 等方向，以及多维并行；部分后端和容错能力明确为实验功能。[1]

### JAX

JAX 以可组合的函数变换、自动微分与编译为特点，常与 XLA、Flax、Optax 和分布式分片方案配合。它适合愿意采用函数式状态管理、重视编译与设备布局的团队。数据类型、静态形状、随机数和重编译行为需要显式理解。

### TensorFlow 与 Keras

TensorFlow 提供训练、图执行和部署相关生态；Keras 应按当前多后端设计与具体兼容文档理解，而不是永久等同于某个 TensorFlow 子模块。存量系统、移动部署和已有数据流水线可能使其仍是合理选择，不能用社交热度代替迁移收益。

## 1.3 大规模并行：Megatron、DeepSpeed 与原生方案

**Megatron-LM／Megatron Core** 面向大模型规模化训练，重点在张量、流水线、专家等并行及高效实现。项目实现、可复用核心组件和更高层配方需要分别判断。它的优势不能脱离模型形状、集群拓扑与通信带宽讨论。

**DeepSpeed** 提供 ZeRO 等内存与分布式优化。ZeRO 的不同阶段分别切分不同状态；offload 能缓解设备内存限制，但会引入主存、CPU 和互连成本。DeepSpeed、FSDP2 和 Megatron 的比较不是“哪个名字更新”，而是能否适配当前模型、训练规模、检查点与运维方式。

**Accelerate** 帮助组织设备、混合精度与不同训练后端，使同一训练脚本更容易切换执行方式。它不是独立替代 PyTorch 的张量框架。

**NeMo 的名称需要特别注意**：本次访问旧 `NVIDIA/NeMo` 地址显示为 `NVIDIA-NeMo/Speech`，README 说明了拆仓与语音／音频方向。[2] 因此，不能继续把旧仓库当作所有 NVIDIA LLM 训练产品的唯一入口；应核对具体领域文档和当前仓库。Framework、Core、Bridge、RL、部署产品不是可以互换的名称。

## 1.4 Ray 专题：它在训练体系中的作用

Ray 提供面向分布式 Python 计算的任务、Actor、对象与资源管理机制。围绕这一运行时，生态中有不同应用库：

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| Ray Core | 分布式任务、Actor 与执行资源 | 自动决定最优模型并行 |
| Ray Train | 训练 worker 的分布式组织、指标和检查点相关流程 | 替代 PyTorch 的梯度计算 |
| Ray Data | 分布式数据读取、变换与批处理 | 自动证明数据质量与训练无泄漏 |
| Ray Tune | 试验调度、搜索与资源分配 | 保证搜索空间和评价指标合理 |
| RLlib | 强化学习算法与执行组件 | 等同于所有 LLM RLHF 系统 |
| Ray Serve | 在线推理服务与应用部署 | 等同于 vLLM 等底层模型执行引擎 |
| KubeRay | 在 Kubernetes 上管理 Ray 资源 | 替代 Ray Train 或集群网络 |

典型组合是：Kubernetes 提供集群资源 → KubeRay 管理 Ray 集群 → Ray Train 启动训练 worker → PyTorch／FSDP／DeepSpeed 执行训练 → 对象存储保留检查点。也可以不使用 Kubernetes，在其他环境中运行 Ray。[3][4]

**Ray 适合什么？** 数据预处理、训练、超参搜索、评测或 RL rollout 需要在同一计算环境协调时；Python 团队希望复用分布式任务与 Actor 模型时。

**什么时候不必上 Ray？** 一个静态 `torchrun` 作业已经能稳定完成训练，团队没有额外编排需求时。引入 Ray 会增加控制面、调度、资源声明、日志和版本管理成本，不应仅为了“分布式”三个字引入。

资源声明也不是硬件隔离的全部：申请 GPU 资源不意味着自动获得安全沙箱、网络隔离或完整的多租户保障。不要把 Ray 控制接口无保护地暴露在不可信网络。

## 1.5 微调与对齐工具怎么选

- **Transformers Trainer／Accelerate**：已有 Hugging Face 模型和自定义训练逻辑，需要相对透明的集成。
- **PEFT**：LoRA 等参数高效适配的组件层；不是一套端到端训练服务。
- **TRL**：SFT、偏好与强化学习相关训练器，具体算法和 API 应按版本验证。
- **LLaMA-Factory／Axolotl**：通过配置组织多模型微调、数据处理和训练配方；需要核对模板、标签掩码与后端。
- **Unsloth**：强调特定路径的训练优化；收益和支持范围依赖模型、硬件、量化和版本，不是任意模型的统一加速保证。
- **Lightning**：训练循环与工程组织抽象，适合希望规范实验代码的团队；抽象层不消除调试分布式错误的需要。

最先检查的通常不是支持多少算法，而是数据模板和损失是否正确：padding 是否参与损失、用户文本是否被错误训练、样本长度是否被截断、评测是否泄漏。

## 1.6 RL 后训练：训练与 rollout 是两种负载

LLM 强化学习循环通常包含生成、工具／环境交互、奖励、优势估计和策略更新。推理阶段追求生成吞吐与低延迟，训练阶段需要反向传播与状态保存，二者的最优资源布局可能不同。

以 **verl** 为例，当前官方仓库跳转到 `verl-project/verl`；文档讨论 Ray worker、FSDP／Megatron 训练后端以及 vLLM／SGLang 等 rollout 引擎。[5] 2026 年 README 还有主线与 recipe 的迁移提示。因此不能把某篇旧博客的 Ray、训练器与推理引擎版本直接拼到最新主线。

选择后训练框架还要检查异步采样带来的策略滞后、权重同步成本、奖励可复现性、超时和轨迹丢失。训练曲线更好不自动意味着 Agent 在真实工具环境中更可靠。

## 1.7 一套可执行的选型顺序

1. 明确任务：预训练、继续预训练、SFT、偏好学习还是环境 RL。
2. 明确模型：稠密／MoE、多模态、上下文长度与可训练参数规模。
3. 测量单卡内存组成，决定是否需要分片和 offload。
4. 检查实际拓扑：设备间互连、节点网络、存储和数据吞吐。
5. 选择能覆盖需求的最简单并行与编排组合。
6. 用小规模测试验证损失、梯度、断点恢复及数据顺序。
7. 扩大规模后报告有效样本吞吐、通信、重算、失败恢复和总成本。

不要混淆峰值 FLOPS、实际算力利用和训练进度。使用更低精度也要验证收敛、数值稳定与检查点兼容，而非只记录速度。
