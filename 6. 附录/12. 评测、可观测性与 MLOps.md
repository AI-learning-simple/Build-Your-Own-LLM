# 12. 评测、可观测性与 MLOps

> **更新基准：2026-11-26。** 训练指标、离线评测、线上质量和系统可用性属于不同层次。一个平台收集到了 Trace，不等于已经知道业务是否成功。

## 12.1 生态地图

| 层次 | 代表项目 | 主要对象 |
|---|---|---|
| 实验追踪 | MLflow、Weights & Biases、Aim、ClearML | 参数、版本、指标、产物 |
| 模型评测 | lm-evaluation-harness、OpenCompass、LightEval | 固定模型任务和基准 |
| 应用与 RAG 评测 | Ragas、DeepEval、Promptfoo 等 | 检索、生成、提示与工作流 |
| Agent 评测 | Agent 任务环境、工具和代码基准 | 多步结果、副作用、成本 |
| LLM 可观测性 | Langfuse、Phoenix、Opik 等 | 调用链、评测和反馈 |
| 系统监控 | Prometheus、OpenTelemetry、Grafana | 指标、日志、Trace 和资源 |
| 数据／模型漂移 | Evidently、Alibi Detect 等 | 输入、输出和性能变化 |
| 生命周期 | 模型注册、部署、灰度和回退系统 | 版本与运行状态 |

传统 MLOps 与 LLMOps 有重叠。提示词、检索索引、工具和策略配置也成为需要版本管理的交付物。

## 12.2 建立分层验收

1. **格式与契约**：字段、类型、约束是否符合接口。
2. **事实与计算**：有无依据、引用是否有效、程序结果是否正确。
3. **任务结果**：目标是否真正完成，是否误改资源。
4. **行为边界**：有无越权、重复执行和不当数据访问。
5. **效率与体验**：成本、时延、人工介入、用户满意度。

平均分不能掩盖关键失败。一百个普通问题成功，不抵消一次错误付款或错误修改重要配置。

## 12.3 LLM-as-a-Judge 的正确位置

模型评审可帮助扩大覆盖，但会受到提示、顺序、长度、风格、模型家族和自身知识限制影响。应使用明确 rubric、人工标定、盲测和争议复核，报告一致性，而不是把一个小数视为客观真理。

确定性的结果尽量用确定性方法验证：单元测试、计算、数据库回执和结构校验。模型不应同时生成结果、制定评分规则并独自宣布成功。

## 12.4 Trace 应记录什么

任务 ID、版本、输入摘要、检索来源、工具调用、返回状态、审批、Token、耗时和成本。敏感材料需要脱敏和保存期限，凭据不能写入日志。

把调用链展开后，应能区分模型错、工具错、数据错、权限错、超时和用户目标不明确。一个统一的“Agent failed”计数不足以指导改进。

## 12.5 版本与回归

固定测试集之外，还要持续加入线上失败案例；同时保留未被反复优化污染的测试集。模型、提示、工具、检索索引或 SDK 升级都可能改变结果。

生产发布可以采用影子评测、有限灰度、人工抽检和回退。基准分数上升不自动批准上线，尤其当行为、费用或尾延迟发生退化时。

## 12.6 选型清单

能否导出原始数据、支持自定义评分、关联业务回执、隔离租户、控制保留策略、复现特定版本、记录成本以及在供应商更换后继续使用。数据量和 Trace 长度还决定存储与查询成本。
