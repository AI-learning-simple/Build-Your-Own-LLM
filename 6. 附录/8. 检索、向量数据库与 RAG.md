# 8. 检索、向量数据库与 RAG

> **更新基准：2026-11-26。** RAG 是用可检索证据支持生成的系统设计，不是某一种向量数据库。检索命中、证据足够和最终答案正确需要分别验证。

## 8.1 一条完整链路

解析 → 分块 → 元数据与权限 → 稀疏／稠密索引 → 查询理解 → 召回 → 重排 → 上下文组织 → 生成与引用 → 结果检查。出错可能发生在任意环节，不能把所有问题归结为 embedding 模型不够大。

| 层次 | 代表项目 | 选择依据 |
|---|---|---|
| 向量索引库 | FAISS、hnswlib、Annoy、USearch | 本地索引、算法、内存与召回 |
| 向量数据库 | Milvus、Qdrant、Weaviate、Chroma、LanceDB | 过滤、持久化、多租户、运维 |
| 数据库向量扩展 | pgvector 等 | 与既有事务数据和权限结合 |
| 全文与混合检索 | Elasticsearch、OpenSearch、Meilisearch、Vespa | 稀疏搜索、结构化过滤与排序 |
| 检索流水线 | Haystack、LlamaIndex、LangChain | 组件组织、数据连接和应用接口 |
| 应用平台 | RAGFlow、LightRAG、FastGPT 等 | 文档处理、检索体验与管理 |
| 知识图谱 | Neo4j、图构建与 GraphRAG 实现 | 实体关系、路径与全局汇总 |

FAISS 不是开箱即用的多租户数据库，向量数据库也不自动提供高质量答案。

## 8.2 主流设计的差异

稠密检索擅长语义近似，稀疏检索对于专有名词、编号和精确词项仍很重要。混合检索将多个信号结合，但需要统一评分或融合策略。

重排器可以改善候选顺序，却增加时延和费用。GraphRAG、层次摘要、长上下文和多跳搜索适用于不同问题，不能把新方法当成所有文档问答的必选升级。

Agentic RAG 让系统决定继续搜索、改写查询或读取更多证据。收益来自更好的任务完成，不是搜索次数更多；必须设预算、停止条件和无答案出口。

## 8.3 权限与删除

权限过滤最好在召回和数据访问层落实，而不是将未经授权内容传入模型后要求它保密。索引更新需要版本与生效时间，删除还要考虑缓存、衍生摘要和备份。

跨租户共享 embedding 或前缀缓存时，应评估信息隔离。检索日志本身也可能包含敏感查询和文件片段。

## 8.4 评测要拆开

- **召回**：正确证据是否出现在候选中，使用 recall 等指标。
- **排序**：关键证据是否排在有限上下文预算内。
- **引用**：链接是否指向实际支持该结论的段落。
- **生成**：是否忠于证据，是否遗漏或添加无依据事实。
- **拒答**：资料不足、冲突或过期时是否明确说明。
- **服务**：时延、成本、更新延迟、失败恢复和人工修正。

用 LLM 评价可以辅助，但应校准评审一致性并抽样人工复核。语义相关不等于证据支持。

## 8.5 怎么选最小方案

少量资料先建立清晰解析和关键词基线，再增加向量召回和重排；已有 PostgreSQL 且规模合适时，可先评估扩展方案。只有当吞吐、过滤、索引更新或运维真的构成瓶颈时，再引入独立系统。

服务公开网页还需要数据使用和抓取边界，不能以“做知识库”为理由绕过权限。
