# 20. 低代码、业务自动化与应用开发

> **更新基准：2026-11-26。** 低代码减少部分开发工作，不消除数据建模、授权、评测和运行责任。工作流节点多，也不等于 Agent 自主能力强。

## 20.1 产品地图

| 形态 | 代表生态 | 适合的工作 |
|---|---|---|
| LLM 应用平台 | Dify、Flowise、Langflow、FastGPT | 模型、RAG、工具和流程组合 |
| 业务自动化 | n8n、Node-RED、Activepieces 等 | 事件、连接器、条件和动作 |
| 持久工作流 | Temporal、Conductor、Trigger.dev 等 | 长任务、状态和恢复 |
| 交互原型 | Gradio、Streamlit、Chainlit | 模型演示与数据应用 |
| 前端 AI SDK | Vercel AI SDK、聊天与交互组件 | 流式响应、模型接入与界面 |
| 内部工具 | Appsmith、ToolJet、Budibase 等 | 表单、业务数据与管理界面 |
| 业务数据底座 | 低代码表格、数据库界面、内容系统 | 结构化数据与团队工作流 |

这些类别存在重叠，主章节只是索引位置。同一仓库不会因具有 RAG、聊天和自动化三种功能计成三款产品。

## 20.2 声明式工作流与动态 Agent

固定图适合流程明确、需要稳定验收和审批的任务。Agent 适合需要根据中间结果决定下一动作的任务，但需要更多运行控制与测试。

一个业务系统可以把二者组合：确定性流程负责审批和状态，Agent 只处理某个非结构化步骤。不要把全部流程交给模型重新推理，尤其是金额计算、权限和交易状态。

## 20.3 连接器不是无成本集成

连接器还要处理凭据、版本、字段差异、限流、分页、重试、删除与业务回执。一个演示里能读取 CRM，不代表已经满足生产多租户、审计和故障恢复要求。

API 返回成功与业务完成需要分开。工作流重跑可能重复发邮件、建工单或提交订单，因此必须设计幂等、去重或补偿。

## 20.4 平台选型与许可

公开源码、开源许可、source-available、fair-code 和商业套餐不同。以 n8n 等产品为例，不能只看到 GitHub 仓库就默认符合任意开源或商业再分发需求；要阅读当时许可与使用条款。

还要检查自托管与云版本差异：身份、日志、连接器、并发、备份、团队功能和费用可能不同。用户需要的是完整可运营系统，不只是一张可拖拽的图。

**维护状态更新：**本次 GitHub 元数据与[Flowise 仓库页面](https://github.com/FlowiseAI/Flowise)均显示其于 2026-08-13 归档、只读；README 提到后续讨论，但本次材料不足以确认继任项目。故表中保留 Flowise 作为历史与迁移参考，不应无说明地作为新项目主推方案，也不猜测商业服务是否同步停止。

## 20.5 上线最小清单

明确责任人、输入输出契约、权限、超时、失败告警、人工升级、数据保留和回退。用真实失败案例测试；有条件时采用灰度发布，并保留不依赖模型的备用流程。

评估总成本：平台、模型、外部 API、存储、人工复核和维护。自动化节省的时间只有真正释放或产生额外价值时，才形成经营收益。
