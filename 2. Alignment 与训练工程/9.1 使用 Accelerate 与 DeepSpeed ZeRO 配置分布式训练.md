# 9.1 使用 Accelerate 与 DeepSpeed ZeRO 配置分布式训练

> **环境要求**：Linux、兼容的 CUDA/PyTorch/DeepSpeed 构建、支持 BF16 的 NVIDIA GPU，以及足够的主机内存和可编译 DeepSpeed 算子的工具链。本例默认单卡，8 GB 是否足够必须实际测量；多卡分片作为可选核验，不在单卡结果中冒充。macOS/MPS 不能直接运行本例。
>
> **本节目标**：用统一模型、输入、计算精度与有效 batch，分别测量基线、梯度检查点、ZeRO-2 + CPU offload 三种配置的 GPU 显存与完整更新耗时。单卡关注重计算与状态迁移，多卡才能验证跨卡分片；随机 Token 的资源实验不是训练效果评估。

## 二、一个统一口径的训练脚本

三组都使用 Accelerate + DeepSpeed、同一个模型 revision、BF16 计算和同一套 AdamW 超参数，避免把“FP16 权重直接交给普通 AdamW”与“DeepSpeed 的 FP32 主权重/优化器状态”混比：

- **A：baseline**，ZeRO stage 0，不重计算、不 offload；stage 0 表示不启用 ZeRO 分片，仍使用 DeepSpeed 引擎。
- **B：checkpoint**，在 A 上只开启 Gradient Checkpointing。
- **C：offload**，在 B 上启用 ZeRO-2 + CPU optimizer offload；单卡没有分片比例收益，此组观察的是 offload 及其实现开销。

本实验显式选择 **FP32 梯度累积**，因此实际状态账本不完全等于第9章用于讲解的 BF16 梯度 \(16P\) 简式；三组都保持这项设置。GPU 与 CPU 上 Adam 的内核仍可能不同，所以这是配置级工程对照，不是位级相同的实现。随机 Token 只用于资源测量，不能据此判断模型训练质量。

将下面的完整脚本保存为实验目录中的 `train_memory.py`。每次只测一个配置，由第四节分别启动新进程；不要在同一 Notebook 进程中依次装载三份模型。模型首次下载与算子编译不计入稳态计时。

```python
import argparse
import gc
import json
import os
import resource
import time
from importlib.metadata import version

import torch
from accelerate import Accelerator
from accelerate.utils import DistributedType, DummyOptim, set_seed
from transformers import AutoModelForCausalLM

parser = argparse.ArgumentParser()
parser.add_argument("--case", choices=["baseline", "checkpoint", "offload"], required=True)
parser.add_argument("--model", default="Qwen/Qwen2.5-0.5B")
parser.add_argument("--revision", default="main")
parser.add_argument("--micro-batch", type=int, default=1)
parser.add_argument("--seq-len", type=int, default=256)
parser.add_argument("--accumulation", type=int, default=4)
parser.add_argument("--warmup-updates", type=int, default=2)
parser.add_argument("--measure-updates", type=int, default=5)
args = parser.parse_args()
assert min(args.micro_batch, args.seq_len - 1, args.accumulation,
           args.warmup_updates, args.measure_updates) > 0

accelerator = Accelerator(mixed_precision="bf16", gradient_accumulation_steps=args.accumulation)
assert accelerator.distributed_type == DistributedType.DEEPSPEED
assert accelerator.device.type == "cuda" and torch.cuda.is_bf16_supported()
set_seed(42)
config = accelerator.state.deepspeed_plugin.deepspeed_config
assert config["train_micro_batch_size_per_gpu"] == args.micro_batch
assert config["gradient_accumulation_steps"] == args.accumulation
assert config["bf16"]["enabled"] is True
assert config["data_types"]["grad_accum_dtype"] == "fp32"
zero = config["zero_optimization"]
assert zero["stage"] == (2 if args.case == "offload" else 0)
assert (zero.get("offload_optimizer", {}).get("device") == "cpu") == (args.case == "offload")

model = AutoModelForCausalLM.from_pretrained(
    args.model, revision=args.revision,
    torch_dtype=torch.bfloat16, attn_implementation="sdpa",
)
model.train()
model.config.use_cache = False
checkpointing = args.case != "baseline"
if checkpointing:
    model.gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False})
else:
    model.gradient_checkpointing_disable()
assert model.is_gradient_checkpointing == checkpointing
resolved_revision = getattr(model.config, "_commit_hash", None)
vocab_size = model.config.vocab_size
optimizer = DummyOptim(model.parameters(), lr=1e-5)
model, optimizer = accelerator.prepare(model, optimizer)
model.train()
assert next(model.parameters()).dtype == torch.bfloat16
assert model.train_micro_batch_size_per_gpu() == args.micro_batch
assert model.gradient_accumulation_steps() == args.accumulation
assert model.train_batch_size() == args.micro_batch * args.accumulation * accelerator.num_processes

# 各配置同一 rank 的输入相同，不同 rank 的输入不同；生成不放进计时区间。
generator = torch.Generator(device="cpu").manual_seed(1234 + accelerator.process_index)
num_micro_steps = (args.warmup_updates + args.measure_updates) * args.accumulation
batches = [torch.randint(vocab_size, (args.micro_batch, args.seq_len), generator=generator)
           for _ in range(num_micro_steps)]
step_index = 0

def run_update():
    global step_index
    for _ in range(args.accumulation):
        with accelerator.accumulate(model):
            ids = batches[step_index].to(accelerator.device)
            output = model(input_ids=ids, labels=ids, use_cache=False)
            accelerator.backward(output.loss)
            optimizer.step()
            optimizer.zero_grad()
            step_index += 1
            del output, ids


torch.cuda.synchronize()
torch.cuda.reset_peak_memory_stats()
for _ in range(args.warmup_updates):
    run_update()
torch.cuda.synchronize()
warmup_peak = torch.cuda.max_memory_allocated()
assert model.global_steps == args.warmup_updates
gc.collect()
accelerator.wait_for_everyone()
torch.cuda.synchronize()
baseline = torch.cuda.memory_allocated()
torch.cuda.reset_peak_memory_stats()
updates_before = model.global_steps
start = time.perf_counter()
for _ in range(args.measure_updates):
    run_update()
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
peak = torch.cuda.max_memory_allocated()
reserved_peak = torch.cuda.max_memory_reserved()
assert model.global_steps - updates_before == args.measure_updates

row = {
    "case": args.case, "rank": accelerator.process_index,
    "world_size": accelerator.num_processes,
    "model": args.model, "revision": resolved_revision or args.revision,
    "gpu": torch.cuda.get_device_name(accelerator.device),
    "cuda": torch.version.cuda,
    "versions": {p: version(p) for p in ["torch", "transformers", "accelerate", "deepspeed"]},
    "dtype": "bf16", "grad_accum_dtype": "fp32", "checkpointing": checkpointing,
    "micro_batch": args.micro_batch, "seq_len": args.seq_len,
    "accumulation": args.accumulation,
    "effective_batch": args.micro_batch * args.accumulation * accelerator.num_processes,
    "baseline_gib": baseline / 2**30,
    "peak_allocated_gib": peak / 2**30,
    "extra_peak_gib": (peak - baseline) / 2**30,
    "peak_reserved_gib": reserved_peak / 2**30,
    "warmup_peak_gib": warmup_peak / 2**30,
    "seconds_per_update": elapsed / args.measure_updates,
    "cpu_max_rss_gib": resource.getrusage(resource.RUSAGE_SELF).ru_maxrss / 2**20,
    "cpu_threads": torch.get_num_threads(),
    "cuda_visible_devices": os.environ.get("CUDA_VISIBLE_DEVICES"),
}
print("RESULT " + json.dumps(row, ensure_ascii=False), flush=True)
accelerator.wait_for_everyone()
accelerator.end_training()
```

此脚本针对 **Linux CUDA 环境**，`ru_maxrss` 按 Linux 的 KiB 单位转换；它是进程生命周期内的主机 RSS 高水位，不是 GPU offload 专属占用。每个 rank 都输出一行结果，多卡吞吐比较应采用最慢 rank 的更新耗时。计时覆盖输入传输、前向、反向和优化器更新，而不是只计 GPU kernel；这样不会漏掉 CPU offload 的耗时。显存报告是 PyTorch allocator 口径，不含全部 NCCL/CUDA 外部分配；同时记录 `nvidia-smi` 有助于解释差额，但不能混用口径。

## 三、DeepSpeed ZeRO 配置文件

下面这段配置生成代码由读者在独立实验目录中运行，生成 `ds_baseline.json`、`ds_checkpoint.json`、`ds_offload.json`。**本节文档不附带已经运行的测量结果。**

```python
import copy
import json
from pathlib import Path

base = {
    "train_micro_batch_size_per_gpu": 1,
    "gradient_accumulation_steps": 4,
    "train_batch_size": "auto",
    "bf16": {"enabled": True},
    "fp16": {"enabled": False},
    "data_types": {"grad_accum_dtype": "fp32"},
    "gradient_clipping": 1.0,
    "optimizer": {
        "type": "Adam",
        "params": {"lr": 1e-5, "betas": [0.9, 0.999], "eps": 1e-8,
                   "weight_decay": 0.01, "adam_w_mode": True},
    },
    "zero_optimization": {"stage": 0},
    "steps_per_print": 1000000,
}
for case in ["baseline", "checkpoint", "offload"]:
    config = copy.deepcopy(base)
    if case == "offload":
        config["zero_optimization"] = {
            "stage": 2,
            "offload_optimizer": {"device": "cpu", "pin_memory": True},
            "contiguous_gradients": True,
            "overlap_comm": False,
            "reduce_bucket_size": 5_000_000,
            "allgather_bucket_size": 5_000_000,
        }
    Path(f"ds_{case}.json").write_text(json.dumps(config, indent=2), encoding="utf-8")
```

- `train_micro_batch_size_per_gpu=1` 与脚本真实输入一致；这里没有 DataLoader，不能留给 Accelerate 从 DataLoader 自动猜。
- `train_batch_size="auto"` 由 **Accelerate 集成层**填为 micro-batch × accumulation × 数据并行进程数；不是任意 DeepSpeed 原生入口都接受这个字符串。
- 三组都在 JSON 内定义优化器，因此脚本用 `DummyOptim` 占位，让 DeepSpeed 创建真实优化器；CPU offload 路径使用其 CPU Adam 实现，不是把 GPU Adam 状态简单复制到 CPU 就结束。
- 一阶矩和二阶矩各有 \(P\) 个 FP32 元素，合计 \(8P\) 字节；再加 FP32 主权重才是理论账本里的 \(12P\)，不能把“元素数两倍”误当“BF16 参数字节数两倍”。
- `overlap_comm=False` 和较小通信桶只是让入门实验减少一部分缓冲干扰，不是最佳性能推荐；多卡调优应单独比较这些参数。

## 四、用 Accelerate 启动一次真实的 DeepSpeed 训练

在同一个实验目录保存 `accelerate_local.yaml`，显式选择它，避免读取机器上不明来源的默认 Accelerate 配置：

```yaml
compute_environment: LOCAL_MACHINE
distributed_type: DEEPSPEED
use_cpu: false
num_machines: 1
num_processes: 1
machine_rank: 0
mixed_precision: bf16
rdzv_backend: static
same_network: true
deepspeed_config: {}
```

先确认当前终端没有遗留的 `ACCELERATE_*`、`RANK`、`WORLD_SIZE` 等训练环境变量。下面三次启动顺序执行、各用独立进程，只替换配置和 case 标签，输入形状与有效 batch 均相同：

```bash
CUDA_VISIBLE_DEVICES=0 accelerate launch --config_file accelerate_local.yaml --use_deepspeed --deepspeed_config_file ds_baseline.json --num_processes 1 --num_machines 1 --mixed_precision bf16 train_memory.py --case baseline --micro-batch 1 --seq-len 256 --accumulation 4
CUDA_VISIBLE_DEVICES=0 accelerate launch --config_file accelerate_local.yaml --use_deepspeed --deepspeed_config_file ds_checkpoint.json --num_processes 1 --num_machines 1 --mixed_precision bf16 train_memory.py --case checkpoint --micro-batch 1 --seq-len 256 --accumulation 4
CUDA_VISIBLE_DEVICES=0 accelerate launch --config_file accelerate_local.yaml --use_deepspeed --deepspeed_config_file ds_offload.json --num_processes 1 --num_machines 1 --mixed_precision bf16 train_memory.py --case offload --micro-batch 1 --seq-len 256 --accumulation 4
```

首次运行后记下输出的模型 commit revision，正式比较时为**三条命令都加上相同的 `--revision` 值**，并固定软件版本。每次完整执行包含 2 个预热更新、5 个测量更新；每个更新累积 4 个 micro-batch，所以单卡有效 batch 为 \(1\times4\times1=4\)。脚本会检查 DeepSpeed 真正生效的 batch 配置，而不只是相信文件中写对了。

若 `cpu_adam`/`fused_adam` 编译失败，先检查编译器、PyTorch/CUDA 与 DeepSpeed 的兼容性；这不是显存不足。若发生 OOM，记录失败阶段及原配置：可以统一缩短三组序列长度，或三组都换更小模型后重测；**不能把一组 OOM 改成一个假想显存数，也不承诺 8 GB 必然跑通**。单卡 ZeRO-2 的持久状态只有一片，C 组节省来自状态迁往 CPU，不是“一张卡实现了多卡切分”。

## 五、三种配置的显存对比总结

下面是**待运行记录表，不是参考性能数据**。用脚本三次输出的 `RESULT` 填写；每组独立重复至少三轮，报告中位数与波动，保留完整原始日志。

| 配置 | 稳态基线 GiB | 总峰值 / 增量峰值 GiB | 秒/完整更新 | CPU RSS 高水位 GiB |
|---|---|---|---|---|
| A：stage 0 | 待测 | 待测 | 待测 | 待测 |
| B：stage 0 + checkpoint | 待测 | 待测 | 待测 | 待测 |
| C：ZeRO-2 + checkpoint + CPU offload | 待测 | 待测 | 待测 | 待测 |

解释结果时依次问：

1. **B 相对 A**：激活重计算是否实际降低峰值？耗时增加多少？短序列或参数状态占主导时，峰值差异可能不大。
2. **C 相对 B**：GPU 状态是否减少、主机内存与更新耗时是否增加？这里只能归因于 offload 配置及引擎实现的综合差异，不能声称验证了多卡 ZeRO 的 \(1/N\) 收益。
3. **总峰值与增量峰值**：状态搬到 CPU 后，常驻基线下降也很重要，不能只比较“峰值减基线”；初始化/预热 OOM 同样意味着该配置在当前设备上不可用。
4. **公平性**：三组模型 revision、dtype、seq_len、micro-batch、累积步数、GPU 数与 CPU 线程是否一致？不一致时先补测，不直接比较。

### 可选：多卡核验分片，而不是把 offload 当分片

有两张或更多同类 GPU 时，可以另开一轮实验：固定 checkpointing、BF16/FP32 累积策略、输入形状和有效 batch；为 stage 0/1/2/3 分别提供**不含 offload**的 DeepSpeed JSON，并移除或相应扩展脚本中仅接受 A/B/C 的 stage 断言。每个配置仍独立启动。单机两卡可使用 `--num_processes 2`，同时将两卡设为可见；若要保持本节有效 batch=4，则把配置和脚本中的 accumulation 同步改为 2，即 \(1\times2\times2=4\)。

这项扩展尚未在本节运行；要记录每卡峰值、通信桶与参数聚合开销，并按真实梯度精度重算理论值，不能期待实测峰值严格等于第9章不含激活/缓冲的 \(16P/N\)。更改 ZeRO 阶段还会改变模型加载和 checkpoint 保存路径，应按对应版本文档完成验证后再扩大规模。

## 本节小结

本节提供了一个可分进程执行的三组测量方案：显式启用训练模式与重计算，统一输入和精度口径，核验有效 batch，并同时记录 GPU 峰值、主机内存与更新耗时。**配置代码经过静态核对，但本节没有附带实际 GPU 运行记录；不能把“提供了实验”写成“已经验证了收益”。** 单卡可观察重计算和 CPU offload，多卡才能观察跨卡分片与通信的权衡。
