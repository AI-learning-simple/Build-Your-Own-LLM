# 11.2 量化（Quantization）、键值缓存（KV Cache）与本地推理加速实战

> **本节定位**：本节只做实践。量化方案、误差来源、速度取舍与 KV Cache 原理见[第11章第六节](<./11.%20大模型推理机制（Inference%20Mechanisms）——KV%20Cache、批处理与量化.md>)，这里不重复讲解。

> **硬件要求**：路径 A 需 NVIDIA CUDA；路径 B 可使用 CPU、Apple Silicon/Metal 或兼容的图形处理器（GPU）。不同平台分别记录条件，不把跨平台耗时差异直接归因于量化。云 GPU 方案见前言 P0.3。
>
> **本节目标**：实验 11.1 关注的是"服务端如何同时服务很多用户"（vLLM + 连续批处理 Continuous Batching）。这一节换一个更贴近个人的场景：**一块 8 GB 显存的消费级显卡，能否运行一个 7B 模型？** 我们会以 7B 检查点（checkpoint）为例，分别介绍 **Hugging Face 生态**（transformers + bitsandbytes）与 **llama.cpp / Ollama**（GGUF 格式）两条量化推理路径；实际测量权重与运行时占用、键值缓存开关延迟，以及不同上下文长度的缓存张量大小。是否能在特定 8 GB 设备运行由平台、量化格式、上下文和运行时共同决定。
>
> **平台边界**：本节路径 A 的 `bitsandbytes` 4-bit 示例按 **NVIDIA CUDA** 环境编写，且需要兼容的驱动、PyTorch 与 bitsandbytes 版本；它不能原样用于 macOS 的 MPS。Apple Silicon 建议走路径 B 的 llama.cpp / Ollama（Metal），此时占用的是统一内存而不是独立“显存”。7B 4-bit 模型能否在 8 GB 设备运行还取决于量化格式、上下文长度、KV Cache、运行时缓冲区和是否发生 CPU 卸载（offload），不能只由权重大小保证。

7B 模型用 FP16 存权重约需 14 GB，尚未计入运行时开销；若要求全部权重常驻 8 GB 设备，需要量化或换更小模型，CPU 卸载则是另一种带传输代价的选择。下面分别走 Hugging Face 与 llama.cpp/Ollama 两条路径，实测权重、运行时占用和 KV Cache 开销。

**两条路径是二选一、顺序运行，不是在同一张 8 GB 卡上同时加载。** 路径 A 的第四、五节继续使用同一 Python 进程中的 HF 模型；路径 B 的 Ollama API 在独立进程调用，不加载 HF 模型。切换到 B 前先退出 A 的 Python 进程；切回 A 前对本例模型执行 `ollama stop qwen2.5:7b`，用 `ollama ps` 确认没有其他模型仍占卡。第六节的小模型质量对照也要在结束 7B 实验后的新进程中运行。

## 一、路径 A：Hugging Face 生态（bitsandbytes 4-bit 量化）

以下代码先显式检查 CUDA，避免在 CPU 或 macOS/MPS 上误运行：

```bash
pip install torch transformers accelerate bitsandbytes
```

```python
import torch
import time
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

if not torch.cuda.is_available():
    raise RuntimeError("此 bitsandbytes 示例需要 NVIDIA CUDA；macOS 请使用下文 Ollama/llama.cpp 路径。")

model_name = "Qwen/Qwen2.5-7B-Instruct"
quant_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, quantization_config=quant_config, device_map="auto")
model.eval()

print("设备映射:", model.hf_device_map)
print("显存占用 (GB):", torch.cuda.memory_allocated() / 1e9)
```

记录本机加载后的 `memory_allocated()`，再分别测试目标提示词（Prompt）长度与生成长度。该值受 transformers/bitsandbytes 版本、量化配置、设备映射和卸载影响，不能从“4-bit”推定固定占用或剩余空间。

## 二、路径 B：llama.cpp / Ollama（GGUF 量化）

`llama.cpp` 是面向本地推理的 C/C++ 引擎，支持 GGUF 量化、CPU/GPU 分层加载和多种硬件后端。它与 transformers 的速度和占用差异取决于量化格式、硬件、内核和卸载配置，必须在相同模型与输入条件下实测。较易上手的方式之一是 **Ollama**：

先按平台从 [Ollama 官方下载页](https://ollama.com/download) 安装：macOS 使用 macOS 应用安装包，Windows 使用 Windows 安装包；Linux 按官网的 Linux 安装说明操作。不要在 macOS 上使用 Linux 安装脚本。安装并启动服务后，在终端运行：

```bash
ollama run qwen2.5:7b
```

模型标签并不永久保证某一种 4-bit 格式，实验前应查看实际模型信息并记录量化类型与模型摘要。

也可以在**不加载 HF 模型的独立进程**中调用 Python API。先固定生成选项，再把首次调用与预热后的测量分开：

```bash
pip install ollama
```

```python
import json
import time
import ollama

MODEL = "qwen2.5:7b"
PROMPT = "用一句话介绍 Transformer。"
OPTIONS = {
    "temperature": 0.0, "seed": 42, "top_p": 1.0, "top_k": 0,
    "repeat_penalty": 1.0, "num_predict": 100, "num_ctx": 2048,
}

print("模型信息:", ollama.show(MODEL))  # 同时用 ollama list 记录模型摘要
print("固定 options:", OPTIONS)

def run_once(label):
    start = time.perf_counter()
    response = ollama.generate(
        model=MODEL, prompt=PROMPT, stream=False,
        options=OPTIONS, keep_alive="5m",
    )
    elapsed = time.perf_counter() - start
    if not response["done"]:
        raise RuntimeError("未完整返回，不能作为成功测速样本")
    tokens = response["eval_count"]
    eval_s = response["eval_duration"] / 1e9
    row = {
        "run": label, "wall_s": elapsed,
        "load_s": response["load_duration"] / 1e9,
        "prompt_eval_count": response["prompt_eval_count"],
        "prompt_eval_s": response["prompt_eval_duration"] / 1e9,
        "eval_count": tokens, "eval_s": eval_s,
        "wall_output_tokens_per_s": tokens / elapsed,
        "eval_tokens_per_s": tokens / eval_s if eval_s > 0 else None,
        "done_reason": response["done_reason"],
        "answer": response["response"],
    }
    print(json.dumps(row, ensure_ascii=False))
    return row

run_once("first_call_warmup")  # 可能已驻留；是否冷启动要看 load_s 和此前状态
rows = [run_once(f"warm_{i}") for i in range(1, 4)]
print("预热后输出一致:", len({row["answer"] for row in rows}) == 1)
```

[Ollama 响应中的时长](https://docs.ollama.com/api/generate)以纳秒计，上例转成秒，分别报告加载、提示求值与生成阶段。`eval_count / eval_duration` 是服务端生成阶段速率，`eval_count / wall_s` 是客户端整段响应口径，两者不能混用；非流式响应没有直接测量 TTFT/ITL。相同提示可能命中缓存，需记录服务版本与缓存条件（版本提供时也保留 `prompt_eval_cached_count`），不能将热提示的 `prompt_eval_duration` 当作全量冷 prefill 成本。改变选项做多配置比较时，分别预热并轮换运行顺序。

Ollama 模型标签对应的具体 GGUF 量化与文件大小可能随发布版本变化。运行时还要分配 KV Cache、计算缓冲区等，并可能在 CPU、Metal 或 CUDA 间分配；请用本机工具记录实际内存/统一内存/显存，而不要由模型文件大小推断能否稳定运行。

## 四、验证键值缓存（KV Cache）的效果

回顾本部分第 11 章：KV Cache 保存历史词元（Token）的键/值（Key/Value），避免每生成一个新词元都重新计算全部历史。以下继续使用路径 A 已加载的 `model`、`tokenizer` 与 CUDA 环境，对比开启和关闭 KV Cache 的生成速度；它不是可直接套到 Ollama 对象上的代码。

```python
import json
import statistics
import time

prompt = "请详细介绍一下深度学习的发展历史。"
text = tokenizer.apply_chat_template(
    [{"role": "user", "content": prompt}],
    tokenize=False, add_generation_prompt=True,
)
input_device = model.get_input_embeddings().weight.device
inputs = tokenizer(text, add_special_tokens=False, return_tensors="pt").to(input_device)
MAX_NEW_TOKENS = 100
raw_eos = model.generation_config.eos_token_id
eos_ids = set(raw_eos if isinstance(raw_eos, (list, tuple)) else [raw_eos])

def timed_generate(use_cache):
    # CUDA 异步执行；本例单卡，在计时边界同步。
    torch.cuda.synchronize()
    start = time.perf_counter()
    with torch.inference_mode():
        output = model.generate(
            **inputs, max_new_tokens=MAX_NEW_TOKENS,
            use_cache=use_cache, do_sample=False, num_beams=1,
        )
    torch.cuda.synchronize()
    elapsed = time.perf_counter() - start
    # 单条无 padding 的结果，计入生成的 EOS，不把上限当实际长度。
    ids = output[0, inputs["input_ids"].shape[1]:].tolist()
    reason = (
        "eos" if ids and ids[-1] in eos_ids
        else "length" if len(ids) == MAX_NEW_TOKENS else "other"
    )
    return {
        "use_cache": use_cache, "elapsed_s": elapsed,
        "output_tokens": len(ids), "finish_reason": reason,
        "output_tokens_per_s": len(ids) / elapsed,
        "token_ids": ids,
        "answer": tokenizer.decode(ids, skip_special_tokens=True),
    }

# 两种模式各完整预热一次，结果不参与计时汇总。
for cache_mode in (True, False):
    timed_generate(cache_mode)

rows = []
for repeat, order in enumerate([(True, False), (False, True)] * 2, start=1):
    for mode in order:
        row = {"repeat": repeat, **timed_generate(mode)}
        rows.append(row)
        print(json.dumps(row, ensure_ascii=False))

same_output = all(row["token_ids"] == rows[0]["token_ids"] for row in rows)
print("所有轮次实际输出 token 一致:", same_output)
for mode in (True, False):
    elapsed = [r["elapsed_s"] for r in rows if r["use_cache"] == mode]
    print("use_cache", mode, "耗时中位数/最小/最大:",
          statistics.median(elapsed), min(elapsed), max(elapsed))
if same_output:
    med = {
        mode: statistics.median(r["elapsed_s"] for r in rows if r["use_cache"] == mode)
        for mode in (True, False)
    }
    print("同输出的耗时中位数比（关闭/开启）:", med[False] / med[True])
else:
    print("输出不同：先检查词元数、停止原因与内容，不把耗时比解释为等工作量加速。")
```

关闭 KV Cache 后，每一步都会重新计算历史词元的 K/V；开启后则复用缓存。上例比较实际 token 序列、停止原因并轮换测量顺序；输出速率包含本次 prefill 与生成循环，**不是纯解码 TPOT**。即使两边都是贪心，也可能因数值误差产生不同输出，不能把提前 EOS 导致的短回答当作缓存加速。加速比受提示/实际输出长度、模型、注意力实现、设备映射和硬件影响，应报告本机实测值与波动，不能预设为“数倍”。

## 五、长上下文（Long Context）的显存代价

KV Cache 不是免费的：上下文越长，缓存占用的显存越多。测试不同长度的提示词，观察显存变化：

```python
def tensor_bytes(obj):
    if torch.is_tensor(obj):
        return obj.numel() * obj.element_size()
    if isinstance(obj, (tuple, list)):
        return sum(tensor_bytes(item) for item in obj)
    if isinstance(obj, dict):
        return sum(tensor_bytes(item) for item in obj.values())
    if hasattr(obj, "layers"):
        return sum(
            tensor_bytes(layer.keys) + tensor_bytes(layer.values)
            for layer in obj.layers
        )
    if hasattr(obj, "key_cache") and hasattr(obj, "value_cache"):
        return tensor_bytes(obj.key_cache) + tensor_bytes(obj.value_cache)
    raise TypeError(f"不支持的缓存类型 {type(obj).__name__}；请检查当前版本的 Cache 接口。")

def measure_kv_cache(token_length):
    vocab_size = model.get_input_embeddings().num_embeddings
    dummy_input = torch.randint(
        0, vocab_size, (1, token_length), device=input_device
    )
    with torch.inference_mode():
        outputs = model(dummy_input, use_cache=True)
    cache = outputs.past_key_values
    # 新版 transformers 可能返回 DynamicCache；转成逐层 (K, V) 元组后统计。
    if hasattr(cache, "to_legacy_cache"):
        cache = cache.to_legacy_cache()
    gib = tensor_bytes(cache) / (1024 ** 3)
    del outputs, cache, dummy_input
    return gib

for length in [128, 512, 2048]:
    kv_gib = measure_kv_cache(length)
    print(f"上下文长度 {length}: KV Cache 张量 {kv_gib:.3f} GiB")
# 确认设备余量后再测试更长序列，避免直接 OOM。
```

这里统计的是普通稠密 K/V 张量的**逻辑字节数**（`numel × element_size`），跨设备时会一起求和，并不等于单张 GPU 的物理分配量。示例覆盖常见的逐层 `(K, V)`、`key_cache/value_cache` 或 `layers[].keys/values` 接口；未知类型必须报错，不能把“不认识缓存格式”写成“缓存占用为 0”。量化/滑窗/静态缓存、共享 storage 与额外 scale 等需要专门的计量方法。

还要区分三种显存口径：

- `memory_allocated()` / `max_memory_allocated()`：当前/重置以来峰值的 PyTorch 活跃张量分配，包括权重、KV 与临时张量，**不包括 allocator 仅保留但未使用的空闲块**；
- `memory_reserved()` / `max_memory_reserved()`：PyTorch caching allocator 当前/峰值保留量，包括活跃分配及池内空闲块；
- 设备工具报告的进程占用：还可能包含 CUDA context、非 PyTorch 库等开销，不应与前两者混用。

测单轮峰值需先同步、调用 `torch.cuda.reset_peak_memory_stats()`，运行目标操作后再次同步再读峰值；多卡需逐卡记录。不能把总峰值直接当作 KV 大小。固定层数、KV 头数、头维度（head dimension）、数据类型（dtype）和批次大小（batch size）时，普通完整上下文缓存才随序列长度近似线性增长。

## 六、低门槛质量对照：同一个小检查点的 FP16 与 4-bit

7B FP16 放不进 8 GB，并不意味着只能测“能否加载”。改用 **Qwen2.5-0.5B-Instruct**，在同一张 CUDA 卡上**顺序加载同一 revision 的 FP16 与 NF4**，即可检查量化前后的逐题退化。该小模型结果不能外推到 7B；这里只建立质量对照闭环，不预设 4-bit 一定变差或不变。

先退出上面的 7B Python 进程，并停止 Ollama 的驻留模型。以下代码在新进程中独立运行，沿用第一节安装的 `torch transformers accelerate bitsandbytes`；不需要评审模型、额外数据集或训练。检查点仍需预先下载/可访问。固定 6 个不参与本次调参/校准的玩具留出例，事先规定“去除首尾空白后精确匹配”；它们不是经过污染排查的正式测试集。

```python
import gc
import json
from importlib.metadata import version

import torch
from transformers import AutoConfig, AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

if not torch.cuda.is_available():
    raise RuntimeError("此 FP16/NF4 对照需要 NVIDIA CUDA 与兼容的 bitsandbytes。")

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"
# 只解析一次 main，然后两种加载都锁到同一提交，避免版本漂移。
REVISION = AutoConfig.from_pretrained(MODEL_ID)._commit_hash
if not REVISION:
    raise RuntimeError("未取得模型提交号，请显式指定同一个已核验 revision。")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID, revision=REVISION)
HELD_OUT = [
    ("只写数值：17 加 25 等于多少？", "42"),
    ("只写数值：9 乘 7 等于多少？", "63"),
    ("只写数值：81 除以 9 等于多少？", "9"),
    ("只写数值：三角形有几条边？", "3"),
    ("只输出英文单词的全大写形式：cat", "CAT"),
    ("从文本中提取颜色，只输出颜色词：盒子是蓝色的。", "蓝色"),
]
print(json.dumps({
    "checkpoint": MODEL_ID, "revision": REVISION,
    "gpu": torch.cuda.get_device_name(0),
    "versions": {p: version(p) for p in ("torch", "transformers", "accelerate", "bitsandbytes")},
    "scoring": "strip 后精确匹配；截断与其他停止不计正确",
    "generation": {"do_sample": False, "num_beams": 1, "max_new_tokens": 32, "use_cache": True},
}, ensure_ascii=False))

def evaluate_precision(mode):
    torch.manual_seed(42)
    kwargs = {"revision": REVISION, "torch_dtype": torch.float16, "device_map": {"": 0}}
    if mode == "nf4":
        kwargs["quantization_config"] = BitsAndBytesConfig(
            load_in_4bit=True, bnb_4bit_quant_type="nf4",
            bnb_4bit_use_double_quant=False, bnb_4bit_compute_dtype=torch.float16,
        )
    model = AutoModelForCausalLM.from_pretrained(MODEL_ID, **kwargs)
    model.eval()
    raw_eos = model.generation_config.eos_token_id
    eos_ids = set(raw_eos if isinstance(raw_eos, (list, tuple)) else [raw_eos])
    rows = []
    try:
        for sample_id, (question, expected) in enumerate(HELD_OUT):
            text = tokenizer.apply_chat_template(
                [{"role": "user", "content": question}],
                tokenize=False, add_generation_prompt=True,
            )
            inputs = tokenizer(text, add_special_tokens=False, return_tensors="pt").to("cuda:0")
            with torch.inference_mode():
                output = model.generate(
                    **inputs, max_new_tokens=32, do_sample=False,
                    num_beams=1, use_cache=True,
                )
            ids = output[0, inputs["input_ids"].shape[1]:].tolist()
            answer = tokenizer.decode(ids, skip_special_tokens=True).strip()
            reason = "eos" if ids and ids[-1] in eos_ids else "length" if len(ids) == 32 else "other"
            row = {
                "id": sample_id, "mode": mode, "question": question,
                "expected": expected, "answer": answer, "token_ids": ids,
                "output_tokens": len(ids), "finish_reason": reason,
                "correct": reason == "eos" and answer == expected,
            }
            rows.append(row)
            print(json.dumps(row, ensure_ascii=False))
            del inputs, output
        return rows
    finally:
        del model
        gc.collect()
        torch.cuda.empty_cache()

fp16_rows = evaluate_precision("fp16")
nf4_rows = evaluate_precision("nf4")  # 上一个调用返回时已释放 FP16 模型
print({
    "n": len(HELD_OUT),
    "fp16_exact_match": sum(r["correct"] for r in fp16_rows) / len(HELD_OUT),
    "nf4_exact_match": sum(r["correct"] for r in nf4_rows) / len(HELD_OUT),
    "fp16_correct_nf4_wrong": sum(a["correct"] and not b["correct"] for a, b in zip(fp16_rows, nf4_rows)),
    "fp16_wrong_nf4_correct": sum(not a["correct"] and b["correct"] for a, b in zip(fp16_rows, nf4_rows)),
})
```

**待测记录，不填写虚构分数**：保留配置、两种精度的逐题原文、token 数、停止原因、精确匹配率与两个方向的变化题数。出现 FP16 对而 NF4 错的题时，先看是事实/计算错误、格式不符还是截断；两边都错也必须进入分母。6 题中一题就改变约 16.7 个百分点，相同分数不证明等价；这里的严格格式任务也不能代表开放回答质量。不要据此反复调量化参数；需要调参时另用开发集，最后换足够规模、领域匹配的独立留出集做配对评测（第 13 章）。

本节不附 GPU 实测结果；运行成功只说明已得到本机记录，是否有质量退化由实际输出决定。路径 B 的读者可在相同源检查点导出的 FP16/GGUF 量化版本上沿用这些固定例和评分规则，但必须记录转换版本与源 revision，不能把两个不明来源的 Ollama 标签当作同模型量化对照。

## 七、（选读）MoE 在小显存单卡上的部署难点

第一部分第 13 章介绍过 MoE 的核心思想：“总参数多、每个词元只激活少数专家”。在**所有权重常驻单卡** 的常见低延迟部署中，显存主要受总参数量约束，而每个词元的计算量更接近激活参数量；top-k 路由（routing）不会自动减少常驻权重。CPU/NVMe 卸载、专家并行或按需换入可以降低单卡常驻量，但会引入通信或传输开销。因此，MoE 通常比同等激活参数量的稠密（Dense）模型更难在 8 GB 单卡低延迟部署，具体占用仍取决于检查点、量化格式和运行时。

如果只是想体会 Router 机制本身（而不需要真的跑一个大模型），可以用几行代码写一个最简化的 MoE 层，在 CPU 上就能运行：

```python
import torch
import torch.nn as nn

class ToyMoE(nn.Module):
    def __init__(self, d_model=8, num_experts=4, top_k=2):
        super().__init__()
        self.experts = nn.ModuleList(
            [nn.Linear(d_model, d_model) for _ in range(num_experts)]
        )
        self.router = nn.Linear(d_model, num_experts)
        self.top_k = top_k

    def forward(self, x):
        router_logits = self.router(x)                         # [batch, experts]
        topk_logits, topk_indices = torch.topk(
            router_logits, self.top_k, dim=-1
        )
        topk_weights = torch.softmax(topk_logits, dim=-1)     # top-k 内重新归一化

        all_outputs = torch.stack(
            [expert(x) for expert in self.experts], dim=1
        )                                                     # [batch, experts, d_model]
        gather_index = topk_indices.unsqueeze(-1).expand(-1, -1, x.shape[-1])
        chosen_outputs = torch.gather(all_outputs, 1, gather_index)
        mixed = (chosen_outputs * topk_weights.unsqueeze(-1)).sum(dim=1)
        return mixed, topk_indices, topk_weights

moe = ToyMoE(top_k=2)
x = torch.randn(1, 8)
output, expert_ids, router_weights = moe(x)
print("选中的专家:", expert_ids.tolist())
print("对应权重:", router_weights.tolist())
```

改变输入 `x`，可以观察 top-k 专家编号与归一化权重如何变化。为让代码短小，上例先计算全部专家再 `gather`；真实稀疏 MoE 内核只调度选中的专家，否则不会获得稀疏计算收益。
