## 一、训练看吞吐，推理看延迟

第 10 章的训练系统追求"用最短时间训练完一个模型"。推理系统面对的是另一幅画面：**成千上万个用户同时发来长度不同的请求，系统要在可接受的延迟下服务尽可能多的人**。

两者的目标几乎相反：

| | 训练系统 | 推理系统 |
|---|---|---|
| 优化目标 | 吞吐量（每小时处理多少词元） | 延迟（每个请求多快返回）+ 吞吐量 |
| 数据 | 固定大批次，形状整齐 | 请求长度参差、动态到达 |
| 显存压力 | 参数 + 梯度 + 优化器 + 激活 | 参数 + KV Cache（随并发和上下文增长） |
| 精度 | BF16/FP32，训练稳定优先 | 可以 INT8/INT4 量化，质量可接受即可 |

**显存容量是推理的硬约束，但不是唯一瓶颈。** 模型参数基本固定，每个并发请求却会占用随上下文增长的 KV Cache；系统还受算力、带宽、卡间通信和请求排队影响。

本章围绕一个问题：**如何在有限资源和延迟目标下，提高可持续服务的吞吐量？**

---

## 二、生成的两个阶段与三个延迟指标

大模型生成回答分两个阶段：

1. **预填充（Prefill）**：把用户输入的整段提示一次性喂给模型，并行算出所有位置的 KV Cache。计算量大，但只做一次；
2. **解码（Decode）**：逐个生成新词元，每步只算最后一个位置，借助 KV Cache 避免重算历史。

两个阶段行为不同，所以用三个指标分开衡量：

| 指标 | 全称 | 含义 | 受什么影响 |
|---|---|---|---|
| **TTFT** | Time To First Token | 从发出请求到收到第一个词元 | 预填充速度 + 排队 + 网络 |
| **TPOT** | Time Per Output Token | 首个词元之后，每个输出词元的平均耗时 | 解码、调度、传输 |
| **ITL** | Inter-Token Latency | 相邻输出词元到达的间隔及分布 | 调度、内核、流式传输 |

一个直观例子：用户问"介绍一下 Transformer"，等待 0.3 秒看到第一个字（TTFT = 0.3 s），之后每秒出 20 个字（TPOT = 0.05 s），总生成 200 个字，总耗时约 `0.3 + 200 × 0.05 = 10.3 s`。

用户对"第一个字什么时候出现"最敏感，所以流式输出很重要；但 TTFT 小不代表总耗时短，两个指标要一起看。

**为什么小批次解码常受显存带宽限制？** 每个请求每步只生成一个词元，权重复用有限。假设 7B 模型的 14 GB 权重每步都从 HBM 读一遍，带宽 1 TB/s，仅权重读取就要约 14 ms。批次增大后，一次权重读取可以服务更多词元；长上下文又会增加 KV 读取量，瓶颈可能转移。

## 三、KV Cache：每个词元保存了什么

KV Cache 避免重复计算历史词元的键（Key）和值（Value），代价是：**每一层、每个已处理词元都要保存一份 K 和一份 V。**

单个请求的理论主体占用：

$$
\text{KV Bytes}
=
2\times L\times T\times H_{kv}\times d_{head}\times b
$$

- `2`：K 和 V 两组；
- `L`：Transformer 层数；
- `T`：当前缓存的词元数；
- `H_kv`：KV 头数（标准多头注意力 Multi-Head Attention, MHA 中等于 Query 头数；分组查询注意力 Grouped-Query Attention, GQA 和多查询注意力 Multi-Query Attention, MQA 中更少）；
- `d_head`：每个头的维度；
- `b`：每个元素的字节数（FP16/BF16 通常为 2）。

以一个简化的 7B 配置为例：`L=32`、标准多头注意力、`H_kv × d_head = d_model = 4096`、FP16。每个词元的缓存是：

```text
2 × 32 × 4096 × 2 Byte = 524,288 Byte ≈ 0.5 MiB
```

| 场景 | 计算 | 理论 KV Cache |
|---|---:|---:|
| 单请求，4K 词元 | `0.5 MiB × 4096` | 约 2 GiB |
| 单请求，128K 词元 | `0.5 MiB × 131072` | 约 64 GiB |
| 100 请求，各 4K 词元 | `100 × 2 GiB` | 约 200 GiB |
| 100 请求，各 32K 词元 | `100 × 16 GiB` | 约 1.56 TiB |

这些数字以本例的层数、标准 MHA 和 FP16 为前提。换模型、换 GQA、换量化，数字都会变。

**减少 KV Cache 的两类思路**：

- **结构层面**：GQA/MQA 让多个 Query Head 共享 KV，多头潜在注意力（Multi-Head Latent Attention, MLA）用压缩的潜在缓存；这些通常需要在模型训练时就支持，不能事后改；
- **存储层面**：KV 量化降低每个元素的字节数；分页管理减少预留和碎片浪费。

## 四、连续批处理：让新请求插进空位

先区分三种方式：

- **逐个排队**：一次只处理一个请求，跨请求无法复用权重；
- **静态批处理（Static Batching）**：一批一起开始，整批结束才接下一批；短请求释放的槽位不能马上接新请求；
- **连续批处理（Continuous Batching）**：在两次迭代之间重新组批，移除已完成请求，接纳等待请求。

用一个简化时间表看差别。最多同时处理 2 个请求，A/B 在第 1 步到达，分别需要 1/4 步；C/D 在第 2 步开始前到达，各需要 1 步。`B2` 表示 B 的第 2 个输出词元。

| 时间步 | 静态批处理：槽 1 / 槽 2 | 连续批处理：槽 1 / 槽 2 |
|---|---|---|
| 1 | A1 / B1 | A1 / B1 |
| 2 | — / B2（C、D 等待） | C1 / B2 |
| 3 | — / B3（C、D 等待） | D1 / B3 |
| 4 | — / B4（C、D 等待） | — / B4 |
| 5 | C1 / D1 | 全部完成 |

先解释静态批处理里那些空槽：第 2 步 A 已经完成，但它释放的槽 1 不能接新请求，因为整批还没结束，只能空着等 B 跑完；C/D 要一直等到第 5 步。

关键动作是：**B 还没结束，C/D 就利用 A 释放的槽位开始推进。**

这个表假设每步等长，省略了预填充、内核启动和调度开销。真实加速比要测量。收益取决于到达模式、长度分布、批次上限、模型和硬件；如果队列里没有等待请求，或显存/算力已经饱和，提升会变小。

## 五、分页注意力：像操作系统管理内存一样管理 KV Cache

连续批处理带来一个新问题：**不同请求的 KV Cache 长度实时变化，怎么高效管理这些大小不一的显存块？**

朴素做法是"按最大可能长度给每个请求预分配一整块连续显存"。但请求实际可能只用 10%，造成巨大浪费；而且请求完成前，这块显存不能被别人用。

vLLM 提出的**分页注意力（PagedAttention）**借鉴操作系统的分页内存管理：

- 把 KV Cache 切成固定大小的**页（Page）**，例如每页 16 个词元；
- 每个请求按需**按页分配**，用一张**页表**记录"逻辑页 → 物理页"；
- 请求增长时分配新页，完成时释放旧页；
- 不同请求可以共享相同的页（Prefix Caching 的基础）。

可以想成：图书馆把书架分成固定大小的格子，读者按格借、读完就还；格子的物理位置不必连续，只要目录能查到就行。

用每块 4 个词元的玩具例子：

| 请求 | 逻辑块 | 物理块 | 已存词元位置 | 块内空位 |
|---|---:|---:|---|---:|
| X | 0 | 7 | X 的 0–3 | 0 |
| X | 1 | 2 | X 的 4–5 | 2 |
| Y | 0 | 5 | Y 的 0–2 | 1 |

X 新增位置 6 时，只填物理块 2 的空位；增长到位置 8 时才申请新块，并把"逻辑块 2 → 新物理块"写进页表。X 完成后，未被共享引用的块可以回收。

**分页不压缩每个词元的 K/V。** 它减少的是"按最大长度预留"和"外部碎片"造成的浪费。相同前缀可以共享物理块，但需要一致性校验、引用计数，修改共享块时还要写时复制。

## 六、量化：把权重、激活和 KV 压到更低精度

> 这一节补原理，11.2 做实践。量化不是“把文件压小”，而是用低比特整数或浮点表示张量，并在计算时反量化或调用低精度内核。

### 基本式：scale、zero-point 与反量化

最常用的仿射量化（affine quantization）是：

$$
q=\mathrm{clip}\left(\mathrm{round}\left(\frac{x}{s}\right)+z,\ q_{\min},q_{\max}\right),
\qquad
\hat{x}=s(q-z)
$$

- $x$：原始浮点值；
- $q$：存下来的低比特整数；
- $s$：缩放因子（scale）；
- $z$：零点（zero-point），把浮点 0 映射到某个整数；
- $q_{\min},q_{\max}$：整数范围，例如 INT8 是 $[-128,127]$，INT4 是 $[-8,7]$；
- $\hat{x}$：反量化后的近似值。

**对称量化**取 $z=0$，只存 scale：

$$
s=\frac{\max |x|}{q_{\max}},\qquad q=\mathrm{round}\left(\frac{x}{s}\right)
$$

它实现简单，适合权重这种近似零均值、对称分布的张量；但如果数据整体偏移，会浪费一部分整数范围。

**非对称量化**同时存 $s$ 和 $z$：

$$
s=\frac{x_{\max}-x_{\min}}{q_{\max}-q_{\min}},
\qquad
z=q_{\min}-\mathrm{round}\left(\frac{x_{\min}}{s}\right)
$$

它能更好地覆盖偏移分布，代价是多存一个 zero-point，反量化也多一次减法。

无论哪种，量化误差都来自两件事：**舍入**和**截断**。`clip` 会保护范围，但超出范围的离群值会被截掉；scale 越大，舍入误差越大。

### 粒度：per-tensor、per-channel 与 per-group

同一个 scale 管多少个数，直接决定误差。

假设一组 INT4 权重：

```text
x = [0.1, 0.2, 0.3, 2.1]
```

**per-tensor**：整组共用一个 scale。$\max|x|=2.1$，$s=2.1/7=0.3$：

```text
q       = [0, 1, 1, 7]
dequant = [0, 0.3, 0.3, 2.1]
误差    = [0.1, 0.1, 0, 0]
```

前两个小权重被大权重“挤”得几乎只剩 0 和 1 两个档位。

**per-group（每组 2 个）**：每组用自己的 scale：

```text
组 1：x=[0.1,0.2]，s=0.2/7≈0.0286，q=[4,7]，dequant=[0.114,0.2]
组 2：x=[0.3,2.1]，s=2.1/7=0.3，  q=[1,7]，dequant=[0.3,2.1]
最大误差从 0.1 降到约 0.014
```

| 方案 | scale 数量 | 最大误差 | 额外开销 |
|---|---|---|---|
| per-tensor | 1 | 0.100 | 最小 |
| per-group（2 个一组） | 2 | 0.014 | 每组一个 scale |
| per-channel | 每个通道一个 | 通常更小 | 元数据更多 |

粒度越细，越能隔离离群通道，但 scale/zero-point 的存储和反量化开销也越大。实际常用 group size 32、64、128；不是越小越好，要看内核支持和元数据成本。

### 量化什么：权重、激活、KV Cache

| 对象 | 特点 | 主要难点 | 常见方法 |
|---|---|---|---|
| 权重 | 静态，训练后固定 | 离群通道、不同层敏感度不同 | GPTQ、AWQ、NF4、GGUF k-quants |
| 激活 | 随输入动态变化 | 激活离群值（outlier）更严重 | SmoothQuant、FP8、W8A8 |
| KV Cache | 随上下文增长 | K/V 分布不同，长上下文误差累积 | INT8/FP8 KV 量化、per-channel/per-token |

**权重-only 量化**最容易：权重不动，量化后存低比特，计算时反量化到 BF16/FP16 再乘。它主要省显存和带宽，不一定省算力。

**激活量化**更难：不同输入、不同 token 的激活范围变化很大，几个离群通道可能把 scale 拉得很大，导致其他通道误差上升。SmoothQuant 的思路是把激活的离群程度通过 per-channel scale 迁移一部分到权重上，让两边都好量化。

**KV Cache 量化**针对长上下文：K 和 V 的分布不同，逐 token、逐通道的 scale 更合适；量化误差会随层数和上下文累积，需要单独评估长上下文任务。

### PTQ 与 QAT

- **训练后量化（Post-Training Quantization, PTQ）**：拿训练好的模型，用校准数据估计 scale/zero-point，或做逐层误差补偿。GPTQ、AWQ、NF4、GGUF 都属于这一类。
- **量化感知训练（Quantization-Aware Training, QAT）**：训练时插入 fake quant，让模型适应舍入；常用 straight-through estimator 回传梯度。效果可能更好，但成本高。

QLoRA 容易被误解为“4-bit 训练”：它把**冻结的基座权重**用 NF4 存储，LoRA 适配器仍用 BF16 训练，激活和优化器状态也没有全部降到 4-bit。它是“量化基座 + 低比特存储 + 适配器训练”，不是所有张量都用 4-bit 计算。

### 常见格式与算法

| 名称 | 形式 | 核心思想 | 典型场景 |
|---|---|---|---|
| INT8 / INT4 | 均匀整数 | scale + zero-point | 通用权重/激活 |
| FP8 E4M3 / E5M2 | 8-bit 浮点 | 指数位换范围，尾数位换精度 | 支持 FP8 的新 GPU |
| NF4 | 4-bit 正态分位 | 按正态分布分位点取 levels，块内 scale | QLoRA |
| GPTQ | 4/8-bit 权重 | 逐层、逐列量化，用 Hessian 近似补偿误差 | GPU 权重-only |
| AWQ | 4-bit 权重 | 用激活统计保护重要通道，再做 per-channel 缩放 | GPU 权重-only |
| SmoothQuant | W8A8 | 把激活 outlier 迁移到权重 | 激活量化 |
| GGUF k-quants | 混合块量化 | 块级 scale、不同块用不同精度 | llama.cpp / 本地 CPU、Metal |

NF4 的关键不是“均匀切 16 档”，而是让 16 个 levels 更密集地覆盖正态分布的高概率区域；再叠加 block-wise scale 和双重量化（对 scale 再量化），进一步降低元数据开销。

GPTQ 和 AWQ 都需要校准数据，也都主要针对权重。它们不是“无损压缩”：4-bit 模型在难题、长上下文、代码和数学上可能明显退化，必须按任务评估。

### 为什么量化不一定加速

量化降低的是**表示位数**，不是自动降低所有计算成本：

- 权重-only 量化常常只省显存/带宽；如果内核仍要反量化到 BF16 再算，延迟可能不变甚至变慢；
- 低比特矩阵乘需要硬件和内核支持；不支持时，反量化开销会吃掉收益；
- batch 很小时可能 memory-bound，量化有帮助；batch 大、算力饱和时，收益可能转向算力瓶颈；
- KV 量化省显存，但 attention 内核可能引入额外反量化/缩放；
- 量化误差可能让模型输出变短、变保守或更容易出错，质量下降会抵消吞吐收益。

所以“4-bit 比 FP16 快 4 倍”不是通用结论。必须固定模型、输入、batch、上下文、内核和硬件，分别测质量、显存、TTFT、TPOT 和吞吐。

### 怎么评估量化

至少分三层：

1. **数值层**：权重/激活的 MSE、余弦相似度、最大误差；看离群通道是否被截断。
2. **模型层**：困惑度、任务准确率、长上下文、代码/数学、拒答与安全行为；不要只看通用 benchmark。
3. **系统层**：显存峰值、TTFT、TPOT、吞吐、批大小上限；同硬件、同内核、同输入比较。

一个实用的判断顺序是：先确认显存是否真的成为瓶颈，再选量化对象（权重/激活/KV），最后用目标任务的未见样本验证质量。量化是“用质量预算换资源”，不是免费加速。

> **一句话记住量化**：低比特表示 + scale/zero-point + 反量化；粒度决定误差，内核决定速度，任务评测决定能不能上线。

## 七、现代推理服务的扩展机制

连续批处理和分页注意力解决“请求怎么排队、KV 放哪里”。生产系统还会再加四层机制，分别处理长提示、阶段隔离、缓存层级和多租户适配。

### chunked prefill：把长提示拆开算

预填充（Prefill）一次处理整个提示，长提示会长时间占用算力，让同一批里的解码请求等待。**chunked prefill** 把提示切成若干块，分多个迭代完成；调度器可以把 decode 请求和新到的 prefill 块混在同一批里。

- 收益：降低 decode 请求被长 prefill 阻塞的尾延迟，提升混合负载下的平滑度；
- 代价：长提示自己的首词元时延（TTFT）可能变长，调度和 KV 管理更复杂；
- 不是“所有请求都快”：如果负载全是长提示、没有 decode 请求可混，收益有限。

### Prefill / Decode 分离：把两个阶段放到不同资源池

Prefill 是计算密集，Decode 是访存密集，二者对 GPU、batch 和并行策略的要求不同。**分离式部署（disaggregated prefill/decode）** 用两组 worker：

1. Prefill worker 算完提示的 KV Cache；
2. 把 KV 传给 Decode worker；
3. Decode worker 持续自回归生成。

好处是各自按瓶颈扩缩容，避免长提示拖慢 decode；代价是要传 KV（带宽、延迟、序列化），还要处理故障和调度。提示短、并发低时，分离的通信开销可能不值得。

### KV Cache 分层：GPU → CPU → SSD

KV Cache 不必全部常驻显存。分层缓存把不活跃请求的 KV 换出到 CPU DRAM 或 SSD，需要时再换回：

- 前缀缓存（Prefix Caching）复用完全匹配的前缀 KV，命中时省掉重算；
- 分层卸载（Offload/Tiering）按访问频率和剩余预算决定哪些块留在 GPU；
- 换入换出受 PCIe/NVLink 带宽限制，长上下文和低延迟场景要谨慎。

它减少的是“常驻显存压力”，不是免费扩容；换出后的首次访问会变慢。

还要区分 offload 与量化：offload 不改变每个 KV 元素的字节数，只改变存放位置；量化降低每个元素的字节数。两者可以组合，但都受带宽和内核限制。如果请求很快会再次访问，换入可能比重新计算前缀更贵；是否值得要看命中率、上下文长度和尾延迟，而不是只看“显存占用下降”。

### 多 LoRA 与约束解码

**多 LoRA 服务**让一个基座模型同时服务多个适配器：请求带上 adapter id，调度器按 adapter 组批，内核在共享基座上切换增量权重。它省的是“每个任务复制一份完整模型”的显存，代价是 adapter 管理、批内切换和内核支持。

**约束解码 / 结构化输出**（guided decoding）在每一步用语法、JSON Schema 或正则限制候选词元，保证输出可解析。它降低格式失败率，但不保证内容正确；约束太强也可能让模型输出变得生硬或漏掉信息。

### 投机解码的收益条件

投机解码用一个小草稿模型先猜几个词元，再由目标模型并行验证：

- 接受率高时，一次目标模型前向能确认多个词元，减少串行步数；
- 接受率低时，草稿和验证都是额外开销，可能更慢；
- 收益取决于草稿模型质量、任务分布、batch 大小和内核实现，不存在固定加速倍数。

> **一句话**：这些机制都在用“更多通信、更多调度或更多约束”换延迟、吞吐或显存；先测瓶颈，再决定加哪一层。

## 八、其它推理加速手段

量化已在第六节展开；下表只列其余手段。

| 技术 | 核心思想 | 收益 | 代价 |
|---|---|---|---|
| 投机解码（Speculative Decoding） | 草稿模型先提几个词元，目标模型验证 | 接受率高时减少串行步数 | 草稿和验证有额外开销 |
| 前缀缓存（Prefix Caching） | 复用完全匹配的前缀 KV | 命中时减少预填充重算 | 依赖命中率和缓存预算 |
| 张量并行推理 | 把权重分片到多卡 | 扩大可容纳的模型或请求规模 | 卡间通信可能抵消收益 |
| GQA / MLA | 多个 Query Head 共享 KV，或压缩缓存 | 减少每词元缓存 | 通常需要模型训练时支持 |

**分层看这些优化**：GQA/MLA 属于模型结构，量化涉及表示格式和内核，投机解码属于生成算法，连续批处理和分页属于调度与缓存管理。它们相互配合，但不是同一层的替代方案。现代推理引擎还需要服务层：兼容 API、流式输出、限流、取消等。

## 本章小结

- 训练追求吞吐，推理同时追求延迟和吞吐；在线服务还要考虑排队和尾延迟。
- 生成分预填充和解码两个阶段；TTFT、TPOT、ITL 分别描述不同环节。
- KV Cache 随层数、上下文和并发增长，是推理显存的主要变量；GQA/MLA 和量化能减少它。
- 连续批处理在迭代边界重新组批，让新请求利用空槽；收益取决于负载，不是固定倍数。
- 分页注意力减少预留和碎片浪费，不压缩每个词元的 K/V。
- chunked prefill、PD 分离、KV 分层、multi-LoRA、约束解码和投机解码，分别在长提示、阶段隔离、缓存层级、多租户和生成算法上做取舍。
- 量化用低比特加 scale/zero-point 表示张量；粒度、量化对象和内核决定误差与速度，省显存不等于加速。
- 推理加速手段分属模型结构、数值格式、生成算法、调度缓存等不同层，不能互相替代。

> **一句话记住本章**：推理工程就是在吞吐、显存和延迟之间做取舍，先测瓶颈，再选手段。
