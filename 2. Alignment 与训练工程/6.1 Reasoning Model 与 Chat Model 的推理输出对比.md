# 6.1 推理模型（Reasoning Model）与对话模型（Chat Model）的推理输出对比

> **硬件要求**：以下示例以单张 CUDA GPU 为主；两个 1.5B 模型的半精度权重合计约 6GB，另需运行时与 KV cache 空间。建议 12GB 以上显存、batch size=1；这不是所有长度都能运行的保证。显存不足可分两轮只加载一个模型，保存相同题目的结果再比较，不必同时驻留。CPU/MPS 可另行适配，但本节未验证其速度与算子兼容性。
>
> **本节目标**：观察一个推理蒸馏模型与一个 Instruct 模型在相同题目上的输出、答案正确率和 token 成本。**这是行为观察，不是“RL 对比 SFT”的受控实验，也不能凭思考标签证明内部推理机制。** 本节会区分错误答案、输出截断、格式失败和无法判定。

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

if not torch.cuda.is_available():
    raise RuntimeError("此示例按单张 CUDA GPU 编写；CPU/MPS 需另行调整。")
dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
reasoning_name = "deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B"
chat_name = "Qwen/Qwen2.5-1.5B-Instruct"

reasoning_tok = AutoTokenizer.from_pretrained(reasoning_name)
reasoning_model = AutoModelForCausalLM.from_pretrained(
    reasoning_name, torch_dtype=dtype, device_map={"": 0}
).eval()
chat_tok = AutoTokenizer.from_pretrained(chat_name)
chat_model = AutoModelForCausalLM.from_pretrained(
    chat_name, torch_dtype=dtype, device_map={"": 0}
).eval()
```

两个模型参数量接近，但蒸馏模型基座是 **Qwen2.5-Math-1.5B**，另一个是 **Qwen2.5-1.5B-Instruct**，基础数据与后训练配方均不相同。R1 原论文的蒸馏小模型使用教师整理数据做 SFT，没有继续做 RL。因此差异不能单独归因于 RL，也不能推出 SFT 只教格式。

## 二、同一道推理题，两种表现

```python
question = (
    "一个房间内有三盏相同的白炽灯，初始关闭且冷却，三个外部开关与灯一一对应。"
    "在房外看不到灯；可以任意操作开关，但只允许进房一次，进房后不能再操作开关。"
    "假设开灯后可留下可安全检测的余温，如何确定对应关系？这是理想化逻辑题，不要实际触摸热灯泡。"
)

import time

@torch.inference_mode()
def ask(model, tok, question, max_new_tokens=2048, seed=42):
    torch.manual_seed(seed)
    messages = [{"role": "user", "content": question}]
    text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tok(text, return_tensors="pt", add_special_tokens=False).to(model.device)
    input_count = inputs["input_ids"].shape[1]
    if input_count + max_new_tokens > model.config.max_position_embeddings:
        raise ValueError("输入与生成预算超过模型配置上限")
    eos = model.generation_config.eos_token_id
    eos_ids = {eos} if isinstance(eos, int) else set(eos or [tok.eos_token_id])
    eos_ids.discard(None)
    pad = tok.pad_token_id if tok.pad_token_id is not None else tok.eos_token_id
    torch.cuda.synchronize()
    start = time.perf_counter()
    output = model.generate(
        **inputs, max_new_tokens=max_new_tokens, do_sample=True,
        temperature=0.6, top_p=0.95, pad_token_id=pad,
    )
    torch.cuda.synchronize()
    elapsed = time.perf_counter() - start
    new_ids = output[0][input_count:]
    stopped = bool(new_ids.numel()) and new_ids[-1].item() in eos_ids
    return {
        "text": tok.decode(new_ids, skip_special_tokens=True),
        "input_tokens": input_count, "output_tokens": new_ids.numel(),
        "seconds": elapsed,
        "finish_reason": "eos" if stopped else "length" if len(new_ids) >= max_new_tokens else "unknown",
        "prefilled_think": text.rstrip().endswith("<think>"),
    }

chat_result = ask(chat_model, chat_tok, question)
reason_result = ask(reasoning_model, reasoning_tok, question)
for name, result in [("Chat", chat_result), ("Reasoning-Distill", reason_result)]:
    print(name, result["finish_reason"], result["output_tokens"], result["seconds"])
    print(result["text"])
```

两者使用相同生成预算与采样参数，便于观察；`temperature=0.6` 参考 R1 模型卡建议，不意味着这是每个模型的最优配置。需记录版本、模板、随机种子，并用多个种子复测。2048 token 仍可能截断长推理：若 `finish_reason="length"`，先标记预算不足，不能把未完成的段落当最终答案。

这是常见逻辑题，可能出现在训练材料里，不适合证明泛化。比较时关注答案是否满足白炽灯余温等条件，不要只数“反思”词语。耗时仅含本地 `generate`，首次运行可能有预热开销，不是完整服务延迟。

## 三、把可见“思考”与“答案”分开，保留解析状态

```python
import re

def split_thinking(result):
    text = result["text"].strip()
    if result["prefilled_think"]:
        text = "<think>" + text
    has_tags = "<think>" in text or "</think>" in text
    match = re.fullmatch(r"<think>(.*?)</think>\s*(.*)", text, re.S)
    if match and text.count("<think>") == text.count("</think>") == 1:
        thinking, answer = match.group(1).strip(), match.group(2).strip()
        return thinking, answer, "tagged" if answer else "missing_answer"
    if has_tags:
        return None, None, "malformed_tags"
    return None, text, "no_tags"

thinking, answer, parse_status = split_thinking(reason_result)
print("解析状态:", parse_status, "生成结束原因:", reason_result["finish_reason"])
print("可见思考节选:", thinking[:300] if thinking else "未提取到")
print("答案部分:", answer)
```

模板可能已经在输入尾部放入 `<think>`，因此只解码新增 token 时不一定能看到开标签；上例检查实际渲染前缀再解析。`no_tags` 只是输出形式，**不是模型没有推理能力的证据**；标签缺失、嵌套或未闭合也应与生成截断一起检查。可见轨迹本身不保证忠实反映内部计算。

## 四、一个简化版 Verifier：只关心结果，不关心过程

先约定输出协议：允许前面分步解题，但最终答案部分只能出现一次 `FINAL:`，且最后一行必须是 `FINAL: 数值`，不带单位、其他文字或代码围栏。题干已明确单位；数值允许整数、小数或整数分数，不支持任意表达式。这样不会把附注、题号或推理中最后出现的数字误作答案。

```python
from fractions import Fraction
from collections import Counter

math_questions = [
    {"q": "小明有15个苹果，送出6个，又买回9个，现在有多少个？", "answer": "18"},
    {"q": "长方形长8米、宽5米，面积是多少平方米？", "answer": "40"},
    {"q": "三次用水分别为2.75、1.5和0.75升，总共用了多少升？", "answer": "5"},
    {"q": "一根绳子长7米，平均分成4段，每段多少米？", "answer": "7/4"},
]
number_pattern = r"[+-]?(?:\d+/\d+|\d+(?:\.\d+)?|\.\d+)"
final_pattern = re.compile(r"FINAL:\s*(" + number_pattern + r")")


def verify(result, expected):
    if result["finish_reason"] == "length":
        return "truncated"
    if result["finish_reason"] != "eos":
        return "unknown"
    _, answer, status = split_thinking(result)
    if status in {"malformed_tags", "missing_answer"} or not answer:
        return "format_failure"
    if answer.count("FINAL:") != 1:
        return "format_failure"
    match = final_pattern.fullmatch(answer.splitlines()[-1].strip())
    if match is None:
        return "format_failure"
    try:
        predicted, target = Fraction(match.group(1)), Fraction(expected)
    except (ValueError, ZeroDivisionError):
        return "unknown"
    return "correct" if predicted == target else "wrong"


suffix = (
    " 请分步解答，最后单独一行写 FINAL: 数值。"
    "仅在该行使用一次 FINAL:，数值允许整数、小数或整数分数，不带单位或其他内容。"
)
for name, model, tok in [
    ("Chat", chat_model, chat_tok), ("Reasoning-Distill", reasoning_model, reasoning_tok)
]:
    counts, total_tokens, total_seconds = Counter(), 0, 0.0
    for item in math_questions:
        result = ask(model, tok, item["q"] + suffix, max_new_tokens=2048)
        status = verify(result, item["answer"])
        counts[status] += 1
        total_tokens += result["output_tokens"]
        total_seconds += result["seconds"]
        print(name, item["q"], status, result["output_tokens"], result["seconds"])
    total = len(math_questions)
    print(name, dict(counts), "严格成功率:", counts["correct"] / total)
    print("平均生成token:", total_tokens / total, "平均生成秒数:", total_seconds / total)
```

`18`、`18.0`、`36/2` 数值等价；本节用 `Fraction` 精确比较这些有理数，不做字符串硬比，也不 `eval` 模型文本。若题目要求近似实数，需要另外声明绝对/相对容差；若答案含单位、区间或多解，需要专用验证器。不要静默套用本例。

这里分别记录 `correct`、`wrong`、`truncated`、`format_failure`、`unknown`。严格成功率以全部题目为分母，不能丢掉解析失败样本后报一个虚高分数；同时应单独报告各失败比例。即使最终结果正确，也不能证明中间步骤正确，过程监督需要额外的逐步反馈或校验。

这些题只用于冒烟观察，不能支持性能排名。请在**未参与调参的保留题集**上增加不同数字、组合约束和题型，再用多个种子重复；“这里新写的题”不保证模型预训练时未见。先比较相同 token 上限，再比较相同总生成 token 或相同延迟预算下的正确率；token 不是严格的 FLOPs 单位，还要记录 tokenizer、硬件和模板差异。

## 本节小结

- 比较的是推理蒸馏模型与 Instruct 模型的行为，不是控制了其他变量的 RL/SFT 因果实验。
- 输出标签、文字长度、自我修正语句都不能单独证明推理能力；先检查完整性与答案格式。
- Outcome Verifier 需要明确协议、数值等价规则和失败状态；正确率与 token/时间成本应一起报告。
