# 10.1 使用 vLLM 验证连续批处理（Continuous Batching）

> **硬件要求**：需 GPU——vLLM 推理服务依赖 CUDA 环境；云 GPU 方案见前言 P0.3
>
> **本节目标**：10.2 节会比较单请求 KV Cache 与本地资源开销；本节关注“很多用户同时请求”的服务端场景。在同一个 vLLM 服务上比较顺序、一次性并发与分批到达，记录实际 Token 吞吐、端到端延迟和请求重叠；同时区分“观察负载效应”与“验证内部调度机制”的证据边界。

---

## 一、先固定实验问题与服务配置

本节比较**同一后端上的三种请求到达方式**，不是比较两个推理引擎：

1. **顺序请求**：上一个响应完成后才发下一个，是客户端闭环负载；
2. **一次性并发**：所有请求在同一计划时刻发出；
3. **分批到达**：每两个请求一组，按预先设定的时间发出，不等待前面的响应。

后两种方式允许服务器同时接收多个请求，由 vLLM 独立的调度循环管理。单个 worker 中反复 `sleep → blocking generate` 仍是串行；仅把它包进线程，并不能模拟独立到达。

在适配当前 GPU/CUDA 的独立环境安装 vLLM；客户端只需要 `httpx`，不加载 HF 模型：

```bash
pip install vllm httpx
vllm serve Qwen/Qwen2.5-1.5B-Instruct \
    --host 127.0.0.1 --port 8000 \
    --dtype half --max-model-len 1024 --max-num-seqs 4 \
    --gpu-memory-utilization 0.85 \
    --generation-config vllm --no-enable-prefix-caching
```

等待服务就绪后，在**另一个终端/进程**运行下文客户端。服务端是唯一加载模型权重的进程，避免 HF 模型与 vLLM 实例同时占用同一张卡。`gpu-memory-utilization` 是执行器整体的显存预算比例，包含权重与运行时开销，并非把 85% 显存全分给 KV Cache；`max-num-seqs` 是调度迭代的序列数上限，不是 HTTP 请求总数上限。

这里关闭跨请求 Prefix Caching，以减少重复 Prompt 命中缓存造成的比较偏差，**并未关闭单请求的 Decode KV Cache**。启动参数会随版本演进，应以安装版本的帮助和 [vLLM serve 文档](https://docs.vllm.ai/en/latest/cli/serve/) 为准；记录 vLLM、PyTorch/CUDA、GPU、模型 revision、Chat Template 和完整服务配置。三种方式始终使用同一服务、同一组 Prompt、同一采样设置。

## 二、异步客户端：到达时刻不由响应完成决定

以下 Python 代码自包含，只依赖已启动的服务与 `httpx`。`asyncio.gather` 同时启动各请求任务；每个任务睡眠到相对统一起点的**绝对计划时刻**，因此慢响应不会推迟下一个请求的计划到达。

```python
import asyncio
import json
import math
import statistics
import time

import httpx

URL = "http://127.0.0.1:8000/v1/chat/completions"
MODEL = "Qwen/Qwen2.5-1.5B-Instruct"
PROMPTS = [
    "介绍一下人工智能的发展历史。",
    "什么是 Transformer？",
    "写一首关于秋天的诗。",
    "解释一下什么是递归。",
    "推荐三本机器学习入门书籍。",
    "简单介绍一下量子计算。",
    "什么是区块链？",
    "解释一下 TCP 和 UDP 的区别。",
]
GROUP_INTERVAL = 0.10


async def request_one(client, index, prompt, origin, offset):
    scheduled = origin + offset
    await asyncio.sleep(max(0.0, scheduled - time.perf_counter()))
    sent = time.perf_counter()
    response = await client.post(URL, json={
        "model": MODEL,
        "messages": [{"role": "user", "content": prompt}],
        "temperature": 0.0,
        "top_p": 1.0,
        "seed": 42,
        "max_tokens": 100,
        "stream": False,
    })
    response.raise_for_status()
    data = response.json()
    done = time.perf_counter()
    usage = data["usage"]
    choice = data["choices"][0]
    return {
        "id": index,
        "scheduled_s": offset,
        "sent_s": sent - origin,
        "done_s": done - origin,
        "dispatch_lag_s": sent - scheduled,
        "latency_s": done - sent,
        "scheduled_latency_s": done - scheduled,
        "prompt_tokens": usage["prompt_tokens"],
        "completion_tokens": usage["completion_tokens"],
        "finish_reason": choice["finish_reason"],
        "answer": choice["message"]["content"],
    }


async def run_case(client, mode):
    origin = time.perf_counter()
    if mode == "sequential":
        rows = []
        for i, prompt in enumerate(PROMPTS):
            offset = time.perf_counter() - origin
            rows.append(await request_one(client, i, prompt, origin, offset))
    else:
        if mode == "burst":
            offsets = [0.0] * len(PROMPTS)
        elif mode == "staggered":
            offsets = [(i // 2) * GROUP_INTERVAL for i in range(len(PROMPTS))]
        else:
            raise ValueError(f"未知模式: {mode}")
        rows = await asyncio.gather(*(
            request_one(client, i, prompt, origin, offsets[i])
            for i, prompt in enumerate(PROMPTS)
        ))
    elapsed = max(row["done_s"] for row in rows)
    return rows, elapsed


def summarize(mode, repeat, rows, elapsed):
    latency = sorted(row["latency_s"] for row in rows)
    tokens = sum(row["completion_tokens"] for row in rows)
    return {
        "mode": mode,
        "repeat": repeat,
        "elapsed_s": elapsed,
        "requests_per_s": len(rows) / elapsed,
        "output_tokens_per_s": tokens / elapsed,
        "actual_output_tokens": tokens,
        "latency_p50_s": statistics.median(latency),
        "latency_p95_s": latency[math.ceil(0.95 * len(latency)) - 1],
        "max_dispatch_lag_s": max(row["dispatch_lag_s"] for row in rows),
        "rows": rows,
    }


async def main():
    limits = httpx.Limits(max_connections=16, max_keepalive_connections=16)
    async with httpx.AsyncClient(timeout=120.0, limits=limits) as client:
        for mode in ("sequential", "burst", "staggered"):
            await run_case(client, mode)
        orders = [
            ("sequential", "burst", "staggered"),
            ("burst", "staggered", "sequential"),
            ("staggered", "sequential", "burst"),
        ]
        for repeat, order in enumerate(orders, start=1):
            for mode in order:
                rows, elapsed = await run_case(client, mode)
                print(json.dumps(
                    summarize(mode, repeat, rows, elapsed), ensure_ascii=False
                ))


if __name__ == "__main__":
    asyncio.run(main())
```

前三轮是各模式的预热，不计入输出；正式测量轮换模式顺序，减轻首次连接、内核初始化和机器温度漂移的影响。每轮都等待全部响应完成后再开始下一轮，避免跨轮重叠。HTTP 错误、超时或缺失 usage 会直接使本次运行失败，不能偷偷用零 Token 把失败请求计作成功。

`temperature=0` 固定为贪心生成，但并发形状与数值实现仍可能引起个别输出差异，因此保留实际回答、Token 数与停止原因。这里报告的是**实际生成 Token 总数 / 整轮墙钟时间**，不是 `8 × max_tokens / 时间`。

## 三、先检查到达记录，再解释指标

观察每条结果的 `scheduled_s`、`sent_s` 和 `done_s`：

- 顺序模式中，下一个 `sent_s` 应不早于上一个 `done_s`；
- 同时到达模式的计划时刻全为 0，实际发出时刻应接近；
- 分批到达的计划时刻为 `0, 0, 0.1, 0.1, 0.2, 0.2, 0.3, 0.3` 秒，是否真的重叠要由 `sent_s < 前面请求的 done_s` 判断。如果机器很快、没有重叠，可先减小组间隔或增加输出预算，随后**用固定的新协议重新测完整三种方式**。

`dispatch_lag_s` 用于发现客户端来不及按计划发出的情况；偏差很大时，应先排查客户端负载或连接限制。客户端发出时刻不等于服务端入队时刻，更不等于 GPU 开始执行时刻。

`latency_s` 是实际发出到完整响应返回的端到端延迟，包含服务端排队、推理、网络与解析；`scheduled_latency_s` 还包括客户端相对计划时刻的延迟。分批模式的整轮时间包含预定的到达间隔，因此它的吞吐可能受**提供负载不足**限制，不代表服务器峰值能力。顺序模式是闭环、其余两种是开放式到达，三者不是同一负载下的调度器消融。

每轮只有 8 个请求，nearest-rank P95 实际上接近最大值，不能作为可靠的线上尾延迟估计。比较各轮原始值与波动；正式压测需更长稳态时间、足够样本和多个请求速率，并统计超时/错误率。本例是非流式响应，**没有测 TTFT、ITL 或 TPOT**；不能把整段耗时除以输出数就当作纯 Decode TPOT。

## 四、这个实验能证明什么，不能证明什么？

它能观察同一 vLLM 服务在不同客户端并发与到达方式下的端到端吞吐、延迟和在途请求重叠。若并发提高了吞吐，可说“当前配置能利用多个请求”，但不能仅凭此断言全部收益来自 Continuous Batching，更不能预设固定加速倍数或 GPU 始终满载。

若要验证“旧请求未结束时，新请求已加入执行 Batch”这一**内部机制**，还需结合对应版本的服务端调度日志/trace，观察请求何时从等待转为运行；若要量化相对静态批处理的净收益，还需固定到达序列、内核、精度、内存预算等，只改变调度策略。HF 逐条生成对比 vLLM 批量生成同时改变了引擎与并发方式，不能作为这样的因果证据。本节不实现生产级静态调度器。

## 本节小结

- 服务端独立运行，异步客户端按计划提交请求，不把 blocking generate 包在线程里假装并发。
- 固定模型、服务配置和生成协议，分别预热并记录实际 Token 吞吐、端到端延迟与到达偏差。
- 请求重叠、内部迭代调度与调度策略的净加速收益是三个不同的证据层次。

**KV Cache 减少单请求内的历史重算，连续批处理改善跨请求资源利用率；收益仍取决于具体负载与资源约束。**
