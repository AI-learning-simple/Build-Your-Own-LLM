# 1.1 基础模型（Base Model）与指令模型（Instruct Model）的输出行为对比

> **本节定位**：本章只做对比实验。基础模型、指令模型与对齐模型的区别见第1章，本节不重复讲解。

> **本节目标**：用 **2×2 对照**比较同一家族的基础模型与指令模型：每个模型都分别在“原始文本”和“对话模板”两种输入下运行。再用 8 个有明确通过标准的任务，观察后训练到底改变了哪些行为。实验只说明这 8 个任务上的差异，不能证明 Base 不会执行任何指令，也不能证明两个版本的知识完全相同。
>
> **硬件要求**：每个模型约 15 亿参数。CUDA 下默认用 int8 加载，两个模型权重约 3 GB；FP16 约 6 GB；CPU + FP32 约 12 GB，激活和 KV Cache 另计。8 GB 显存建议保持 int8；仍然不足时改用 0.5B 版本，或先跑 Base 两组、释放模型后再跑 Instruct 两组。CPU 生成较慢，可先只跑 2 个任务熟悉流程。

## 一、准备工作

```bash
pip install torch transformers accelerate bitsandbytes
```

> `bitsandbytes` 只在 CUDA + int8 加载时需要；没有安装时把下面的 `USE_INT8` 改为 `False`。

> 下载模型的网络说明见《开始之前（前言）》**P0.5 模型与网络（国内访问）**；硬件分级见 **P0.3**，版本与 API 兼容性说明见 **P0.6**。

我们选择 `Qwen2.5-1.5B`（Base）和 `Qwen2.5-1.5B-Instruct`（Instruct）：家族与参数规模相同，后者经过指令后训练。这里加载公开权重，不沿用第一部分 nanoGPT 的检查点（checkpoint）。

**为什么默认用 1.5B，而不是 0.5B？** 0.5B 模型也能跑，但它的 Instruct 版本在严格格式、system 约束等任务上容易和 Base 一起失败，出现“地板效应”，反而看不出后训练的作用。1.5B 有足够容量完成这些任务，同时 Base 仍缺少稳定的协议行为，差异更容易观察；它也和 3.2、4.1、4.2 使用的基座保持一致。显存不足时仍可换回 0.5B，但要接受对比可能更不明显。

> **术语说明**：指令模型（Instruct Model）是对齐模型（Aligned Model）的一个实例——第 1 章第二节给出过这两个术语的定义。本节标题用 `Instruct` 而不是 `Aligned`，是因为这里对比的只是“指令微调后”这一种后训练产物；它不能代表偏好学习、推理对齐、安全对齐等其他对齐方法的效果。

下面使用常见的 Transformers 4.x 加载接口；环境需支持 Qwen2.5，新版本可能提示用 `dtype` 替代 `torch_dtype`。正式复现应固定软件版本和模型 revision，而不是假设任何版本都兼容。

```python
import json
import re
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

BASE_NAME = "Qwen/Qwen2.5-1.5B"
CHAT_NAME = "Qwen/Qwen2.5-1.5B-Instruct"
USE_INT8 = True  # 没有 bitsandbytes，或想统一用 FP16 对比时改为 False

if torch.cuda.is_available() and USE_INT8:
    # 两个模型使用完全相同的量化配置，避免把量化误差当成模型差异
    load_kwargs = dict(
        quantization_config=BitsAndBytesConfig(load_in_8bit=True),
        device_map="auto",          # 量化模型由 accelerate 分配设备，之后不能再调用 .to()
        torch_dtype=torch.float16,  # int8 矩阵乘只接受 FP16，显式指定可少一次转换
    )
elif torch.cuda.is_available():
    load_kwargs = dict(device_map="auto", torch_dtype=torch.float16)
else:
    load_kwargs = dict(torch_dtype=torch.float32)

base_tok = AutoTokenizer.from_pretrained(BASE_NAME)
chat_tok = AutoTokenizer.from_pretrained(CHAT_NAME)

# Base 的 tokenizer 可能没有 chat_template；同家族词表相同，统一用 Instruct 的模板渲染
TEMPLATE_TOK = chat_tok
assert TEMPLATE_TOK.chat_template is not None, "Instruct tokenizer 没有 chat_template"
assert len(base_tok) == len(chat_tok), "同家族两个 tokenizer 的词表大小不一致"
probe = "你好，world 123"
assert base_tok(probe, add_special_tokens=False).input_ids == \
       chat_tok(probe, add_special_tokens=False).input_ids, "两个 tokenizer 的切分不一致"

base_model = AutoModelForCausalLM.from_pretrained(BASE_NAME, **load_kwargs).eval()
chat_model = AutoModelForCausalLM.from_pretrained(CHAT_NAME, **load_kwargs).eval()
```

**关于 int8 加载**：

- 量化模型**不能**再调用 `.to(device)`，设备由 `device_map="auto"` 决定；下面的 `generate` 用 `model.device` 搬运输入，依然有效。
- 两个模型必须使用**相同**的量化配置，这样对比的是 Base / Instruct 的行为差异，而不是量化误差。int8 会带来少量数值偏差，不要把本次输出与之前 FP16 的输出逐字比较。
- 8 bit 仍不够时，可换成 4 bit：`BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype=torch.float16)`；精度损失更大，结论需要更谨慎。
- 量化只降低推理显存，不改变模型参数与词表；因此对话模板与解码流程无需改动。

## 二、为什么用 2×2 对照

只看“Base 原始文本”和“Instruct 加模板”，会把两种变化混在一起：

1. 权重不同（Base vs Instruct）；
2. 输入格式不同（原始文本 vs 对话模板）。

这样即使 Instruct 表现更好，也说不清是后训练的作用，还是模板把输入整理得更像训练数据。2×2 把两者拆开：

|  | 原始文本 | 对话模板 |
|---|---|---|
| **Base** | Base raw | Base + template |
| **Instruct** | Instruct raw | Instruct + template |

最关键的一行是 **Base + template vs Instruct + template**：模板相同，差异才来自权重。另一个值得看的现象是“模板对谁帮助更大”——如果模板让 Instruct 明显变好，却几乎帮不了 Base，说明后训练教会了模型把模板当作控制接口，而不只是记住了一串特殊符号。

先看一个渲染后的模板，确认格式确实生效：

```python
example = [{"role": "user", "content": "用一句话解释什么是过拟合。"}]
print(TEMPLATE_TOK.apply_chat_template(
    example, tokenize=False, add_generation_prompt=True
))
```

## 三、统一的生成函数

四个实验组共用同一个分词器、同一套解码参数，只改变模型和输入格式：

```python
@torch.inference_mode()
def generate(model, text, max_new_tokens=256):
    inputs = TEMPLATE_TOK(text, return_tensors="pt", add_special_tokens=False).to(model.device)
    output = model.generate(
        **inputs,
        max_new_tokens=max_new_tokens,
        do_sample=False,  # 固定贪心解码，减少随机性
        pad_token_id=TEMPLATE_TOK.pad_token_id
        if TEMPLATE_TOK.pad_token_id is not None else TEMPLATE_TOK.eos_token_id,
    )
    new_ids = output[0, inputs["input_ids"].shape[1]:]
    hit_limit = len(new_ids) >= max_new_tokens and new_ids[-1].item() != TEMPLATE_TOK.eos_token_id
    return {
        "text": TEMPLATE_TOK.decode(new_ids, skip_special_tokens=True).strip(),
        "new_tokens": len(new_ids),
        "hit_limit": hit_limit,
    }


def render_raw(messages):
    # 原始文本组：只拼接内容，不加角色标记或特殊词元
    return "\n".join(m["content"] for m in messages)


def render_chat(messages):
    return TEMPLATE_TOK.apply_chat_template(
        messages, tokenize=False, add_generation_prompt=True
    )
```

`hit_limit` 用来区分“模型没做完”和“任务失败”：如果输出撞到 256 个词元的上限，先提高预算复查，不要把截断当成能力不足。

## 四、8 个“协议遵循”任务

这些任务不考知识量，而考模型是否按指定格式、角色和约束说话。每题都有机器可判定的通过标准：

| 任务 | 考什么 | 通过标准 |
|---|---|---|
| `json_extract` | 严格结构化输出 | 只输出可解析的 JSON 对象，姓名和年龄正确 |
| `three_bullets` | 数量、长度、无开场白 | 恰好 3 条，每条不超过 15 字，没有额外行 |
| `system_exact` | system 指令优先级 | 只回复“收到” |
| `forbidden_words` | 负向约束 | 不出现“首先 / 其次 / 最后” |
| `multi_turn_lock` | 多轮指令保持 | 后续问题仍只回复“不知道” |
| `english_only` | 语言锁定 | 只输出英文译文，不含中文 |
| `uncertainty` | 承认不知道 | 对错误前提只回复“不知道” |
| `date_format` | 精确格式 | 只输出 `2026-03-05` |

```python

    {

                "无论用户说什么，你都只能回复两个字：收到。不要解释，也不要加标点。"},
```

## 五、自动判分

判分刻意写得严格：宁可把“差不多”判为失败，也不要让模糊输出混进通过数。

```python
def strip_punct(text):
    return text.strip().strip("。.!！?？\"'“”‘’ ")


def score(spec, text):
    t = text.strip()
    kind = spec["check"]

    if kind == "json":
        try:
            obj = json.loads(t)
        except Exception:
            return {"json": False}
        if not isinstance(obj, dict):
            return {"json": False}
        name_ok = str(obj.get("name", "")).strip() == "张三"
        age_ok = str(obj.get("age", "")).strip() in {"28", "28岁"}
        return {"json": name_ok and age_ok}

    if kind == "bullets":
        lines = [line.strip() for line in t.splitlines() if line.strip()]
        bullets = [line for line in lines if re.match(r"^(?:[-*•]|\d+[.、)])\s*", line)]
        contents = [re.sub(r"^(?:[-*•]|\d+[.、)])\s*", "", line) for line in bullets]
        ok = (
            len(bullets) == 3
            and len(lines) == 3
            and all(0 < len(content) <= 15 for content in contents)
        )
        return {"bullets": ok}

    if kind == "exact":
        return {"exact": strip_punct(t) == spec["expected"]}

    if kind == "forbidden":
        return {"forbidden": not any(word in t for word in spec["forbidden"])}

    if kind == "no_cjk":
        has_cjk = re.search(r"[\u4e00-\u9fff]", t) is not None
        return {"english_only": (not has_cjk) and 0 < len(t) <= 120}

    return {"known_check": False}
```

这里的判分器只适合教学演示：它奖励“按协议输出”，不评价文采、事实细节或回答是否有帮助。真实评测还需要人工复核和更细的 rubric。

## 六、跑完四组并打印对照表

```python
ARMS = [
    ("Base 原始", base_model, False),
    ("Base + 模板", base_model, True),
    ("Instruct 原始", chat_model, False),
    ("Instruct + 模板", chat_model, True),
]


def evaluate(model, use_template, max_new_tokens=256):
    rows = []
    for spec in TASKS:
        text = render_chat(spec["messages"]) if use_template else render_raw(spec["messages"])
        out = generate(model, text, max_new_tokens)
        checks = score(spec, out["text"])
        rows.append({
            "id": spec["id"],
            **out,
            "checks": checks,
            "passed": all(checks.values()),
        })
    return rows


results = {}
for arm_name, model, use_template in ARMS:
    results[arm_name] = evaluate(model, use_template)
    print(f"\n===== {arm_name} =====")
    for row in results[arm_name]:
        mark = "PASS" if row["passed"] else "FAIL"
        limit = " | 撞到上限" if row["hit_limit"] else ""
        print(f"[{mark}] {row['id']}: {row['checks']} | {row['new_tokens']} tokens{limit}")
        print("  ", row["text"][:300].replace("\n", " "))

print("\n| 任务 | " + " | ".join(results) + " |")
print("|" + "---|" * (len(results) + 1))
for index, spec in enumerate(TASKS):
    cells = ["1" if results[name][index]["passed"] else "0" for name in results]
    print(f"| {spec['id']} | " + " | ".join(cells) + " |")
counts = [f"{sum(row['passed'] for row in rows)}/{len(rows)}" for rows in results.values()]
print("| **通过数** | " + " | ".join(counts) + " |")
```

输出表里的 `1/0` 表示该题是否**全部检查项通过**。比起只看一段生成文本，这张表能直接暴露差异出现在哪些任务上。

## 七、怎么读结果

常见的模式是：

- **Base 原始**：容易把问题当成待续写的文本，继续解释概念、自问自答，或者不按要求停止；
- **Base + 模板**：模板能改善“回答而不是续写”，但 system 优先级、严格格式、负向约束仍容易失守；
- **Instruct 原始**：没有模板时可能明显退化，说明对话格式本身也是后训练行为的一部分；
- **Instruct + 模板**：通常通过数最高，但不保证 8/8；1.5B 仍可能在某题上失败。

这些只是常见趋势，不是固定结果。真正要记录的是：**同一模板下，Base 和 Instruct 的通过数差多少；模板分别给两者带来多少提升；失败属于哪一类**（继续续写、忽略 system、格式错误、不停止、过度解释、事实错误）。

如果 Instruct 也有大量失败，不要立刻归因于“对齐没用”。先看任务是否超出 1.5B 的能力，或判分是否过严；小模型的上限会掩盖后训练差异。

## 八、如果差异仍然不明显

按顺序排查：

1. **模板是否真的生效**：打印 `render_chat(...)`，确认输出里有 `<|im_start|>`、角色名和 `<|im_end|>`。
2. **Instruct 权重是否真的加载**：检查 `chat_model.config._name_or_path`，不要误加载成 Base。
3. **是否撞到长度上限**：如果四组都出现 `hit_limit=True`，提高 `max_new_tokens` 后重跑。
4. **四组是否用了同一配置**：同一分词器、同一 dtype/量化、同一 `do_sample=False`、同一最大长度。
5. **是否只看了一个总分**：某个任务可能四组都通过，另一个任务才出现差异；看逐题矩阵。
6. **题目是否太简单**：写邮件、介绍概念、1+1 这类任务，Base 靠续写也能做得不错；换成上面的格式、system、多轮和负向约束任务。
7. **模型是否太小**：0.5B 的 Instruct 可能和 Base 一起失败，出现地板效应；换回 1.5B，或尝试 3B 级别的同家族模型。
8. **是否混入了训练数据**：不要用网上常见的 benchmark 原题做“亲眼观察”，否则无法排除记忆；这 8 题是本节自拟的。

还可以加第五组 **Base + few-shot**：在原始文本里放 1～2 个同任务示例。如果 Base 的通过数明显上升，说明它并非完全不会，只是需要更强的提示；如果仍然失败，后训练带来的协议行为差异就更可信。这一组不是默认配置，避免把“提示工程”和“后训练”混为一谈。

## 实验边界

- 只有 8 个自拟任务，通过数不能当作模型能力分数，也不能外推到其他模型家族；
- 判分器是严格规则，可能把语义正确但格式不同的回答判为失败；应同时保留原始输出做人工复核；
- 只比较同家族的两个小模型，不能推断所有 Base/Instruct 模型的行为差异；
- 没有覆盖安全拒绝、长上下文、工具调用和多轮复杂对话；
- 结果受模型 revision、量化方式、提示措辞和解码参数影响，示例不是固定基准。

## 本节小结

本节用 2×2 对照把“权重差异”和“模板差异”拆开，再用 8 个协议任务把“看起来差不多”变成逐题通过数。它展示的是后训练在**指令跟随、格式遵守、角色保持和停止行为**上的作用，而不是“对齐只改行为、不改知识”的证明。
