# 10.2 量化、KV Cache 与本地推理加速实战

> **硬件要求**：路径 A 需 NVIDIA CUDA；路径 B 可使用 CPU、Apple Silicon/Metal 或兼容 GPU。不同平台分别记录条件，不把跨平台耗时差异直接归因于量化。云 GPU 方案见前言 P0.3。
>
> **本节目标**：10.1 节我们关注的是"服务端如何同时服务很多用户"（vLLM + 连续批处理（Continuous Batching））。这一节换一个更贴近个人的场景：**一块 8GB 显存的消费级显卡，到底能不能跑动一个 7B 模型？** 我们会以 7B checkpoint 为例，分别介绍 **Hugging Face 生态**（transformers + bitsandbytes）与 **llama.cpp / Ollama**（GGUF）两条量化推理路径；实际测量权重与运行时占用、KV Cache 开关延迟，以及不同上下文长度的缓存张量大小。是否能在特定 8GB 设备运行由平台、量化格式、上下文和运行时共同决定。
>
> **平台边界**：本节路径 A 的 `bitsandbytes` 4-bit 示例按 **NVIDIA CUDA** 环境编写，且需要兼容的驱动、PyTorch 与 bitsandbytes 版本；它不能原样用于 macOS 的 MPS。Apple Silicon 建议走路径 B 的 llama.cpp / Ollama（Metal），此时占用的是统一内存而不是独立“显存”。7B 4-bit 能否在 8GB 设备运行还取决于量化格式、上下文长度、KV Cache、运行时缓冲区和是否发生 CPU offload，不能只由权重大小保证。

# 一、为什么 7B 模型原本装不进 8GB？

`Qwen2.5-7B` 有 76 亿参数。如果用 FP16（每个参数占 2 字节）存储，仅权重就需要 `76亿 × 2字节 ≈ 15GB`，还没算推理时的中间激活值和 KV Cache——**远超 8GB 显存**。这正是第一部分第13章 MoE 一节提到的"参数越多、计算/存储代价越大"问题的另一面：**存储代价同样会随参数线性增长**。

---

# 二、量化的核心思想

量化（Quantization）用更少的比特表示权重或激活。FP16 权重每参数 16 bit，4-bit 权重的理想数据 payload 是其 `1/4`；实际还要存分组 scale、zero point 等元数据。最终权重与运行时占用取决于量化方案和实现，必须连同 KV Cache、临时张量、缓冲区与 offload 一起实测。

代价是表示误差与额外的量化/反量化处理。质量变化可能很小，也可能集中损伤某些敏感任务，不能预设都“轻微且可接受”。是否值得采用，应在相同输入与生成协议下同时比较质量、速度和内存；更少的 bit 不自动等于更快的内核。

# 三、路径 A：Hugging Face 生态（bitsandbytes 4-bit 量化）

以下代码先显式检查 CUDA，避免在 CPU 或 macOS/MPS 上误运行：

```bash
pip install torch transformers accelerate bitsandbytes
```

```python
import torch
import time
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

if not torch.cuda.is_available():
    raise RuntimeError("此 bitsandbytes 示例需要 NVIDIA CUDA；macOS 请使用下文 Ollama/llama.cpp 路径。")

model_name = "Qwen/Qwen2.5-7B-Instruct"
quant_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, quantization_config=quant_config, device_map="auto")

print("显存占用 (GB):", torch.cuda.memory_allocated() / 1e9)
```

记录本机加载后的 `memory_allocated()`，再分别测试目标 Prompt 长度与生成长度。该值受 transformers/bitsandbytes 版本、量化配置、设备映射和 offload 影响，不能从“4-bit”推定固定占用或剩余空间。

# 四、路径 B：llama.cpp / Ollama（GGUF 量化）

```bash
ollama run qwen2.5:7b
```

模型标签并不永久保证某一种 4-bit 格式，实验前应查看实际模型信息并记录量化类型与模型摘要。

# 六、体验 KV Cache 的效果

回顾本部分第 10 章：KV Cache 保存历史 Token 的 Key/Value，避免每生成一个新 Token 都重新计算全部历史。以下继续使用路径 A 已加载的 `model`、`tokenizer` 与 CUDA 环境，对比开启和关闭 KV Cache 的生成速度；它不是可直接套到 Ollama 对象上的代码。

```python
import time

prompt = "请详细介绍一下深度学习的发展历史。"
input_device = model.get_input_embeddings().weight.device
inputs = tokenizer(prompt, return_tensors="pt").to(input_device)


def timed_generate(use_cache):
    # CUDA kernel 异步执行，计时边界必须同步。
    torch.cuda.synchronize()
    start = time.perf_counter()
    with torch.inference_mode():
        output = model.generate(
            **inputs, max_new_tokens=100, use_cache=use_cache, do_sample=False
        )
    torch.cuda.synchronize()
    return output, time.perf_counter() - start


# 两种模式分别短预热，减少首次编译、内存分配等一次性开销。
with torch.inference_mode():
    for cache_mode in (True, False):
        model.generate(
            **inputs, max_new_tokens=8, use_cache=cache_mode, do_sample=False
        )

output_with_cache, time_with_cache = timed_generate(True)
output_no_cache, time_no_cache = timed_generate(False)

print(f"开启 KV Cache 耗时: {time_with_cache:.2f}s")
print(f"关闭 KV Cache 耗时: {time_no_cache:.2f}s")
print(f"速度比: {time_no_cache / time_with_cache:.2f}x")
```

关闭 KV Cache 后，每一步都会重新计算历史 Token 的 K/V；开启后则复用缓存。加速比受 Prompt/输出长度、模型、Attention 实现和硬件影响，应报告本机实测值，不能预设为“数倍”。

# 七、体验 Long Context 的显存代价

KV Cache 不是免费的：上下文越长，缓存占用的显存越多。测试不同长度的 Prompt，观察显存变化：

```python
def tensor_bytes(obj):
    if torch.is_tensor(obj):
        return obj.numel() * obj.element_size()
    if isinstance(obj, (tuple, list)):
        return sum(tensor_bytes(item) for item in obj)
    if isinstance(obj, dict):
        return sum(tensor_bytes(item) for item in obj.values())
    if hasattr(obj, "layers"):
        return sum(
            tensor_bytes(layer.keys) + tensor_bytes(layer.values)
            for layer in obj.layers
        )
    if hasattr(obj, "key_cache") and hasattr(obj, "value_cache"):
        return tensor_bytes(obj.key_cache) + tensor_bytes(obj.value_cache)
    raise TypeError(f"不支持的缓存类型 {type(obj).__name__}；请检查当前版本的 Cache 接口。")


def measure_kv_cache(token_length):
    vocab_size = model.get_input_embeddings().num_embeddings
    dummy_input = torch.randint(
        0, vocab_size, (1, token_length), device=input_device
    )
    with torch.inference_mode():
        outputs = model(dummy_input, use_cache=True)
    cache = outputs.past_key_values
    # 新版 transformers 可能返回 DynamicCache；转成逐层 (K, V) 元组后统计。
    if hasattr(cache, "to_legacy_cache"):
        cache = cache.to_legacy_cache()
    gib = tensor_bytes(cache) / (1024 ** 3)
    del outputs, cache, dummy_input
    return gib


for length in [128, 512, 2048]:
    kv_gib = measure_kv_cache(length)
    print(f"上下文长度 {length}: KV Cache 张量 {kv_gib:.3f} GiB")
# 确认设备余量后再测试更长序列，避免直接 OOM。
```

这里统计的是普通稠密 K/V 张量的**逻辑字节数**（`numel × element_size`），跨设备时会一起求和，并不等于单张 GPU 的物理分配量。示例覆盖常见的逐层 `(K, V)`、`key_cache/value_cache` 或 `layers[].keys/values` 接口；未知类型必须报错，不能把“不认识缓存格式”写成“缓存占用为 0”。量化/滑窗/静态缓存、共享 storage 与额外 scale 等需要专门的计量方法。

还要区分三种显存口径：

- `memory_allocated()` / `max_memory_allocated()`：当前/重置以来峰值的 PyTorch 活跃张量分配，包括权重、KV 与临时张量，**不包括 allocator 仅保留但未使用的空闲块**；
- `memory_reserved()` / `max_memory_reserved()`：PyTorch caching allocator 当前/峰值保留量，包括活跃分配及池内空闲块；
- 设备工具报告的进程占用：还可能包含 CUDA context、非 PyTorch 库等开销，不应与前两者混用。

测单轮峰值需先同步、调用 `torch.cuda.reset_peak_memory_stats()`，运行目标操作后再次同步再读峰值；多卡需逐卡记录。不能把总峰值直接当作 KV 大小。固定层数、KV head 数、head dimension、dtype 和 batch size 时，普通完整上下文缓存才随序列长度近似线性增长。

# 八、（选读）为什么 MoE 更难在小显存单卡部署？

第一部分第 13 章介绍过 MoE 的核心思想：“总参数多、每个 Token 只激活少数专家”。在**所有权重常驻单卡**的常见低延迟部署中，显存主要受总参数量约束，而每 Token 计算量更接近激活参数量；top-k 路由不会自动减少常驻权重。CPU/NVMe offload、专家并行或按需换入可以降低单卡常驻量，但会引入通信或传输开销。因此，MoE 通常比同等激活参数量的 Dense 模型更难在 8GB 单卡低延迟部署，具体占用仍取决于 checkpoint、量化格式和运行时。

如果只是想体会 Router 机制本身（而不需要真的跑一个大模型），可以用几行代码写一个最简化的 MoE 层，在 CPU 上就能运行：

```python
import torch
import torch.nn as nn

class ToyMoE(nn.Module):
    def __init__(self, d_model=8, num_experts=4, top_k=2):
        super().__init__()
        self.experts = nn.ModuleList(
            [nn.Linear(d_model, d_model) for _ in range(num_experts)]
        )
        self.router = nn.Linear(d_model, num_experts)
        self.top_k = top_k

    def forward(self, x):
        router_logits = self.router(x)                         # [batch, experts]
        topk_logits, topk_indices = torch.topk(
            router_logits, self.top_k, dim=-1
        )
        topk_weights = torch.softmax(topk_logits, dim=-1)     # top-k 内重新归一化

        all_outputs = torch.stack(
            [expert(x) for expert in self.experts], dim=1
        )                                                     # [batch, experts, d_model]
        gather_index = topk_indices.unsqueeze(-1).expand(-1, -1, x.shape[-1])
        chosen_outputs = torch.gather(all_outputs, 1, gather_index)
        mixed = (chosen_outputs * topk_weights.unsqueeze(-1)).sum(dim=1)
        return mixed, topk_indices, topk_weights


moe = ToyMoE(top_k=2)
x = torch.randn(1, 8)
output, expert_ids, router_weights = moe(x)
print("选中的专家:", expert_ids.tolist())
print("对应权重:", router_weights.tolist())
```

改变输入 `x`，可以观察 top-k 专家编号与归一化权重如何变化。为让代码短小，上例先计算全部专家再 `gather`；真实稀疏 MoE 内核只调度选中的专家，否则不会获得稀疏计算收益。
