## 一、训练关心吞吐，推理关心延迟与并发

第9章的训练系统追求"用最短时间训练完一个模型"；推理系统面对的是完全不同的场景：**成千上万个用户同时发来长度各不相同的请求，系统需要在可接受的延迟下，同时服务尽可能多的用户**。两者的工程目标几乎是反的：

| | 训练系统 | 推理系统 |
|---|---|---|
| 优化目标 | 吞吐（每小时处理的 Token 数） | 延迟（每个请求多快返回）+ 吞吐（单位时间服务多少用户） |
| 数据 | 固定的大 batch，形状整齐 | 请求长度参差、动态到达 |
| 显存压力 | 参数 + 梯度 + 优化器 + 激活值 | 参数 + **KV Cache**（随并发请求数线性增长） |
| 精度 | BF16/FP32（要训练稳定） | 可以 INT8/INT4 量化（质量损失可接受） |

**显存容量是推理的硬约束，但不是唯一瓶颈**：模型参数基本固定，每个并发请求却会占用随上下文增长的 KV Cache。系统还受算力、显存带宽、卡间通信和请求排队影响。本章围绕一个问题展开：**如何在有限资源与延迟目标下，提高可持续服务的吞吐量？**

## 二、自回归生成的两个阶段与三大延迟指标

LLM 生成回答的过程（第1.1节讲过）分为两个阶段：

1. **Prefill（预填充）**：把用户输入的整个 Prompt 一次性喂给模型，并行计算出所有位置的 KV Cache。这一步计算量大但只需要一次；
2. **Decode（解码）**：逐个生成新的 Token（每步只算最后一个位置，借助 KV Cache 避免重算历史），每步生成一个 Token，直到遇到结束符。

两个阶段的行为完全不同，因此业界用三个指标分开衡量：

| 指标 | 全称 | 含义 | 受什么影响 |
|---|---|---|---|
| **TTFT** | Time To First Token | 从发出请求到收到第一个 Token | Prefill 速度 + 排队时间 + 网络 |
| **TPOT** | Time Per Output Token | 首个输出之后每个 Token 的平均耗时；常用 `(总响应时长 − TTFT) / (输出 Token 数 − 1)`，需输出多于 1 个 Token | Decode、调度与传输；须声明统计口径 |
| **ITL** | Inter-Token Latency | 相邻输出 Token 到达的间隔及其分布 | 调度、内核与流式传输；分块返回时不一定等于单 Token 间隔 |

**为什么小 Batch 的 Decode 常受显存带宽限制？** 回顾第8章的 Roofline 模型：每个请求每步只生成一个 Token，权重复用有限。假设 Dense 7B 的约 14 GB 权重每步都从 HBM 读取一次，有效带宽为 1 TB/s，仅权重读取的理想时间就是约 14 ms；这不是所有模型的普遍下限，还未计入 KV 读取、内核与通信开销。Batch 增大可让一次权重读取服务更多 Token，长上下文又会增加 KV 读取量，瓶颈可能转移。因此，量化可能减少带宽压力，但不能保证固定的延迟收益。

## 三、KV Cache 的显存账本：每个 Token 都保存了什么

KV Cache 避免重复计算历史 Token 的 Key 和 Value，但代价是：**每一层、每个已处理 Token 都要各保存一份 K 和一份 V。** 因此，计算显存时要逐项回答：多少层、多少个 KV Head、每个 Head 多宽、缓存多少 Token、每个元素占多少字节。

单个请求的理论主体占用为：

```math
\text{KV Bytes}
=
2\times L\times T\times H_{kv}\times d_{head}\times b
```

**这个公式的作用**：估算一个请求的 KV Cache 数据本体，不包含内存对齐、分页元数据、临时 Workspace 等额外开销。

- `2`：K 和 V 两组缓存；
- `L`：Transformer 层数；
- `T`：当前已缓存 Token 数；
- `H_kv`：KV Head 数；标准 MHA 中通常等于 Query Head 数，GQA/MQA 中更少；
- `d_head`：每个 Head 的维度；
- `b`：每个元素的字节数，FP16/BF16 通常为 `2`。

以一个简化的 7B 配置为例：`L=32`、标准 MHA、`H_kv×d_head=d_model=4096`、FP16。每个 Token 的缓存是：

```text
2 × 32 × 4096 × 2 Byte = 524,288 Byte ≈ 0.5 MiB
```

由此得到：

| 场景 | 计算 | 理论 KV Cache |
|---|---:|---:|
| 单请求，4K Token | `0.5 MiB × 4096` | 约 `2 GiB` |
| 单请求，128K Token | `0.5 MiB × 131072` | 约 `64 GiB` |
| 100 请求，各 4K Token | `100 × 2 GiB` | 约 `200 GiB` |
| 100 请求，各 32K Token | `100 × 16 GiB` | 约 `1.56 TiB` |

这些数字以本例的层数、标准 MHA 与 FP16 为前提；仅相乘“并发数 × Token 数”还得不到字节量，必须乘上每个 Token 在所有层的 K/V 开销。若模型采用 8 个 KV Head、32 个 Query Head 的 GQA，在其他条件相同时，主体占用约缩小为 MHA 的 `8/32=1/4`；量化 KV 还会进一步改变每元素字节数。

总并发缓存近似等于各请求当前 `T` 的占用之和，而不是简单按模型最大上下文为所有请求分配。PagedAttention 主要减少预留和碎片浪费，GQA/MQA/MLA 与 KV 量化则直接减少每个 Token 需要保存的数据量。

## 四、Continuous Batching：在迭代边界补入新请求

先区分三种方式：

- **逐个排队**：每次只处理一个请求，难以利用跨请求的权重复用；
- **静态批处理（Static Batching）**：一批请求一起开始，整批结束才接下一批。短请求可以先返回，但它释放的槽位不能马上接新请求；
- **Continuous Batching（连续批处理）**：在调度迭代边界重新组成 Batch，移除已完成请求，并在资源预算允许时接纳等待请求。它不是任意时刻打断正在运行的 GPU 内核，也不等同于所有形式的“动态组批”。

看一个仅含 Decode 的玩具时间表：最多同时处理 2 个请求，A/B 在第 1 步到达，分别需要 1/4 步；C/D 在第 2 步开始前到达，各需要 1 步。`B2` 表示 B 的第 2 个输出 Token，`—` 表示空槽。

| 时间步 | 静态批处理：槽 1 / 槽 2 | 连续批处理：槽 1 / 槽 2 |
|---|---|---|
| 1 | A1 / B1 | A1 / B1 |
| 2 | — / B2（C、D 等待） | C1 / B2 |
| 3 | — / B3（C、D 等待） | D1 / B3 |
| 4 | — / B4（C、D 等待） | — / B4 |
| 5 | C1 / D1 | 全部完成 |

关键动作不是“大家一起开始”，而是 **B 尚未结束时，C/D 就利用释放的槽位推进**。此表假设每步等长，省略了新请求 Prefill、内核和调度开销；真实系统还要决定 Prefill 与 Decode 如何共享 Token 预算，不能把表中的步数比当作实测加速比。

收益取决于到达模式、长度分布、Batch 上限、模型和硬件。没有等待请求、受显存或算力限制时，连续批处理也不能保证 GPU 满载。10.1 节会用真实服务观察不同到达方式下的请求重叠与吞吐，而不是预设固定倍数。

## 五、PagedAttention：像操作系统管理内存一样管理 KV Cache

Continuous Batching 带来一个新问题：**不同请求的 KV Cache 长度实时变化，如何高效管理这些大小不一、持续增长的显存块？**

朴素的做法是"按最大可能长度给每个请求预分配一整块连续显存"——但一个请求实际可能只用 10% 的分配空间，造成巨大浪费（**显存碎片 + 内部碎片**）；更糟的是，请求完成前这块显存不能被其它请求使用，而新请求又不断到来。

vLLM 提出的 **PagedAttention** 借鉴了操作系统**分页内存管理**的思想：

- 把 KV Cache 切成固定大小的**页（Page）**（如每页 16 个 Token 的 KV）；
- 每个请求按需**按页分配**，用一张**页表**记录"逻辑页 → 物理页"的映射；
- 请求增长时分配新页，完成时释放旧页——**碎片化显存被重新利用**，不同请求甚至可以共享相同的页（Prefix Caching 的基础）。

用每块 4 个 Token 的玩具例子看页表：请求 X 已缓存 6 个 Token，请求 Y 已缓存 3 个 Token；物理块编号不必连续。

| 请求 | 逻辑块 | 物理块 | 已存的 Token 位置 | 块内空位 |
|---|---:|---:|---|---:|
| X | 0 | 7 | X 的 0–3 | 0 |
| X | 1 | 2 | X 的 4–5 | 2 |
| Y | 0 | 5 | Y 的 0–2 | 1 |

X 新增位置 6 时只填物理块 2 的空位；增长到位置 8 时才申请另一个块，并把“逻辑块 2 → 新物理块”加入页表。X 完成后，未被共享引用的块 7、2 等可以回收。读 Attention 时依页表定位 K/V，不要求整段缓存物理连续。

此例为 9 个 Token 分配了 12 个槽位，尾块仍有 3 个空位。**分页不压缩每个 Token 的 K/V，也不会把 200 GiB 的有效缓存凭空变成几 GiB**；它减少最大长度预留和外部碎片浪费。相同前缀可在实现允许时共享物理块，但需要前缀一致性校验、引用计数，修改共享块时还需写时复制等机制。

实际显存利用率取决于块大小、请求长度和实现，不能把某个基准中的百分比当作普遍保证。这是推理引擎借鉴操作系统的典型案例；第三部分还会讨论 Agent 图执行中的类似工程借鉴。

## 六、其它推理加速手段

| 技术 | 核心思想 | 收益 | 代价 |
|---|---|---|---|
| 量化（INT8/INT4/FP8） | 分别降低权重、激活或 KV 的存储精度 | 降低对应数据体积；是否加速取决于硬件、反量化与内核 | 有元数据开销，质量变化须按任务评估，并非必然“轻微” |
| 投机解码（Speculative Decoding） | 草稿模型或辅助预测器提出多个 Token，目标模型验证 | 接受率足够高时减少串行目标模型步数，不保证固定倍数 | 草稿与验证有额外开销；正确的接受/校正算法才能保持目标采样分布 |
| Prefix Caching | 复用完全匹配的前缀 KV | 命中时减少 Prefill 重算，不直接加快所有 Decode | 依赖命中率、缓存预算及正确的共享管理 |
| 张量并行推理 | 将权重等分片到多卡，KV 的分摊还依赖结构与实现 | 扩大可容纳模型或请求规模，吞吐与延迟均需实测 | 卡间通信可能抵消收益；高速互联有利但不是一律要求 NVLink |
| GQA / MLA | 多个 Query Head 共享 KV，或使用压缩的潜在缓存 | 减少每 Token 缓存，具体比例由结构和实现决定 | 通常需模型训练时支持，不能任意修改已训练结构 |

**分层看这些优化**：GQA/MLA 属于模型结构，量化涉及表示格式与计算内核，投机解码属于生成算法，Continuous Batching/Paging 属于调度与缓存管理。它们相互配合，但不是同一层的替代方案。现代推理引擎还需要服务层（兼容 API、流式输出、限流与取消等）。

## 七、主流推理引擎的定位

| 引擎 | 出品方 | 特点 |
|---|---|---|
| vLLM | 开源社区，起源于加州伯克利 | 以 PagedAttention 和高吞吐服务为代表，支持多种模型与服务接口 |
| TensorRT-LLM | NVIDIA | 围绕 NVIDIA GPU 的内核、量化与多卡推理优化 |
| SGLang | 开源社区 | 重视前缀复用、结构化生成与复杂服务负载 |
| TGI（Text Generation Inference） | Hugging Face | HF 生态中的推理服务实现；使用前检查当前维护状态与支持矩阵 |
| LMDeploy | 上海 AI Lab 等 | 提供量化、推理与服务工具链，支持范围按版本核对 |

这些引擎常组合连续批处理、分页或其它缓存管理、量化与流式输出，但模型支持、调度策略、硬件后端和服务行为并不相同。理解共同机制有助于迁移，**实际迁移不只是换 API**，还要校验输出质量、错误处理和性能。

例如 TensorRT-LLM 的 **In-flight Batching** 与连续批处理思想相近，**Paged KV Cache** 也采用分页缓存管理；FP8 权重/激活与 FP8 KV 则是需要分别核对的配置能力。能否启用、质量影响和吞吐收益取决于模型、设备、版本与负载，不能把硬件支持等同于自动获得加速。

## 本章总结

本章我们理解了：

- 训练与推理都关心资源效率，但在线推理还必须满足排队与尾延迟目标。
- Prefill/Decode 的瓶颈随 Batch、上下文和硬件改变；TTFT、TPOT、ITL 分别描述不同体验。
- 普通 KV 主体占用为 `2 × L × T × H_kv × d_head × b`，总并发占用对各请求求和，不能漏掉层数、头数、dtype 与 K/V 两份。
- Continuous Batching 在迭代边界补入新请求，PagedAttention 用页表按需管理缓存；分页不等于压缩每 Token 的 K/V。
- 量化、投机解码、前缀复用和多卡并行各有条件与代价，吞吐倍数和显存利用率必须在具体工作负载下测量。
- 推理引擎组合模型结构、生成算法、内核、调度与服务能力，理解共同机制有助于判断各实现的取舍。

> **KV Cache 解决"一个请求内部"的重复计算，Continuous Batching 解决"多个请求之间"的资源利用率，PagedAttention 解决"KV Cache 怎么放得下"——三个问题层层递进，构成了推理工程的完整主线。**
