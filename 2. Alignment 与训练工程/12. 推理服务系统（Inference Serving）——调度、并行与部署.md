# 12. 推理服务系统（Inference Serving）——调度、并行与部署

> **读之前**：读完第 11 章，理解预填充/解码、KV Cache、连续批处理和分页注意力。本章不再重复这些机制，只讨论“把它们组成一个可运营的服务”需要什么。
>
> **读完你能做到**：说清 goodput、p99 和 SLA 的含义；理解调度、抢占、公平性和准入控制；区分推理侧的 TP/PP/EP；知道 chunked prefill、PD 分离、前缀缓存、投机解码和长上下文各自的代价；能判断一个推理引擎的取舍。

第 11 章回答的是“一次生成怎么算得快、显存怎么放得下”。本章回答另一个问题：

> **很多用户、长短不一的请求、有限的 GPU 和明确的延迟目标同时存在时，系统怎样稳定地服务？**

单请求的 TTFT/TPOT 好看，不等于服务好。生产系统还要处理排队、尾延迟、多租户、故障和成本。

---

## 一、服务指标

第 11 章已经定义了 TTFT、TPOT 和 ITL。服务层还要补三个视角：

| 指标 | 回答什么 | 为什么重要 |
|---|---|---|
| **goodput** | 单位时间内满足 SLA 的请求数或词元数 | 吞吐高但超时率高，不算有效服务 |
| **p95 / p99 延迟** | 慢请求有多慢 | 平均值会掩盖长尾，用户感知的是尾延迟 |
| **吞吐-延迟曲线** | 提高并发后，延迟如何变化 | 只报一个“最大吞吐”没有意义 |

一个系统可能平均 TTFT 只有 200 ms，但 p99 是 3 s：大多数请求很快，少数请求排队很久。长提示、长回答、缓存未命中、调度不公平都会把尾延迟拉高。

**SLA（Service Level Agreement，服务等级协议）** 是把这些指标变成约束，例如“p95 TTFT < 1 s，p99 端到端 < 30 s”。调度器的目标不是让某个指标单独最优，而是在 SLA 内最大化 goodput。

---

## 二、调度与 SLA

连续批处理决定“每个迭代混哪些请求”，调度器还要决定优先级和资源分配。

### 常见调度目标

| 目标 | 做法 | 风险 |
|---|---|---|
| 先来先服务（FCFS） | 按到达顺序排队 | 长请求阻塞短请求 |
| 最短剩余时间优先 | 优先短回答 | 长请求可能饥饿 |
| 优先级队列 | 高优请求先调度 | 低优请求可能长期等待 |
| 公平调度 | 按租户/用户分配配额 | 实现复杂，可能牺牲总吞吐 |
| 截止时间优先 | 接近 SLA 截止时间的请求优先 | 需要准确估计剩余时间 |

生产系统通常组合使用：**按租户配额保证公平，再按优先级和截止时间排序，最后用连续批处理填满每个迭代。**

### 准入控制

不是所有请求都应该立刻接收。准入控制会在排队前检查：

- 当前 KV Cache 预算是否足够；
- 请求长度是否超过模型上下文；
- 租户是否超过配额或速率限制；
- 当前队列的预计等待时间是否已经超过 SLA。

直接接收再排队，会把“拒绝”变成“超时”，既浪费算力，也让指标更难看。

### 抢占策略

当新请求或长上下文需要更多 KV 空间，而 GPU 已经装满，调度器有三种选择：

| 策略 | 做法 | 代价 |
|---|---|---|
| 重算（Recompute） | 丢弃部分 KV，之后重新预填充 | 额外算力，TTFT/TPOT 抖动 |
| 换出（Swap） | 把 KV 换到 CPU/SSD | PCIe 带宽和换入延迟 |
| 丢弃（Drop） | 终止低优或超时请求 | 用户体验受损，需要明确错误 |

抢占不是“免费腾显存”。重算会增加算力，换出会增加带宽，丢弃会损失请求；选择哪一种取决于 SLA、请求价值和缓存命中率。

### 公平性与饥饿

只追求总吞吐，可能让长请求或低优租户长期得不到服务。公平调度需要给每个租户/请求类型保留最低配额，并限制单租户占用比例。否则一个批量任务可以把在线请求全部挤到队尾。

## 三、推理并行：TP、PP 与 EP

单卡装不下模型，或单卡算力不够时，需要多卡并行。训练章的 DP/TP/PP/ZeRO 不能直接照搬，因为推理没有梯度和优化器状态，但有 KV Cache 和严格的延迟目标。

| 方式 | 切什么 | 优点 | 代价 |
|---|---|---|---|
| **张量并行（Tensor Parallel, TP）** | 切隐藏维/注意力头/FFN | 单层计算分摊到多卡 | 每层都要 all-reduce，通信频繁 |
| **流水线并行（Pipeline Parallel, PP）** | 切层 | 适合跨节点放大模型 | 流水线气泡，首尾卡利用率低 |
| **专家并行（Expert Parallel, EP）** | 切 MoE 专家 | 容纳大量专家 | all-to-all 路由，负载不均衡 |

**TP 是低延迟推理最常用的方式**：同一层的矩阵乘切到多卡，每层结束做一次通信。卡间互联越好，TP 越划算；跨节点 TP 常被通信拖慢。

**PP 适合“模型很深、跨节点”的场景**：每张卡持有连续几层，但请求要依次经过各段，首段和尾段容易成为瓶颈。推理的 PP 还要处理 KV Cache 的分段存放。

**EP 只适用于 MoE**：每个词元只路由到少数专家，但路由结果可能落在其他卡上，需要 all-to-all。专家负载不均衡时，最忙的专家决定整批延迟。

还要区分**复制（Replication）** 和**分片（Sharding）**：

- 复制：每张卡放完整模型，适合模型能单卡放下、追求吞吐；
- 分片：多卡合放一个模型，适合模型太大或单卡算力不足。

---

## 四、Chunked Prefill：长提示分块

预填充一次处理整个提示，长提示会长时间占用算力，让同一批里的解码请求等待。**chunked prefill** 把提示切成若干块，分多个迭代完成；调度器可以把 decode 请求和新到的 prefill 块混在同一批里。

- 收益：降低 decode 请求被长 prefill 阻塞的尾延迟，提升混合负载下的平滑度；
- 代价：长提示自己的 TTFT 可能变长，调度和 KV 管理更复杂；
- 不是“所有请求都快”：如果负载全是长提示、没有 decode 请求可混，收益有限。

它解决的是**阶段之间的干扰**，不是“让预填充本身变快”。

---

## 五、Prefill / Decode 分离：把两个阶段放到不同资源池

Prefill 是计算密集，Decode 是访存密集，二者对 GPU、batch 和并行策略的要求不同。**分离式部署（disaggregated prefill/decode）** 用两组 worker：

1. Prefill worker 算完提示的 KV Cache；
2. 把 KV 传给 Decode worker；
3. Decode worker 持续自回归生成。

好处是各自按瓶颈扩缩容，避免长提示拖慢 decode；代价是要传 KV（带宽、延迟、序列化），还要处理故障和调度。提示短、并发低时，分离的通信开销可能不值得。

分离式部署不是“默认更先进”：它适合 prefill 与 decode 比例失衡、且集群网络足够好的场景；小规模服务通常先把连续批处理和分页做好。

## 六、KV Cache 的服务层管理

第 11 章讲了 KV 的物理结构和分页。服务层还要管理它的生命周期。

### 前缀缓存

**前缀缓存（Prefix Caching）** 复用完全匹配的前缀 KV。多轮对话、固定 system prompt、RAG 的公共文档都可能有大量重复前缀。

命中时省掉预填充重算，但需要：

- 前缀匹配与一致性校验；
- 引用计数与共享页；
- 修改共享页时的写时复制（Copy-on-Write）；
- 缓存预算和淘汰策略。

前缀缓存省的是**预填充算力**，不是 KV 的物理字节数；命中率低时，维护缓存的元数据反而增加开销。

### 分层与淘汰

KV 不必全部常驻显存。分层缓存把不活跃请求的 KV 换出到 CPU DRAM 或 SSD：

- 按访问频率、剩余预算和 SLA 决定哪些块留在 GPU；
- 换入换出受 PCIe/NVLink 带宽限制；
- 换出后的首次访问会变慢。

淘汰策略常见的有 LRU、LFU、按租户配额和按剩余时间。没有一种策略适合所有负载：长对话需要保留会话前缀，批量任务可能更看重总吞吐。

### 显存预算

服务层要维护一张实时账本：

```text
可用 KV = GPU 显存
        - 权重
        - 激活/临时缓冲
        - 预留安全余量
```

新请求能否准入，取决于这张账本，而不是“当前 batch 还没满”。分页减少的是预留和碎片浪费，不增加总容量。

## 七、多 LoRA 与约束解码

**多 LoRA 服务** 让一个基座模型同时服务多个适配器：请求带上 adapter id，调度器按 adapter 组批，内核在共享基座上切换增量权重。它省的是“每个任务复制一份完整模型”的显存，代价是 adapter 管理、批内切换和内核支持。

**约束解码 / 结构化输出**（guided decoding）在每一步用语法、JSON Schema 或正则限制候选词元，保证输出可解析。它降低格式失败率，但不保证内容正确；约束太强也可能让模型输出变得生硬或漏掉信息。约束解码还需要额外的语法状态和候选过滤开销，高并发时要测量它对 TPOT 的影响。

---

## 八、投机解码：草稿、验证与接受率

投机解码用一个小草稿模型先猜几个词元，再由目标模型并行验证：

1. 草稿模型对当前前缀生成 `k` 个候选词元；
2. 目标模型一次前向，计算这些位置的概率；
3. 按接受规则保留前缀，遇到拒绝就从目标分布重新采样；
4. 接受多个词元时，减少目标模型的串行步数。

设草稿分布为 `q`，目标分布为 `p`，某个候选词元的接受概率通常写成：

$$
\min\left(1,\frac{p(x)}{q(x)}\right)
$$

- $x$：当前候选词元；
- $p(x)$：目标模型给 $x$ 的概率；
- $q(x)$：草稿模型给 $x$ 的概率；
- 比值越高，越容易接受；$p(x)\ge q(x)$ 时接受概率为 1。

接受率越高，一次验证能确认的词元越多；接受率低时，草稿和验证都是额外开销。

常见变体：

- **Medusa**：在目标模型上挂多个预测头，避免独立草稿模型；
- **EAGLE**：用轻量草稿模型在特征层预测，提高接受率；
- **树式投机**：一次验证多条候选分支，用树注意力并行处理。

收益取决于草稿质量、任务分布、batch 大小和内核实现，不存在固定加速倍数。投机解码对延迟敏感、batch 小的场景更友好；batch 已经很大时，目标模型算力饱和，收益会下降。

## 九、长上下文推理

长上下文会把 KV Cache 线性放大，并拉长预填充时间。服务层常见手段：

| 手段 | 思路 | 代价 |
|---|---|---|
| RoPE 外推/缩放 | 扩展可处理的位置范围 | 超出训练分布后质量下降 |
| 滑动窗口注意力 | 只保留最近窗口 | 远处信息丢失 |
| Attention Sinks | 保留开头少量“锚点”词元 | 任务相关，不是通用解 |
| KV 量化 | 降低每个元素字节数 | 误差累积，长上下文更明显 |
| KV 淘汰/压缩 | 丢弃低价值或合并相似 KV | 可能丢关键信息 |
| 前缀/上下文缓存 | 复用公共前缀 | 依赖命中率和一致性 |

长上下文不是“窗口开得越大越好”。更长的上下文会增加预填充成本、KV 显存和 attention 计算；如果任务只需要局部信息，滑动窗口或检索增强可能更便宜。

## 十、引擎与运维

| 引擎 | 出品方 | 特点 |
|---|---|---|
| vLLM | 开源社区，起源于伯克利 | PagedAttention、连续批处理、高吞吐服务 |
| TensorRT-LLM | NVIDIA | NVIDIA GPU 内核、量化、多卡优化 |
| SGLang | 开源社区 | 前缀复用、结构化生成、复杂负载 |
| TGI | HuggingFace | HF 生态的推理服务实现；使用前检查维护状态 |
| LMDeploy | 上海 AI Lab 等 | 量化、推理与服务工具链 |

这些引擎常组合连续批处理、分页缓存、量化和流式输出，但模型支持、调度策略、硬件后端并不相同。理解共同机制有助于迁移，**实际迁移不只是换 API**，还要校验输出质量、错误处理和性能。

服务层还要处理：

- **自动扩缩容**：按队列长度、KV 利用率、TTFT/TPOT 扩容，而不是只看 CPU；
- **限流与配额**：按租户/API key 限制并发和词元速率；
- **重试与超时**：重试要幂等，避免重复计费或重复工具调用；
- **可观测性**：记录排队时间、TTFT、TPOT、ITL、KV 命中率、抢占次数和错误码；
- **成本**：每百万 token 成本、GPU 利用率、空转和扩缩容滞后；
- **发布**：灰度、回滚、模型版本与 tokenizer 版本绑定。

推理服务的很多故障不是“模型算错了”，而是排队、超时、重试风暴、缓存污染和版本不一致。

## 十一、请求在服务系统中的生命周期

| 阶段 | 输入 | 操作 | 产物 |
|---|---|---|---|
| 1. 准入与排队 | 请求、采样参数、租户配额 | 分词、长度与配额检查、限流 | 待调度请求，排队时延计入 TTFT |
| 2. 组批 | 等待队列、空闲槽位、剩余 KV 预算 | 连续批处理决定本迭代混哪些 prefill / decode | 调度计划（迭代边界可重组） |
| 3. 预填充 | 提示词元 | 一次或分块前向 | 首词元、各层 KV 页、页表项 |
| 4. 解码 | 已生成词元与已分配页 | 逐步前向、追加 K/V、采样 | 每步词元，以及 TPOT / ITL |
| 5. 结束与回收 | 结束符、长度上限或取消 | 归还物理页、写指标与日志 | 完整回答、显存回到可用池 |

**完成判据**：请求以结束符、长度上限或取消三种方式之一终止，其占用的物理页按引用计数回收，TTFT、TPOT、ITL、排队时间和 KV 命中率随请求一起记录。**失败边界**：显存装不下新请求时，系统只能排队、抢占或拒绝；分页减少的是预留与碎片浪费，不增加总容量。

## 本章小结

- 服务层看 goodput 和 p95/p99，而不只看平均 TTFT/TPOT。
- 调度要同时处理优先级、公平性、准入和抢占；抢占的代价是重算、换出或丢弃。
- 推理并行分 TP、PP、EP：TP 降单层延迟但通信频繁，PP 适合跨节点，EP 只用于 MoE。
- chunked prefill 降低长提示对 decode 的干扰，PD 分离按阶段扩缩容，两者都有通信或调度代价。
- 前缀缓存、分层和淘汰管理 KV 生命周期；分页不增加总容量。
- 投机解码的收益由接受率决定；长上下文要同时看质量、显存和预填充成本。
- 服务运维包括扩缩容、限流、重试、可观测性和成本，不是“模型部署完就结束”。

> **一句话记住本章**：推理机制决定“一次生成多快”，服务系统决定“很多请求下能否稳定、公平、可负担地完成”。
