# 13.4 量化、KV Cache 与本地推理加速实战

> **本节目标**：这是第13章篇幅最大、也最贴近真实工程部署的一节。我们将把一个 **7B 大模型**（远超"塞进 8GB 显存"的直觉认知）通过量化压缩到 8GB 显存能够承受的大小，分别用 **Hugging Face 生态**（transformers + bitsandbytes）和 **llama.cpp / Ollama**（GGUF 量化）两条路径完成本地部署，并亲手对比 KV Cache 开关、不同上下文长度对推理速度的影响。
>
> **硬件要求**：这是全书对硬件挑战最大的一节，但依然被严格限制在 **8GB 显存**以内——这正是"量化"存在的意义：用可控的精度损失，换取能在普通消费级显卡上运行原本装不下的大模型。

---

# 一、为什么 7B 模型原本装不进 8GB？

`Qwen2.5-7B` 有 76 亿参数。如果用 FP16（每个参数占 2 字节）存储，仅权重就需要 `76亿 × 2字节 ≈ 15GB`，还没算推理时的中间激活值和 KV Cache——**远超 8GB 显存**。这正是第13章 MoE 一节提到的"参数越多、计算/存储代价越大"问题的另一面：**存储代价同样会随参数线性增长**。

---

# 二、量化的核心思想

量化（Quantization）就是：**用更少的比特数存储每一个参数**。FP16 用 16 位存一个数字，4-bit 量化只用 4 位——存储空间直接降到 `1/4`。`Qwen2.5-7B` 用 4-bit 量化后，权重占用降到约 `76亿 × 0.5字节 ≈ 4~5GB`，**终于能塞进 8GB 显存**，还留有 KV Cache 和激活值的空间。

代价是什么？精度损失。4-bit 量化会让每个参数的数值变得不那么精确，因此模型输出质量会有轻微下降——但对大多数任务，这个损失通常在可接受范围内，这也是"量化"能在消费级硬件上大规模普及的原因。

# 三、路径 A：Hugging Face 生态（bitsandbytes 4-bit 量化）

```bash
pip install torch transformers accelerate bitsandbytes
```

```python
import torch
import time
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

model_name = "Qwen/Qwen2.5-7B-Instruct"
quant_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, quantization_config=quant_config, device_map="auto")

print("显存占用 (GB):", torch.cuda.memory_allocated() / 1e9)
```

在 8GB 显卡上，你应该能看到显存占用大约在 5~6GB，还留有余量。

# 四、路径 B：llama.cpp / Ollama（GGUF 量化）

`llama.cpp` 是专门为本地推理设计的 C++ 推理引擎，配合 GGUF 格式的量化模型，通常比直接用 transformers 推理更快、显存占用更低。最简单的方式是通过 **Ollama**（对 llama.cpp 的友好封装）：

```bash
# 安装 Ollama（以 macOS/Linux 为例，Windows 请到官网下载安装包）
curl -fsSL https://ollama.com/install.sh | sh

# 拉取并运行 4-bit 量化的 Qwen2.5-7B（Ollama 会自动下载 GGUF 格式）
ollama run qwen2.5:7b
```

也可以直接调用 Python API，方便和前面章节的实验放在同一个脚本里对比：

```bash
pip install ollama
```

```python
import ollama
import time

start = time.time()
response = ollama.generate(model="qwen2.5:7b", prompt="用一句话介绍 Transformer。")
elapsed = time.time() - start

print(response["response"])
print(f"耗时: {elapsed:.2f}s")
```

Ollama 底层直接使用 GGUF 的 4-bit 量化权重（约 4.5GB），加上运行时开销，通常也能稳定控制在 8GB 显存以内。

# 五、两条路径的对比

| | Hugging Face（bitsandbytes） | llama.cpp / Ollama（GGUF） |
|---|---|---|
| 易用性 | Python 代码直接调用，适合和训练/微调代码放一起 | 命令行/简单 API，部署更简单 |
| 推理速度 | 中等 | 通常更快（专门为推理优化过的算子） |
| 显存占用 | 4-bit 约 5~6GB | 4-bit 约 4.5~5.5GB，通常更省 |
| 适合场景 | 研究、实验、需要和训练流程集成 | 真实产品部署、边缘设备、纯推理服务 |

# 六、体验 KV Cache 的效果

回顾第13章：KV Cache 保存历史 Token 的 Key/Value，避免每生成一个新 Token 都重新计算全部历史。用 `transformers` 直接对比开启和关闭 KV Cache 的生成速度：

```python
import time

prompt = "请详细介绍一下深度学习的发展历史。"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

start = time.time()
output_with_cache = model.generate(**inputs, max_new_tokens=200, use_cache=True, do_sample=False)
time_with_cache = time.time() - start

start = time.time()
output_no_cache = model.generate(**inputs, max_new_tokens=200, use_cache=False, do_sample=False)
time_no_cache = time.time() - start

print(f"开启 KV Cache 耗时: {time_with_cache:.2f}s")
print(f"关闭 KV Cache 耗时: {time_no_cache:.2f}s")
print(f"速度提升: {time_no_cache / time_with_cache:.2f}x")
```

关闭 KV Cache 后，模型每生成一个新 Token 都要把之前所有 Token 重新算一遍 Attention，随着生成长度增加，这个差距会越来越明显——你通常会观察到 **开启 KV Cache 后速度提升数倍**，这正是第13章讲的核心结论。

# 七、体验 Long Context 的显存代价

KV Cache 不是免费的：上下文越长，缓存占用的显存越多。测试不同长度的 Prompt，观察显存变化：

```python
def measure_memory_for_length(token_length):
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()
    dummy_input = torch.randint(0, tokenizer.vocab_size, (1, token_length)).to(model.device)
    with torch.no_grad():
        model(dummy_input, use_cache=True)
    return torch.cuda.max_memory_allocated() / 1e9

for length in [128, 512, 2048, 8192]:
    mem = measure_memory_for_length(length)
    print(f"上下文长度 {length}: 显存占用 {mem:.2f} GB")
```

你会看到显存占用随上下文长度增长——这正是第13章讲的"Long Context 面临的新挑战"，也是为什么 128K、1M 级别的超长上下文需要额外的工程优化（Paged Attention、KV Compression 等）才能落地。

# 八、（选读）为什么 MoE 模型在 8GB 显存上特别难跑？

第13章讲过 MoE 的核心思想是"参数很多，但每次只激活少数专家"。问题在于：**即使只激活 2 个专家，模型仍然需要把全部专家的权重都加载到显存里**（因为不知道下一个 Token 会路由到哪个专家），因此 MoE 模型的**显存占用取决于总参数量，而不是激活参数量**。例如 `Qwen1.5-MoE-A2.7B` 总参数约 143 亿（激活参数只有 27 亿），即使 4-bit 量化，权重也需要约 7~8GB，几乎耗尽 8GB 显存的全部空间，几乎没有余量留给 KV Cache——这也是为什么消费级显卡上，MoE 大模型的本地部署比同等"激活参数量"的 Dense 模型更困难。

如果只是想体会 Router 机制本身（而不需要真的跑一个大模型），可以用几行代码写一个最简化的 MoE 层，在 CPU 上就能运行：

```python
import torch
import torch.nn as nn

class ToyMoE(nn.Module):
    def __init__(self, d_model=8, num_experts=4, top_k=1):
        super().__init__()
        self.experts = nn.ModuleList([nn.Linear(d_model, d_model) for _ in range(num_experts)])
        self.router = nn.Linear(d_model, num_experts)
        self.top_k = top_k

    def forward(self, x):
        scores = self.router(x)
        topk = torch.topk(scores, self.top_k, dim=-1)
        chosen_expert = topk.indices[0, 0].item()
        return self.experts[chosen_expert](x), chosen_expert

moe = ToyMoE()
x = torch.randn(1, 8)
output, expert_id = moe(x)
print(f"这次 Token 被路由到了 Expert {expert_id}")
```

多次运行，换不同的输入 `x`，你会看到不同输入被路由到不同的 Expert——这就是 Router 机制最朴素的样子，不需要任何显存压力就能理解它的原理。

# 九、显存与速度参考总结

| 配置 | 显存占用 | 说明 |
|---|---|---|
| Qwen2.5-7B FP16（原始） | ~15GB | 8GB 显卡无法加载 |
| Qwen2.5-7B + bitsandbytes 4-bit | ~5~6GB | 8GB 显卡可运行 |
| Qwen2.5-7B GGUF Q4_K_M（llama.cpp/Ollama） | ~4.5~5.5GB | 8GB 显卡可运行，通常更快 |
| 关闭 KV Cache | 显存略降，但速度大幅下降 | 不推荐日常使用，仅用于本节对比实验 |
| Qwen1.5-MoE-A2.7B 4-bit | ~7~8GB | 8GB 显存下几乎没有余量 |
