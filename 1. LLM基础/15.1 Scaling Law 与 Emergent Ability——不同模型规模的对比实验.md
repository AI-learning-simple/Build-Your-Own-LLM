# 15.1 规模定律（Scaling Law）与涌现能力（Emergent Ability）——不同模型规模的对比实验

> **硬件要求**：需 GPU——要加载 0.5B～7B 的多个模型做对比，建议 8GB+ 显存；无 GPU 可用云 GPU（见前言 P0.3）
>
> **本节目标**：用同一模型家族的 0.5B / 1.5B / 3B 指令模型做一次**定性规模对比**，练习控制提示词（Prompt）、解码方式和评分标准。本实验不能据此证明规模定律（Scaling Law），也不能用一两道题判定真正的涌现能力（Emergent Ability）；严格结论需要统一训练设置、大规模评测和连续指标。
>
> **硬件说明**：示例使用 4-bit 量化减少显存，但 `bitsandbytes` 对 CUDA、操作系统和显卡有兼容要求。实际占用随库版本、量化后端和运行时缓存变化，不保证三个模型能在 8GB 显存中同时常驻。显存不足时请逐个加载模型；量化的原理与显存估算详见第二部分 10.2 节。

# 一、环境准备

```bash
pip install torch transformers accelerate bitsandbytes
```

`bitsandbytes` 是本节用到的量化库，让我们能用更小的显存加载模型。其原理是**用更低的数值精度（如 4-bit）表示权重**，从而大幅压缩显存占用——本节先直接使用，完整的量化原理、两条量化路径对比与显存测量方法见**第二部分 10.2 节**。

# 二、批量加载三个不同规模的模型

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig

quant_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)

model_names = [
    "Qwen/Qwen2.5-0.5B-Instruct",
    "Qwen/Qwen2.5-1.5B-Instruct",
    "Qwen/Qwen2.5-3B-Instruct",
]

models = {}
tokenizers = {}
for name in model_names:
    tokenizers[name] = AutoTokenizer.from_pretrained(name)
    models[name] = AutoModelForCausalLM.from_pretrained(name, quantization_config=quant_config, device_map="auto")

print("三个模型全部加载完成")
```

---

# 三、设计一个能体现规模差异的任务

Scaling Law 的效果在简单任务上不容易看出来（0.5B 模型也能回答"中国的首都是哪里"），需要选一个**稍微复杂、需要多步推理**的问题，才能看出规模的差异：

```python
prompt = "小明有15个苹果，他把其中的3/5送给了小红，又买了7个，请问小明现在有多少个苹果？请说明计算过程。"

def ask(model_name, prompt):
    tok = tokenizers[model_name]
    model = models[model_name]
    messages = [{"role": "user", "content": prompt}]
    text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tok(text, return_tensors="pt").to(model.device)
    output = model.generate(**inputs, max_new_tokens=200, do_sample=False)
    return tok.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

for name in model_names:
    print(f"\n========== {name} ==========")
    print(ask(name, prompt))
```

---

# 四、观察结果：Scaling Law 的直观体现

正确答案是：`15 × 3/5 = 9`，送出 9 个剩 `15 - 9 = 6`，再买 7 个，`6 + 7 = 13`。运行上面的代码，你通常会观察到：

- **0.5B**：可能算错分数（例如把 3/5 算成 0.5），或者步骤混乱、跳步；
- **1.5B**：大概率能算对分数，但偶尔在多步累加时出错；
- **3B**：通常能完整、正确地写出每一步，并得到正确答案。

如果较大模型在多道题上表现更稳定，这与“规模增加通常提升能力”的经验趋势一致。但这些模型的训练数据、训练步数和后训练细节未必完全相同，因此不能把差异只归因于参数量，更不能用单题结果验证 Scaling Law。

---

# 五、体验 Emergent Ability：换一个更难的任务

再换一个需要"组合多种能力"的任务，例如简单的代码 + 逻辑推理：

```python
prompt2 = "写一个 Python 函数，判断一个字符串是否是回文串，并解释为什么你的实现是正确的。"

for name in model_names:
    print(f"\n========== {name} ==========")
    print(ask(name, prompt2))
```

你可能观察到某个规模开始完整满足“代码正确 + 解释充分”两项要求。但二元的“完成/未完成”评分会把连续能力变化显示成突然跃迁，这可能是真正的能力变化，也可能只是评测阈值造成的视觉效果。因此这里只能记录现象，不能据此断言出现了 Emergent Ability。

# 六、给这个观察打个分（可选，量化对比）

如果想更严谨地对比，可以设计 5~10 道类似难度的题目，人工打分（0~1），画出"参数规模 vs 平均得分"的曲线：

```python
import matplotlib.pyplot as plt

# 示例分数，实际使用时请替换成你自己测试打出的真实分数
scores = {"0.5B": 0.3, "1.5B": 0.6, "3B": 0.85}

plt.plot(list(scores.keys()), list(scores.values()), marker="o")
plt.xlabel("模型规模")
plt.ylabel("多步推理任务平均得分")
plt.title("Scaling Law 实测曲线")
plt.show()
```

如果分数平滑上升，可以描述为该评测上的渐进改善；如果某个规模出现跳升，还需要检查评分阈值、样本数量、随机性和模型训练差异，不能直接把它归因于 Emergent Ability。

# 七、显存占用如何确认

不要把固定表格当作自己的显存结论。权重只是占用的一部分，运行时还包括量化元数据、CUDA Context、临时张量和 KV Cache。建议每次只加载一个模型，并在生成前后实测：

```python
if torch.cuda.is_available():
    torch.cuda.reset_peak_memory_stats()
    # 在这里执行一次 generate(...)
    print("峰值显存(GB):", torch.cuda.max_memory_allocated() / 1024**3)
```

记录本机环境、库版本、输入长度和生成长度后再比较；这些条件不同，显存结果就不可直接横向对照。

本实验完成了同一模型家族的定性规模对比，并说明了正确解释结果时必须控制 Prompt、解码、评分方式和硬件配置。观察到的差异可以形成研究假设，但不能替代严格的 Scaling Law 或 Emergent Ability 实验。
