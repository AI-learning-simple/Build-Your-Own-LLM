# 实验 3.2：从 One-Hot 到 Embedding Matrix

> **实验目标**
>
> 上一节，我们使用 One-Hot Encoding 成功解决了 Token ID 没有语义的问题，例如 `cat → [0,0,1,0]`。但新问题出现了：**如果 Vocabulary 有 100000 个 Token，每一个 One-Hot 向量都会有 100000 个维度**。本实验将回答：**为什么现代 LLM 不使用 One-Hot，而使用 Embedding Matrix？**

---

# 一、One-Hot 的问题

继续使用上一节的 Vocabulary（apple/banana/cat/dog），One-Hot 很容易理解。但如果 Vocabulary 变成 100000 个 Token，`cat` 对应 `[0,0,...,1,...,0]`，长度 100000，其中真正有用的数据只有一个 `1`，其它 99999 个都是 `0`，是不是非常浪费？

---

# 二、再观察一下 One-Hot

```text
apple  → [1,0,0,0]
banana → [0,1,0,0]
cat    → [0,0,1,0]
dog    → [0,0,0,1]
```

真正决定 Token 身份的，其实只是**哪一个位置是 1**。因此 One-Hot 本质上就是**根据 Token ID，选择某一行**。

---

# 三、换一种保存方式

假设提前准备一个表：

```text
apple  → [0.12, 0.83]
banana → [-0.55, 0.27]
cat    → [0.91, -0.18]
dog    → [0.88, -0.22]
```

现在已经不需要 100000 个 0，只需要直接找到 `cat` 对应的 `[0.91,-0.18]` 即可，是不是快很多？

---

# 四、这张表叫什么？

这张二维表就是 **Embedding Matrix**，它的 shape 是 `4 × 2`（4 行、2 列）：

```python
embedding = [
    [0.12, 0.83],      # apple
    [-0.55, 0.27],     # banana
    [0.91,-0.18],      # cat
    [0.88,-0.22]       # dog
]
```

这里的 `4` 表示 Vocabulary 大小（一共有 4 个 Token），`2` 表示 Embedding Dimension（每个 Token 用 2 个数字表示）。真正 GPT 可能是 `100000 × 768` 或 `150000 × 4096`，原理完全一样。

---

# 五、Lookup（查表）

Tokenizer 输出 `cat → 2`，Embedding 其实什么都没有计算，它只是取 `embedding[2]`：

```python
embedding = [[0.12,0.83],[-0.55,0.27],[0.91,-0.18],[0.88,-0.22]]
token_id = 2
vector = embedding[token_id]
print(vector)  # [0.91,-0.18]
```

这里没有乘法、加法、神经网络，只是 Python 列表索引。所以 Embedding 又叫 **Lookup Table（查找表）**。

---

# 六、One-Hot 与 Embedding 的关系

很多教材会说 Embedding 是 One-Hot 的升级版，更准确地说：

> **Embedding Matrix 是 One-Hot 的高效实现。**

如果把 One-Hot `cat → [0,0,1,0]` 乘以 Embedding Matrix，计算 `[0,0,1,0] × Embedding` 会直接得到第三行 `[4,5]`（假设矩阵行为 `[1,0],[2,3],[4,5],[6,7]`）。因此真正 Transformer 并不会先生成 One-Hot 再做矩阵乘法，它直接 `Embedding[token_id]`——速度、结果完全一样，只是更高效。

---

# 七、完整代码

```python
#!/usr/bin/env python3
vocab = ["apple", "banana", "cat", "dog"]
embedding = [[0.12,0.83],[-0.55,0.27],[0.91,-0.18],[0.88,-0.22]]

token = "cat"
token_id = vocab.index(token)
vector = embedding[token_id]

print("Token:", token)          # cat
print("Token ID:", token_id)    # 2
print("Embedding:", vector)     # [0.91,-0.18]
```

输出结果为:
```
Token: cat
Token ID: 2
Embedding: [0.91, -0.18]
```

---

# 八、现在这些向量有意义吗？

`[0.91,-0.18]` 是谁写的？为什么 `cat` 就是这个向量？答案很简单：**目前没有任何意义**，我们只是随便写了几个数字。真正 GPT 中，这些数字全部都是随机初始化的，然后在训练过程中不断更新，越来越合理。因此 Embedding 真正重要的不是 Lookup，而是**训练**。

---

# 九、本实验修改了什么？

相比上一节，唯一变化是 `One-Hot → Embedding Matrix`，Language Model、Attention、Transformer 全部没有出现，只是增加了 Lookup。整个数据流升级为：

```mermaid
flowchart LR
    A[Text] --> B[Tokenizer] --> C["Token IDs"] --> D["Embedding Matrix"] --> E[Vectors]
```

---

# 实验收获（Takeaways）

✅ 理解 One-Hot 为什么效率低；理解 Embedding Matrix 的结构与 Lookup Table 的工作方式。
✅ 理解 Embedding Matrix 本质上是 One-Hot 的优化实现。
❌ 当前 Embedding 向量仍然是随机的，没有语义。

---

# Design Discussion（为什么 Embedding 会有语义？）

目前 `cat → [0.91,-0.18]` 完全是随机数。那么为什么训练结束以后会变成 `[0.24,0.81,...]`，并且与 `dog` 越来越接近？是谁修改了这些数字？答案就是下一节：**Embedding Training（Embedding 是如何学会语义的）**。下一节，我们将第一次引入**梯度下降（Gradient Descent）**和**反向传播（Backpropagation）**，用一个极简实验观察 Embedding 向量如何一步步学习到语义。
