# 11.1 搭建智能体运行时（Agent Runtime）——用 LangGraph 部署持续运行的服务

> **本节定位**：本节只做实践。Agent Runtime 的执行架构与服务化边界见第 11 章，本节不重复讲解，只把 Agent 部署成 HTTP 服务。
>
> **硬件要求**：需模型推理。本地运行建议 8GB+ 显存 GPU，也可按本节说明改用 API 或量化方案（云 GPU 见前言 P0.3）
>
> **本节目标**：把 6.1 节的 Agent Loop 用 FastAPI 部署成一个持续运行的 HTTP 服务，并用 `session_id` 隔离不同用户的会话状态。

---

## 一、起点：一个脚本形态的 Agent

```python
def run_agent_once(question):
    # 复用6.1节的 AgentLoop 逻辑（这里简化为一次调用）
    return f"[Agent 处理结果] {question}"
```

这种形态的问题是：**每次调用都要重新加载模型、重新初始化 Agent 状态**，完全无法支撑真实的多用户并发访问。

---

## 二、用 FastAPI 把 Agent 包装成一个持续运行的服务

```bash
pip install fastapi uvicorn langgraph langchain-core
```

```python
# 用字符串拼接生成一份独立的服务脚本文件，方便用 uvicorn 单独启动
service_code = '''
import torch
from fastapi import FastAPI
from pydantic import BaseModel
from typing import TypedDict, List, Dict
from langgraph.graph import StateGraph, END
from transformers import AutoTokenizer, AutoModelForCausalLM

app = FastAPI(title="Agent Runtime")

# 关键：模型加载放在模块顶层，服务启动时只执行一次，之后所有请求都复用这一份模型
model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

def llm(prompt, max_new_tokens=150):
    messages = [{"role": "user", "content": prompt}]
    text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tokenizer(text, return_tensors="pt").to(model.device)
    output = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
    return tokenizer.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

class AgentState(TypedDict):
    question: str
    answer: str

def answer_node(state: AgentState) -> AgentState:
    return {"answer": llm(state["question"])}

# 这里只是一个最简单的单节点图，实际项目中可以换成 6.1/7.1 节那样更复杂的Agent Loop
graph = StateGraph(AgentState)
graph.add_node("answer", answer_node)
graph.set_entry_point("answer")
graph.add_edge("answer", END)
agent_app = graph.compile()

class Query(BaseModel):
    question: str

@app.post("/agent/invoke")
def invoke_agent(query: Query):
    # 每次请求只是调用一次已经编译好的 Graph，不涉及任何模型重新加载
    result = agent_app.invoke({"question": query.question, "answer": ""})
    return {"answer": result["answer"]}

@app.get("/health")
def health():
    # 健康检查接口，方便负载均衡器或容器编排系统判断服务是否存活
    return {"status": "ok"}
'''

with open("agent_service.py", "w") as f:
    f.write(service_code)

print("agent_service.py 已生成")
```

关键区别在于：**模型的加载（`AutoModelForCausalLM.from_pretrained`）只在服务启动时执行一次**，之后所有请求都复用同一个已经加载好的模型实例。这正是本实验要观察的服务化行为。

---

## 三、启动服务并测试

```bash
uvicorn agent_service:app --host 0.0.0.0 --port 9000
```

```python
import requests

response = requests.post(
    "http://localhost:9000/agent/invoke",
    json={"question": "介绍一下 Transformer。"},
)
print(response.json())
```

现在这个 Agent 已经是一个真正的**长期在线服务**：可以持续接收多个用户的请求，模型只需要加载一次，每次请求只需要走一次前向推理，不需要重新初始化任何东西。

## 四、加入会话状态：让Runtime 记住每个用户的上下文

```python
session_code_patch = '''
sessions = {}   # 用 session_id 隔离每个用户的对话历史（生产环境通常换成 Redis/数据库）

class ChatQuery(BaseModel):
    session_id: str
    question: str

@app.post("/agent/chat")
def chat_with_session(query: ChatQuery):
    # 取出这个用户之前的对话历史（如果没有则为空列表）
    history = sessions.get(query.session_id, [])
    context = "\\n".join(f"用户: {h[0]}\\n助手: {h[1]}" for h in history)
    prompt = f"{context}\\n用户: {query.question}\\n助手:"

    answer = llm(prompt)
    history.append((query.question, answer))
    sessions[query.session_id] = history        # 把更新后的历史存回去，供下一次请求使用

    return {"answer": answer, "turn": len(history)}
'''

with open("agent_service.py", "a") as f:      # 用追加模式把新接口加进已有的服务文件
    f.write(session_code_patch)

print("已追加带session 的多轮对话接口")
```

```python
requests.post("http://localhost:9000/agent/chat", json={"session_id": "user_1", "question": "我叫小明。"})
resp = requests.post("http://localhost:9000/agent/chat", json={"session_id": "user_1", "question": "我叫什么名字？"})
print(resp.json())
```

不同 `session_id` 的对话历史被隔离保存在 `sessions` 字典里——这正是本实验要验证的行为。生产环境会把这个字典换成 Redis 或数据库，以支持服务重启后状态不丢失、多台服务器之间共享状态。

---

## 五、这个服务的运行特征

本实验是单进程、单副本的服务：模型和 `sessions` 都在进程内存里，重启即丢失，也没有鉴权、限流与配额。与普通 Web 服务的完整差异见第 11 章，这里只需观察两点：同一 `session_id` 能记住上下文，不同 `session_id` 互不影响。

---

## 实验边界

- 单进程、单副本运行，没有负载均衡、多副本与滚动发布；
- 会话状态存在进程内存，重启即丢失，生产环境应落到 Redis/数据库；
- 没有鉴权、限流、配额与租户隔离；
- 没有处理长任务恢复、幂等与工具副作用；
- 延迟与并发数据依赖本机硬件，不能直接外推到生产容量规划。

## 本节小结

✅ 把脚本形态的Agent 改造成了一个用 FastAPI 长期运行的 HTTP 服务 ✅ 验证了模型只需加载一次、可以持续处理多个请求 ✅ 加入了基于 `session_id` 的多轮对话状态管理。一句话总结：**Agent Runtime 的核心价值，是把"一次性运行的脚本"变成"持续在线、能够维护状态、服务多用户的系统"。**
