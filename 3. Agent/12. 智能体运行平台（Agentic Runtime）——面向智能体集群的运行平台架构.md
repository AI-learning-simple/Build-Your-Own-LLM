## 从单 Agent 运行到 Agent 集群

第 10 章的 Agent Runtime 解决的是"如何让一个 Agent 持续在线运行"；但当系统里同时存在几十、几百甚至成千上万个 Agent 实例时，问题的性质发生了变化——**这不再是运行"一个程序"，而是要管理一整个由众多 Agent、能力和共享环境组成的"世界"。** 这正是 **Agentic Runtime** 要解决的问题。

先划清一个边界：**Agentic Runtime 是概念上的"调度与编排层"，不是真正的操作系统内核。** 它通常构建在容器编排（如 Kubernetes）、队列、数据库和模型服务之上，借用进程调度的思想，但并不直接管理 CPU、内存页表或硬件中断。把它理解成"Agent 世界的控制平面（Control Plane）"更准确。

## 一种教学架构：三个职责组件

以下命名是本章用于拆解问题的架构视角，不是所有产品必须采用的行业统一标准；第 10 章的运行时也可以服务多个 Agent，两者并无严格按数量划分的术语边界。

```mermaid
flowchart TD
    A[Agentic Runtime] --> B[World Scheduler]
    A --> C[Capability Registry]
    A --> D[Persistent World]
    B --> E[统一调度所有正在运行的 Agent]
    C --> F[统一管理所有可用能力]
    D --> G[维护长期存在的共享状态]
```

- **World Scheduler**：类似操作系统的进程调度器，决定哪些 Agent 任务优先执行、同一时刻允许多少任务并发；
- **Capability Registry**：统一登记所有可用能力（工具、MCP Server、其它Agent），供任意Agent 发现和调用；
- **Persistent World**：所有 Agent 共享的、持续存在的状态存储，不会因为某个 Agent 进程重启而丢失。但"共享"会立刻带来一致性问题：多个 Agent 同时读写同一份状态时，谁赢？用乐观锁、版本号还是串行化？跨 Agent 的多步操作要不要事务？状态模型设计不好，"持久"反而会变成"持久地不一致"。

## 用进程管理的视角理解调度

管理大量并发运行的 Agent，本质上和操作系统调度进程面临的问题高度相似：**资源有限（GPU、显存、API 配额），任务有优先级差异（紧急任务应该被优先处理），需要避免某个任务耗尽全部资源**。因此，一个简化的 Agent调度器通常需要具备两个基本能力：

| 能力 | 作用 | 只做这件事的风险 |
|---|---|---|
| 优先级排序 | 让更重要或更紧急的任务优先获得计算资源 | 低优先级任务可能长期饥饿（Starvation） |
| 并发上限 | 限制同一时刻运行的 Agent 数量，避免资源被瞬间耗尽 | 粒度过粗会浪费资源，过细则调度开销高 |
| 配额（Quota） | 按用户/团队/租户限制资源总量 | 配额僵化会导致突发任务无法执行 |
| 抢占（Preemption） | 高优先级任务可中断低优先级任务 | 被中断任务需要可恢复，否则前功尽弃 |
| 公平性（Fairness） | 在优先级与吞吐之间取得平衡 | 实现复杂，指标难以定义 |

进一步地，还可以按资源类型分池调度——例如需要模型推理的任务争抢有限的 GPU 资源槽位，不需要推理的纯逻辑任务则走另一条独立的资源池，两者互不干扰。但分池也会带来**利用率下降**：某个池空闲时，另一个池未必能借用。生产系统通常需要在"隔离性"和"利用率"之间做取舍。

## 任务生命周期：提交到回收

三个核心组件之所以必须同时存在，是因为一个任务要依次穿过它们。少任何一个，链路都会在某一阶段断开：

| 阶段 | 输入 | 操作 | 产物 |
|---|---|---|---|
| 提交 | 目标 + 资源需求 + 优先级 | 校验配额，生成任务记录 | 带 `task_id` 的待调度任务 |
| 排队 | 待调度任务 | 按优先级与公平性入队，必要时限流 | 有序队列（含等待时长） |
| 分配 | 队列 + 资源槽位 | 选资源池、查并发上限、必要时抢占 | 任务与资源的租约（Lease） |
| 执行 | 租约 + 隔离环境（第 11 章） | 跑 Agent Loop，定期写 Checkpoint（第 6 章） | 中间状态、Span、外部副作用 |
| 收敛 | 终态或租约到期 | 写 Persistent World（带版本号/并发控制），释放租约 | 一致的共享状态 |
| 回收 | 任务记录 | 判定成功/失败/被抢占，清理环境与孤儿进程 | 可审计的任务结果 |

**完成判据**：只有"终态已写入 Persistent World 且租约已释放"才算一次任务结束，把结果返回给调用方并不算——否则槽位会被永久占住。**失败边界**：抢占的前提是任务可续跑，没有 Checkpoint 的抢占只是丢弃；调度器自身崩溃时，可用租约超时重新纳管孤儿任务，但还需 fencing token/实体版本阻止旧持有者继续提交。Checkpoint 不能撤回已经发生的外部副作用，幂等键也必须由执行端原子记录并与副作用关联；否则恢复仍可能重复执行。

## 2026 年的平台形态：托管运行时 + 每会话沙箱

第 10 章讨论的托管平台可承接容器生命周期、弹性伸缩、会话状态或隔离环境等职责，但支持范围与隔离粒度应逐产品核查，不能默认每个会话都拥有独立 VM 或完整执行栈恢复。平台也不会自动补齐业务调度策略：优先级、配额、抢占、检查点提交边界以及副作用幂等仍需明确设计。

一个值得警惕的趋势是：平台越"无服务器"，越容易让人误以为不需要设计状态。实际上缩容到零恰恰放大了状态问题——**进程随时可能消失，所以任何"只存在内存里"的进度都不再可靠**。

## Agent 运行平台的兴起背景

在只有一两个 Agent 的阶段，简单地各自运行互不干扰即可；但随着 Agent 数量、种类持续增长，"如何统一调度""如何共享能力""如何维护一致的世界状态"逐渐变成了独立的系统工程问题——这正是 Agentic Runtime 作为一个新的基础设施层出现的原因，也是它与第 10 章"单Agent Runtime"最大的区别。

## 本章总结

本章我们理解了：

- Agentic Runtime 管理的不是一个 Agent，而是由众多 Agent、能力和共享环境组成的整个世界
- 它是构建在容器编排、队列与模型服务之上的控制平面，不是真正的 OS 内核
- World Scheduler、Capability Registry、Persistent World 是其三个核心组件
- 调度不仅要"排优先级"，还要处理饥饿、抢占、配额与公平性
- 共享状态必须设计并发控制与冲突解决，否则"持久"会变成"持久地不一致"

> **Runtime 管理一个 Agent，Agentic Runtime 管理一个由众多 Agent、能力和环境组成的数字世界。**
