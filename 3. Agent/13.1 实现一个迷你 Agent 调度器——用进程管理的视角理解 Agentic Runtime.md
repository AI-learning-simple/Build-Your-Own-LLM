# 13.1 实现一个迷你 Agent 调度器——用进程管理的视角理解 Agentic Runtime

> **本节目标**：第13章讲的 Agentic Runtime，核心变化是 Runtime 已经不再只管理"一个 Agent"，而是要管理由**多个 Agent 共享的整个世界**——其中的 World Scheduler 负责统一调度所有正在运行的 Agent，Capability Registry 负责统一管理能力，Persistent World 负责维护长期存在的状态。这个概念比较抽象，这一节我们亲手写一个最简化的"Agent 调度器"，用真正的进程管理思想（优先级、并发上限、资源隔离）实现 World Scheduler 的核心逻辑，把这个前瞻性的概念变成一段可以运行的代码。

---

## 一、把 Agent 任务抽象成"进程"

```python
import asyncio
import time
import random
from dataclasses import dataclass, field

@dataclass
class AgentTask:
    task_id: str
    priority: int      # 数值越大代表优先级越高，调度器会优先处理它
    goal: str
    status: str = "pending"     # pending → running → completed，类似进程的生命周期状态
    result: str = None
```

---

## 二、一个模拟的 Agent 执行函数

```python
async def run_agent_task(task: AgentTask):
    task.status = "running"
    print(f"[调度器] 开始执行任务 {task.task_id}（优先级={task.priority}）: {task.goal}")

    # 用随机耗时模拟"Agent 正在思考和行动"的过程（真实场景中这里是一次模型推理或工具调用）
    duration = random.uniform(1, 3)
    await asyncio.sleep(duration)

    task.result = f"任务 '{task.goal}' 已完成，耗时 {duration:.1f}s"
    task.status = "completed"
    print(f"[调度器] 任务 {task.task_id} 完成")
    return task
```

在真实系统里，这里应该是我们前面几节写过的完整 Agent Loop（LangGraph 图、工具调用、Memory 等），这里为了聚焦"调度"本身，用一个简单的 `sleep` 模拟"Agent 正在思考和行动"的耗时过程。

## 三、核心：一个带并发上限和优先级的调度器

```python
class AgentScheduler:
    def __init__(self, max_concurrent=2):
        self.max_concurrent = max_concurrent
        # Semaphore 是并发控制的经典工具：最多允许 max_concurrent 个协程同时进入临界区
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.task_queue = []
        self.completed_tasks = []

    def submit(self, task: AgentTask):
        self.task_queue.append(task)
        # 按优先级从高到低排序（取负数实现降序），优先级高的任务会先被调度执行
        self.task_queue.sort(key=lambda t: -t.priority)
        print(f"[调度器] 收到新任务 {task.task_id}，当前队列长度: {len(self.task_queue)}")

    async def _run_with_limit(self, task: AgentTask):
        # 只有拿到 semaphore 的"许可"才能真正开始执行，超过并发上限的任务会在这里排队等待
        async with self.semaphore:
            result = await run_agent_task(task)
            self.completed_tasks.append(result)
            return result

    async def run_all(self):
        pending = self.task_queue.copy()
        self.task_queue.clear()
        # asyncio.gather 同时启动所有任务的协程，但真正并发执行的数量受 semaphore 限制
        results = await asyncio.gather(*[self._run_with_limit(t) for t in pending])
        return results
```

`asyncio.Semaphore(max_concurrent)` 正是操作系统调度里最经典的"资源限制"思想：**不管同时提交了多少个任务，同一时刻真正在运行的Agent 数量永远不超过 `max_concurrent`**——这在真实场景里对应的是"显存只能同时支撑几个模型实例同时推理"这个硬约束。

## 四、模拟多个 Agent 任务同时到达

```python
async def main():
    scheduler = AgentScheduler(max_concurrent=2)      # 同一时刻最多只有2个任务在运行

    tasks = [
        AgentTask(task_id="T1", priority=1, goal="总结一篇文章"),
        AgentTask(task_id="T2", priority=3, goal="紧急：修复线上Bug"),     # 优先级最高
        AgentTask(task_id="T3", priority=1, goal="翻译一段文本"),
        AgentTask(task_id="T4", priority=2, goal="回答用户问题"),
    ]

    for t in tasks:
        scheduler.submit(t)

    start = time.time()
    results = await scheduler.run_all()
    elapsed = time.time() - start

    print(f"\n全部任务完成，总耗时: {elapsed:.1f}s（并发上限=2）")
    for r in results:
        print(f"  {r.task_id}: {r.result}")

asyncio.run(main())
```

观察打印的执行顺序：优先级更高的`T2`（"紧急：修复线上Bug"）会更早被调度执行，同一时刻最多只有2个任务处于 `running`状态，其它任务在队列里等待——这正是操作系统"进程调度"最基本的两个要素：**优先级排序**和**并发限制**。

## 五、加入"资源感知"：根据任务类型分配不同资源

```python
class ResourceAwareScheduler(AgentScheduler):
    def __init__(self, gpu_slots=1, cpu_slots=3):
        super().__init__(max_concurrent=gpu_slots + cpu_slots)
        # 分别用两个独立的 Semaphore管理"需要 GPU 推理"和"只需要 CPU"的两类任务
        self.gpu_semaphore = asyncio.Semaphore(gpu_slots)
        self.cpu_semaphore = asyncio.Semaphore(cpu_slots)

    async def _run_with_limit(self, task: AgentTask):
        # 简单地用关键词判断这个任务是否需要模型推理，从而决定它该抢占哪一类资源槎位
        needs_gpu = "推理" in task.goal or "生成" in task.goal
        sem = self.gpu_semaphore if needs_gpu else self.cpu_semaphore

        async with sem:
            result = await run_agent_task(task)
            self.completed_tasks.append(result)
            return result

async def main_v2():
    scheduler = ResourceAwareScheduler(gpu_slots=1, cpu_slots=2)
    tasks = [
        AgentTask(task_id="G1", priority=1, goal="生成一篇长文章"),      # 走 GPU 资源池
        AgentTask(task_id="G2", priority=1, goal="生成一段代码"),        # 走 GPU 资源池
        AgentTask(task_id="C1", priority=1, goal="整理文件列表"),        # 走 CPU 资源池，互不干扰
    ]
    for t in tasks:
        scheduler.submit(t)
    await scheduler.run_all()

asyncio.run(main_v2())
```

这里模拟了一个更接近真实系统的场景：需要用到模型推理（"生成"类任务）的 Agent 争抢有限的 GPU 资源槎位，而不需要模型推理的任务（比如纯粹的文件操作）走另一条不占用 GPU 的资源池——这正是"Agentic OS"设想中，未来的调度系统需要同时理解"Agent 在做什么"和"这件事需要什么资源"。

## 六、从这个玩具调度器，回看Agentic Runtime 的设想

我们写的这几十行代码，只触及了"Agentic Runtime"这个概念的冰山一角——真正的 Agentic Runtime 还需要处理：Agent 之间的通信与协作（类似进程间通信 IPC）、Agent 权限隔离（类似用户权限管理）、Agent 崩溃后的自动重启（结合11.2 节的Checkpoint 机制）、跨多台机器的调度（类似 Kubernetes 对容器的调度）、以及一个所有 Agent 共享的 Capability Registry 和 Persistent World。但核心思想是相通的：**当 Agent 的数量从"一个"变成"成千上万个同时运行"时，管理这些Agent 本身，就会变成和管理进程、管理容器一样重要的系统工程问题。**
