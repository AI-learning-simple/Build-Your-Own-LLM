# 2.1 实现函数调用（Function Calling）——从 JSON 解析到原生工具调用（Tool Calling）

> **本节定位**：本节只做实践。工具调用（Tool Calling）的原理与边界见第 2 章，本节不重复讲解，只做两种实现方式的对照。
>
> **硬件要求**：需模型推理。本地运行建议 8GB+ 显存 GPU，也可按本节说明改用 API 或量化方案（云 GPU 见前言 P0.3）
>
> **本节目标**：1.1 节里我们用正则表达式解析 `Action: 工具名[输入]` 这种自定义格式，这其实就是最原始的 Function Calling。这一节我们先把这种手写方式做得更规范（让模型输出标准 JSON），再体验现代开源模型**原生支持**的 Tool Calling——看看工程上到底进化了什么。

---

## 一、方式A：手写 JSON 格式的 Function Calling

```python
import json
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

def get_weather(city):
    # 真正会被执行的函数，模型本身并不会调用它，只会"决定"要不要调用、传什么参数
    fake_weather = {"北京": "晴，25°C", "上海": "多云，28°C"}
    return fake_weather.get(city, "未知城市")

# 用纯 Prompt 的方式，人工告诉模型"应该输出什么格式的 JSON"
manual_prompt = """你可以调用以下函数：

get_weather(city: str)：查询指定城市的天气

如果需要调用函数，请只输出如下 JSON 格式，不要输出其它任何文字：
{{"function": "函数名", "arguments": {{"参数名": "参数值"}}}}

用户问题：{question}"""

def call_manual(question):
    text = manual_prompt.format(question=question)
    inputs = tokenizer(text, return_tensors="pt").to(model.device)
    output = model.generate(**inputs, max_new_tokens=80, do_sample=False)
    return tokenizer.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

raw_output = call_manual("北京今天天气怎么样？")
print("模型原始输出:", raw_output)

def parse_manual_output(text):
    """解析手写 Prompt 的 JSON 输出，并校验必需字段。"""
    try:
        parsed = json.loads(text.strip())
    except json.JSONDecodeError:
        return None, "解析失败：模型没有输出合法 JSON"
    if not isinstance(parsed, dict):
        return None, "解析失败：顶层不是 JSON 对象"
    if parsed.get("function") != "get_weather":
        return None, f"未知函数：{parsed.get('function')!r}"
    args = parsed.get("arguments")
    if not isinstance(args, dict) or "city" not in args:
        return None, "参数不合法：缺少 city"
    return parsed, None

parsed, error = parse_manual_output(raw_output)
if error:
    print(error)
else:
    print("函数执行结果:", get_weather(**parsed["arguments"]))
```

这种手写方式的问题很明显：**模型有没有严格按照 JSON 格式输出，完全没有保证**——它可能多说一句话，可能漏一个引号，导致 `json.loads` 直接报错。这也是早期 Function Calling 实现最头疼的地方。

## 二、方式B：使用模型原生支持的 Tool Calling

现代很多开源模型（Qwen2.5、Llama 3.1、Mistral 等）在 Instruct 阶段专门训练过"识别工具描述、输出结构化调用"的能力，`transformers` 的 `apply_chat_template` 已经原生支持传入 `tools` 参数：

```python
# 用标准的 JSON Schema 描述工具（这是 OpenAI Function Calling 定下的行业惯例格式）
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"},
                },
                "required": ["city"],
            },
        },
    }
]

messages = [{"role": "user", "content": "北京今天天气怎么样？"}]

# 关键区别：这里把 tools 直接传给 apply_chat_template，
# 模型会依据自己训练阶段学到的格式自动决定是否调用、调用哪个工具
text = tokenizer.apply_chat_template(messages, tools=tools, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)
output = model.generate(**inputs, max_new_tokens=100, do_sample=False)
raw_output = tokenizer.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

print("原生 Tool Calling 输出:", raw_output)
```

注意这里我们完全没有自己写"请输出 JSON 格式"这样的指令——**模型在 Instruction Tuning 阶段就已经专门学过如何根据 `tools` 描述，判断要不要调用工具、调用哪个工具、传什么参数**，输出格式的稳定性远比手写 Prompt 的方式可靠。

## 三、解析原生 Tool Call 并执行

```python
import re

def parse_native_tool_call(text):
    """兼容 <tool_call> 标签与裸 JSON 两种常见形态，并校验字段。"""
    candidates = []
    match = re.search(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", text, re.S)
    if match:
        candidates.append(match.group(1))
    # 部分模型/模板会直接输出 JSON，这里做一次兜底
    candidates.append(text.strip())

    for raw in candidates:
        try:
            obj = json.loads(raw)
        except json.JSONDecodeError:
            continue
        if isinstance(obj, dict) and isinstance(obj.get("name"), str) and isinstance(obj.get("arguments"), dict):
            return obj
    return None

tool_call = parse_native_tool_call(raw_output)
if tool_call is None:
    print("未检测到合法工具调用；模型可能直接给出了文字回答，或输出格式不符合预期。")
elif tool_call["name"] == "get_weather":
    print("解析到工具调用:", tool_call)
    print("函数执行结果:", get_weather(**tool_call["arguments"]))
else:
    print(f"未知工具：{tool_call['name']!r}，拒绝执行。")
```

不同模型的原生 Tool Call 输出格式略有差异（有的用 `<tool_call>` 标签，有的直接输出 JSON，有的由 chat template 注入特殊 token），但共同点是：**格式由模型训练与模板约定，而不是我们临时拼字符串**，因此通常更稳定。但"更稳定"仍不等于"一定正确"：参数可能缺字段、工具名可能拼错，所以解析后必须做**Schema 校验与未知工具拒绝**，生产环境还应把校验失败的错误信息回填给模型重试。

## 四、把 Observation 传回去，完成一次完整对话

```python
def build_tool_result_message(tool_call, result):
    # 用专门的 "tool" 角色把执行结果重新放回对话历史，模型接下来会基于这个结果生成回答
    return {
        "role": "tool",
        "name": tool_call["name"],
        "content": json.dumps({"result": result}, ensure_ascii=False),
    }

messages.append({"role": "assistant", "content": raw_output})     # 记录模型刚才的工具调用请求
messages.append(build_tool_result_message(tool_call, result))     # 追加真实的执行结果

# 再一次调用模型，这次它能看到完整的"提问→调用工具→拿到结果"的历史，从而给出真正的最终回答
text2 = tokenizer.apply_chat_template(messages, tools=tools, tokenize=False, add_generation_prompt=True)
inputs2 = tokenizer(text2, return_tensors="pt").to(model.device)
output2 = model.generate(**inputs2, max_new_tokens=100, do_sample=False)
final_answer = tokenizer.decode(output2[0][inputs2["input_ids"].shape[1]:], skip_special_tokens=True)

print("最终回答:", final_answer)
```

## 五、两种方式的对比

| | 手写 JSON 解析 | 原生 Tool Calling |
|---|---|---|
| 格式稳定性 | 依赖 Prompt 措辞，容易出错 | 训练时固定，稳定性高 |
| 适用模型 | 任意模型 | 需要模型本身支持 Tool Calling |
| 多工具/多参数场景 | Prompt 会变得越来越复杂 | 天然支持结构化 Schema |
| 学习价值 | 帮助理解底层原理 | 是工业界实际采用的方式 |

---

## 实验边界

- 工具只有 `get_weather`，不涉及网络、鉴权、写操作与副作用；
- JSON Schema 只校验了 `city` 字段，生产环境应使用完整 Schema 校验与参数范围检查；
- 没有实现“校验失败 → 错误回填 → 模型重试”的闭环；
- 解析器覆盖了 `<tool_call>` 与裸 JSON 两种常见形态，但不同模型的模板仍可能产生别的格式；
- 本地小模型可能不遵循工具调用格式，示例输出会随模型与版本变化。

## 本节小结

✅ 亲手实现了最原始的"手写 JSON"版 Function Calling，并体会到它的脆弱性 ✅ 使用了模型原生支持的 Tool Calling，观察到输出格式明显更稳定 ✅ 完整走完了"用户提问 → 模型决定调用工具 → 执行 → 结果传回 → 模型给出最终回答"的闭环。一句话总结：**Function Calling 的本质从未改变，真正进化的是"模型对调用格式的遵循能力"，这背后正是 Instruction Tuning 的功劳。**
