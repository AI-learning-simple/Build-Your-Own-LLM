# 8.1 搭建 MCP Server——让智能体通过 MCP 协议调用工具

> **本节定位**：本节只做实践。MCP 的协议定位与边界见第 8 章，本节不重复讲解，只搭建 Server 与 Client。
>
> **硬件要求**：需模型推理。本地运行建议 8GB+ 显存 GPU，也可按本节说明改用 API 或量化方案（云 GPU 见前言 P0.3）
>
> **本节目标**：亲手搭建一个最小的 MCP（Model Context Protocol）Server，再用官方 Inspector 和自己写的客户端通过协议调用它。

## 一、安装 MCP SDK

```bash
# Python 3.11+；cli extra 提供下文的 mcp dev 命令
python -m pip install "mcp[cli]>=2.1,<3" jsonschema
# 第五部分可选本地模型客户端需要：
python -m pip install torch transformers accelerate
```

> **版本提示**：`pip install mcp` 现在装到的是 2.x（对应 MCP 规范 `2026-07-28`）。1.x 时代的 `FastMCP` 在 2.0 中改名为 `MCPServer`，且旧 import 路径被直接删除（不是弃用别名）——所以网上大量 `from mcp.server.fastmcp import FastMCP` 的教程在 2.x 下会第一行就报 `ModuleNotFoundError`。协议层面同时删掉了 `initialize` 握手与会话 ID，客户端不再需要先"握手"再调用。

## 二、最小 MCP Server 搭建

创建 `weather_server.py`：

```python
# 用字符串拼接生成一份独立的 Server 脚本文件（MCP Server 通常作为独立进程启动）
server_code = '''
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("weather-server")     # 创建一个 MCP Server 实例，"weather-server" 是它的标识名

FAKE_WEATHER = {
    "北京": "晴，25°C",
    "上海": "多云，28°C",
    "深圳": "小雨，30°C",
}

@mcp.tool()   # 用装饰器把一个普通函数注册成MCP 工具，函数签名和docstring 会自动变成工具的 Schema
def get_weather(city: str) -> str:
    """查询固定演示天气数据，不提供实时天气。"""
    if city not in FAKE_WEATHER:
        raise ToolError(f"暂无{city}的示例天气数据")
    return FAKE_WEATHER[city]

@mcp.tool()
def calculator(expression: str) -> str:
    """计算有界四则表达式；不支持幂运算，所有中间值绝对值不超过 1e12。"""
    import ast
    import math
    import operator
    ops = {ast.Add: operator.add, ast.Sub: operator.sub,
           ast.Mult: operator.mul, ast.Div: operator.truediv}
    def safe_eval(expr: str) -> float:
        if len(expr) > 200:
            raise ValueError("表达式过长")
        tree = ast.parse(expr, mode="eval")
        if len(list(ast.walk(tree))) > 64:
            raise ValueError("表达式节点过多")
        def _eval(node):
            if isinstance(node, ast.Expression):
                return _eval(node.body)
            if isinstance(node, ast.Constant) and type(node.value) in (int, float):
                value = node.value
            elif isinstance(node, ast.BinOp) and type(node.op) in ops:
                value = ops[type(node.op)](_eval(node.left), _eval(node.right))
            elif isinstance(node, ast.UnaryOp) and isinstance(node.op, (ast.USub, ast.UAdd)):
                value = _eval(node.operand) * (-1 if isinstance(node.op, ast.USub) else 1)
            else:
                raise ValueError("只允许有限数字、括号与四则运算")
            if not math.isfinite(value) or abs(value) > 1e12:
                raise ValueError("数值超出实验范围")
            return value
        return _eval(tree)
    try:
        return str(safe_eval(expression))
    except (ValueError, SyntaxError, ZeroDivisionError, OverflowError, RecursionError) as e:
        raise ToolError(f"计算出错: {e}") from e

if __name__ == "__main__":
    mcp.run(transport="stdio")     # 以标准输入输出作为通信方式启动 Server 进程
'''

with open("weather_server.py", "w") as f:
    f.write(server_code)

print("weather_server.py 已生成")
```

`MCPServer` 是 MCP 官方 SDK 提供的高层封装：只需要用 `@mcp.tool()` 装饰一个普通 Python 函数，函数的类型签名和 docstring 会被转换成 MCP 协议要求的工具描述（Schema），从而**无需手写 JSON Schema**。不过类型签名能表达的结构有限，复杂的业务约束仍应在工具实现里显式校验。

顺带说明一处容易踩的坑：2.x 里 `MCPServer(...)` 的位置参数顺序变了（`name, title, description, instructions, ...`），1.x 习惯写的 `FastMCP("demo", "你是一个助手")` 迁移过来不会报错，但那句话会静默落到 `title` 而不是 `instructions`。除了 `name`，其余参数建议一律用关键字传。

## 三、用官方 Inspector 快速验证 Server

```bash
mcp dev weather_server.py
```

这条命令会启动一个本地调试界面（MCP Inspector），你可以在浏览器里直接看到这个 Server 暴露了哪些工具、每个工具的参数是什么，并且可以直接在界面上试调用 `get_weather("北京")`，验证 Server 是否正常工作。

> `mcp dev` 内部会用 `npx` 拉起官方 Inspector（一个 Node 应用），所以本机需要安装 Node.js；如果你的 Server 依赖了第三方包，`mcp dev` 会读取文件里声明的依赖并在启动时一并安装。

## 四、MCP Client 连接实现

```python
client_code = '''
import asyncio
import sys
from mcp import Client, StdioServerParameters

async def main():
    # 用当前解释器启动 Server，避免 "python" 指向另一个虚拟环境
    server_params = StdioServerParameters(command=sys.executable, args=["weather_server.py"])

    # v2 把"会话 + 传输"两层合并成一个 Client：传 StdioServerParameters 就是拉起子进程，
    # 传 URL 字符串就是 Streamable HTTP，传 Server 对象则是内存直连（测试常用）。
    # 注意构造不等于连接，必须用 async with 打开。
    async with Client(server_params) as client:
        print("协商到的协议版本:", client.protocol_version)

        # 自动发现 Server 提供的全部工具，不需要人工事先知道有哪些工具
        tools = await client.list_tools()
        print("Server 提供的工具:")
        for tool in tools.tools:
            print(f"  - {tool.name}: {tool.description}")
            # print(tool.input_schema)        # v2 的字段是 snake_case；v1 写 inputSchema

        # 真正调用远程 Server 上的工具，参数以字典形式传入
        result = await client.call_tool("get_weather", {"city": "北京"})
        print("\\n调用 get_weather(城市=北京) 结果:", result.content[0].text)

        result2 = await client.call_tool("calculator", {"expression": "23*17+100"})
        print("调用 calculator(23*17+100) 结果:", result2.content[0].text)
        print("是否工具层错误:", result2.is_error)      # v1 写 isError

asyncio.run(main())
'''

with open("weather_client.py", "w") as f:
    f.write(client_code)

print("weather_client.py 已生成")
```

```bash
python weather_client.py
```

运行后你会看到 Client 首先通过 `list_tools()` 获取到 Server 暴露的全部工具列表（这一步完全是自动生成的，不需要人工维护"工具清单"），然后分别调用了 `get_weather` 和 `calculator` 两个工具，拿到真实的返回结果——**这就是MCP 协议真正跑通的完整闭环**。

## 五、让 LLM Agent 通过 MCP 调用工具

```python
agent_code = '''
import asyncio
import json
import re
import sys
import torch
from jsonschema import validate, ValidationError
from transformers import AutoTokenizer, AutoModelForCausalLM
from mcp import Client, StdioServerParameters

model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

def llm_decide(question, mcp_tools):
    # 把从 MCP Server 自动发现的工具列表，转换成模型能理解的文字描述
    tool_desc = json.dumps([
        {"name": t.name, "description": t.description, "input_schema": t.input_schema}
        for t in mcp_tools
    ], ensure_ascii=False)
    prompt = f"""可用工具：
{tool_desc}

用户问题：{question}

请判断需要调用哪个工具，只输出 JSON：{{"tool": "工具名", "arguments": {{...}}}}"""
    messages = [{"role": "user", "content": prompt}]
    text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tokenizer(text, return_tensors="pt").to(model.device)
    output = model.generate(**inputs, max_new_tokens=80, do_sample=False)
    return tokenizer.decode(output[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

def parse_decision(text, valid_tools):
    """从模型输出中抽取 JSON，并校验工具名与参数类型。"""
    obj = json.loads(text.strip())  # 必须整个响应都是 JSON，不宽松截取任意大括号
    if not isinstance(obj, dict):
        raise ValueError("决策结果不是 JSON 对象")
    tool, args = obj.get("tool"), obj.get("arguments")
    if not isinstance(tool, str) or tool not in valid_tools:
        raise ValueError(f"未知工具：{tool!r}")
    if not isinstance(args, dict):
        raise ValueError("arguments 必须是 JSON 对象")
    if set(obj) != {"tool", "arguments"}:
        raise ValueError("决策只能包含 tool 和 arguments")
    validate(instance=args, schema=valid_tools[tool].input_schema)
    return tool, args

async def main():
    server_params = StdioServerParameters(command=sys.executable, args=["weather_server.py"])

    async with Client(server_params) as client:
        tools = (await client.list_tools()).tools     # 动态获取工具列表，交给模型做决策

        question = "请查询北京的固定演示天气数据（不是实时天气）。"
        decision_text = llm_decide(question, tools)
        print("模型决策:", decision_text)

        # 把模型的决策解析出来，校验后再通过 MCP 协议调用对应工具
        try:
            tool_name, arguments = parse_decision(decision_text, {t.name: t for t in tools})
            result = await client.call_tool(tool_name, arguments)
            if result.is_error:
                print("工具返回错误:", result.content[0].text)
            else:
                print("MCP 工具调用结果:", result.content[0].text)
        except (ValueError, ValidationError) as e:
            # 生产环境应把错误回填给模型重试，而不是直接崩溃
            print("决策解析失败：", e)

asyncio.run(main())
'''

with open("mcp_agent.py", "w") as f:
    f.write(agent_code)

print("mcp_agent.py 已生成，运行: python mcp_agent.py")
```

## 六、对照结果分析

对比 2.1 节手写的 Function Calling：那里的工具 Schema 手工写在 Prompt 里，执行逻辑和 Agent 代码在同一个文件；本节的 MCP Server 是**完全独立的进程**，客户端通过 `list_tools()` 自动发现能力，再通过 `call_tool()` 调用。同一个 Server 可以被不同客户端复用，但复用仍受协议版本、鉴权方式与部署环境约束。

还有一个容易被忽略的变化：在 `2026-07-28` 这一版协议里，客户端与服务端之间**没有会话**了。每次 `call_tool` 都是一次自包含的请求（版本与客户端能力放在 `_meta` 里），所以你可以把同一个 Server 部署在多台机器、由网关随意路由；代价是"跨调用记住一点状态"必须由服务端自己签发一个句柄，作为普通工具参数传回来，而不能指望连接替你记住。

---

## 实验边界

- 使用本地 `stdio` 传输，未实现鉴权、TLS 和多租户；启动 Server 本身就在授予本地进程权限，不能把任意来源的 Server 当作可信代码；
- 天气是明确的固定样例，不是实时天气；未知城市和计算失败使用 `ToolError`，由 SDK 表示工具层错误，不能返回普通错误字符串伪装成功；
- 模型同时获得工具说明与 `input_schema`，执行器在调用前用 JSON Schema 校验；服务端仍独立校验业务边界，Schema 通过不等于有权调用；
- Server 暴露的工具是本机可信代码，未演示不可信 Server 的审核与隔离；
- 只覆盖了 Tools，没有展开 Resources、Prompts 与 MCP Apps（交互式 UI）扩展；
- 决策解析失败时只打印错误，没有实现自动重试与降级；
- 没有演示超时、取消、并发调用与 Server 崩溃时的客户端行为；
- 未演示 Tasks 扩展（长任务轮询）与 MRTR（服务端要求补充输入的往返流程）。

## 本节小结

- 用 `MCPServer`（原 `FastMCP`）亲手搭建了一个暴露两个工具的 MCP Server
- 用官方 Inspector 验证了 Server 的工具是否正常工作
- 亲手编写了 MCP Client，通过标准协议完成了 `list_tools` 和 `call_tool` 的完整调用
- 让 LLM Agent 通过 MCP 协议动态发现并调用工具。一句话总结：**MCP 把"工具"变成了一个可以被任何 Agent 通过标准协议发现和调用的独立服务，而不再是绑死在某一个 Agent 框架里的私有代码。**
