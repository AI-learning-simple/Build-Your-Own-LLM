# 10.3 评测一个 Agent——成功率、步数与 Trace 回放

> **本节目标**：第 10 章讲了 Agent 评测的指标（成功率、平均步数、工具调用正确率）和可观测性（Trace/Span）。这一节我们全部亲手做一遍：给一个带 calculator 工具的 ReAct Agent 出 10 道它心算不动的算术题，跑评测、看指标、用 Trace 定位失败原因，然后**修复、再评测**——完整走一遍"评测 → 定位 → 修复 → 再评测"的迭代闭环。复用 10.1 节的本地模型（Qwen2.5-1.5B-Instruct）。

---

# 一、准备：一个带计算器工具的 Agent 和 10 道题

```python
import re
import time
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

SYSTEM = ("你是一个会使用计算器工具的助手。你必须先调用 calculator 计算,得到结果后再回答。\n"
          "需要计算时输出:ACTION: calculator(算式)\n"
          "得到计算结果后输出:ANSWER: 数字\n"
          "禁止不调用工具就直接给出答案。")

# 10 道题:三位数乘除/复合运算,1.5B 模型心算不动,必须真用工具
QUESTIONS = [
    ("387×291=?", 112617), ("(23+45)×12=?", 816), ("1567-889=?", 678),
    ("1024÷32=?", 32), ("57×83=?", 4731), ("9527-3468=?", 6059),
    ("144+256-89=?", 311), ("9720÷27=?", 360), ("68×74=?", 5032),
    ("(1000-237)÷7=?", 109),
]
```

**为什么选模型心算不动的题？** 评测要测出"Agent 是否真的会借助工具"，如果题太简单，模型直接心算就答对了，工具调用就变成了走过场，评测就失去了意义。

评测脚本的核心是一个 `run_one` 函数：跑一道题，**把每一步的 LLM 调用和工具执行都记录进 `trace` 列表**（这就是第 10 章讲的 Trace/Span），最多 6 步，最后返回"是否答对、步数、工具调用次数、Trace"：

```python
def llm(messages, max_new_tokens=80):
    text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
    inputs = tokenizer(text, return_tensors="pt").to(model.device)
    out = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
    return tokenizer.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

def run_one(question, expected, max_steps=6):
    trace = []
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": f"请计算:{question}"}]
    steps, tool_calls = 0, 0
    for step in range(max_steps):
        t0 = time.time()
        resp = llm(messages)
        trace.append({"type": "llm", "input": messages[-1]["content"],
                      "output": resp, "latency": round(time.time() - t0, 2)})
        steps += 1
        m = re.search(r"ACTION:\s*calculator\(([^)]+)\)", resp)   # v1:正则提取
        m_ans = re.search(r"ANSWER:\s*(-?[\d.]+)", resp)
        if m:
            result = calculator(m.group(1).strip())
            tool_calls += 1
            trace.append({"type": "tool", "args": m.group(1).strip(), "result": result})
            if m_ans:   # v1:模型同轮抢答,直接采纳(这是 bug,见下文)
                return (abs(float(m_ans.group(1)) - expected) < 0.01, steps, tool_calls, trace)
            messages.append({"role": "assistant", "content": resp})
            messages.append({"role": "user", "content": f"计算结果:{result}"})
            continue
        if m_ans:
            return (abs(float(m_ans.group(1)) - expected) < 0.01, steps, tool_calls, trace)
        messages.append({"role": "assistant", "content": resp})
        messages.append({"role": "user", "content": "请继续,输出 ACTION 或 ANSWER。"})
    return (False, steps, tool_calls, trace)

correct = total_steps = total_tools = 0
for q, ans in QUESTIONS:
    ok, steps, tools, trace = run_one(q, ans)
    correct += ok; total_steps += steps; total_tools += tools
print(f"答对率: {correct}/10 = {correct/10:.0%}")
print(f"平均推理步数: {total_steps/10:.1f}")
print(f"工具调用总数: {total_tools}")
```

# 二、评测第一版：5/10，及格线以下

评测脚本的核心是一个 `run_one` 函数：跑一道题，记录每一步的 LLM 调用和工具执行（这就是 Trace），最多 6 步，最后返回"是否答对、步数、工具调用次数、Trace"。对 10 道题各跑一遍，汇总指标：

```text
== 逐题结果 ==
  第 1题 387×291=?   答对=False 步数=1 工具调用=1
  第 2题 (23+45)×12=? 答对=False 步数=1 工具调用=1
  第 3题 1567-889=?  答对=True  步数=1 工具调用=1
  ...(10 题)
  第10题 (1000-237)÷7=? 答对=False 步数=1 工具调用=1

== 评测汇总 ==
答对率: 5/10 = 50%
平均推理步数: 1.0
工具调用总数: 10(平均每题 1.0)
```

**10 道题每道都调用了工具，但只答对了一半**——工具明明调用成功了，为什么还会错？指标只能告诉你"哪里不行"（50%），接下来要靠 Trace 回答"为什么不行"：

```text
== 第一题(387×291=?)的 Trace ==
Span0: LLM 调用 输出='ACTION: calculator(387*291)\nANSWER: 114057'
Span1: 工具 calculator(387*291) = 112617
```

**问题一目了然：模型在同一轮里既调用了工具、又抢答了自己的心算结果 114057——而工具算出来的正确答案是 112617。** Agent 在"工具结果返回之前"就交卷了，交的还是自己心算的（错的）答案。这类失败模型上还有个专门的名字：**Agent 没有"等工具结果"就提前作答**——真实项目里非常常见。

---

# 三、修复 v2：强制等工具结果，再评测 → 70%

修复方式：无论模型是否在同一轮给出 ANSWER，只要它调用了工具，就**必须把工具结果回传、让模型在下一轮基于真实结果作答**：

```python
if expr is not None:
    result = calculator(expr)
    tool_calls += 1
    trace.append({"type": "tool", "name": "calculator", "args": expr, "result": result})
    # 修复 v2:以工具结果为准,让模型在下一轮基于真实结果作答
    messages.append({"role": "assistant", "content": resp})
    messages.append({"role": "user", "content": f"计算结果:{result}。请基于该结果输出:ANSWER: 数字"})
    continue
```

再评测：

```text
答对率: 7/10 = 70%
平均推理步数: 2.9
工具调用总数: 13(平均每题 1.3)
```

从 50% 提到 70%。但还剩 3 道失败——这次 Trace 诊断又暴露了**两类完全不同的 bug**，而且它们不是模型的问题，是**我们自己的实现问题**：

```text
--- 失败题:(23+45)×12=?(5 步,1 次工具调用) ---
Span0: LLM 输出='ACTION: calculator((23+45)*12)'
Span1: 工具 calculator((23+45) = 错误:'(' was never closed
--- 失败题:9720÷27=?(2 步,1 次工具调用) ---
Span0: LLM 输出='ACTION: calculator(9720 ÷ 27)'
Span1: 工具 calculator(9720 ÷ 27) = 错误:算式含非法字符
```

1. **正则解析器截断了嵌套括号**：我们用 `calculator\(([^)]+)\)` 提取参数，遇到 `(23+45)*12` 这种**嵌套括号**时，`[^)]+` 在第一个 `)` 处就停了，只提取到 `(23+45`——表达式被拦腰截断。这正是第2.1节讲过的：**手写正则解析函数调用会踩坑，所以真实系统用模型原生的 Function Calling 协议**（那边由专门的解码器保证括号配对）；
2. **工具容错不足**：模型把 `9720÷27` 原样传了进来（全角 `÷`），我们的白名单只认识 ASCII 符号，直接拒绝——工具对真实世界的常见输入变体（全角符号、多余空格）不够宽容。

---

# 四、修复 v3：括号配对解析 + 工具容错，再评测 → 100%

两个修复都写在工具侧：

```python
def calculator(expr):
    expr = expr.replace("×", "*").replace("÷", "/").replace(" ", "")  # 容错:全角/空格
    if not re.fullmatch(r"[0-9+\-*/().]+", expr):
        return "错误:算式含非法字符"
    try:
        return str(eval(expr))
    except Exception as e:
        return f"错误:{e}"

def extract_calc(resp):
    """修复 v3:用括号配对提取完整参数,而不是正则截断"""
    m = re.search(r"calculator\(", resp)
    if not m:
        return None
    i, depth, j = m.end(), 1, m.end()
    while j < len(resp) and depth > 0:
        if resp[j] == "(":
            depth += 1
        elif resp[j] == ")":
            depth -= 1
        j += 1
    return resp[i:j - 1].strip() if depth == 0 else None
```

第三次评测：

```text
== 评测汇总 ==
答对率: 10/10 = 100%
平均推理步数: 2.0
工具调用总数: 10(平均每题 1.0)
单题平均耗时: 0.4s
```

三次迭代的完整轨迹：

| 版本 | 改动 | 答对率 | 平均步数 |
|---|---|---|---|
| v1 | 采纳模型同轮抢答 | 5/10 = 50% | 1.0 |
| v2 | 强制等工具结果 | 7/10 = 70% | 2.9 |
| v3 | 括号配对解析 + 工具容错 | 10/10 = 100% | 2.0 |

# 五、这个实验告诉了我们什么？

1. **评测的价值不在"测一次"，而在"迭代"**：三次评测，每一步都在前一步的失败证据（Trace）指引下前进——没有 Trace，v1 的 50% 只能靠猜；
2. **指标和 Trace 是一对**：答对率告诉你"哪里不行"（第2题错了），Trace 告诉你"为什么不行"（正则截断了括号）；只看指标你会去调模型，看了 Trace 才发现是自己的解析器有 bug——**Agent 系统的很多"模型问题"，其实是工程问题**；
3. **10 道题拿到 100% 不说明模型很强**：样本太小、任务太专。真实项目会用 GAIA 这类标准基准、成百上千道题，并持续维护一个回归测试集——每次改代码都重跑一遍，防止"修好 A 弄坏 B"（这正是第 10 章讲过的可观测性平台 LangSmith/Langfuse 帮你做的事情）。

# 本实验总结

✅ 给一个带 calculator 工具的 Agent 跑了 10 道题的完整评测，得到成功率、平均步数、工具调用数等真实指标 ✅ 用 Trace 定位了 v1 的失败根因：Agent 在工具结果返回前抢答 ✅ 修复后重测 50% → 70%，Trace 又暴露了两类实现 bug（正则截断嵌套括号、工具不容错全角符号）✅ 再修复后 100%，完成"评测 → 定位 → 修复 → 再评测"闭环。一句话总结：**Agent 评测不是"打个分就完事"，而是一条由 Trace 驱动的持续迭代流水线——指标负责发现问题，Trace 负责定位问题，修复之后永远要再测一遍。**
