# 11.2 Agent 流式输出——首 Token 延迟与增量响应

> **硬件要求**：需模型推理。本地运行建议 8GB+ 显存 GPU，也可按本节说明改用 API 或量化方案（云 GPU 见前言 P0.3）
>
> **本节目标**：第 11 章讲了流式输出（Streaming）为什么是 Agent 的体验刚需。这一节我们用本地模型亲手对比两种输出方式：**非流式**（等全部生成完，一次性返回）和**流式**（逐 token 生成、边生成边输出），并看看生产环境中的 SSE（Server-Sent Events）格式长什么样。全部代码在本地 GPU 上运行，复用 11.1 节同一个模型（Qwen2.5-1.5B-Instruct）。

---

# 一、为什么"逐字出现"和"一次给全"差别这么大？

同样是 200 个 token 的输出，两种方式的体验完全不同：

- **非流式**：用户发出请求后，屏幕上一片空白，直到 3 秒后整段文字一次性出现——如果 Agent 要跑好几轮"思考→调工具→再思考"，用户面对的可能是一两分钟的空白等待；
- **流式**：第一个字几百毫秒内就出现，后面的内容一边生成一边刷新——用户能立刻感受到"它在工作"，并且可以提前开始阅读。

**总耗时几乎一样，差别全在"第一个字何时出现"**——这个指标在工程上叫 **TTFT（Time To First Token，首 Token 延迟）**。下面亲手把它测出来。

---

# 二、非流式：等全部生成完

```python
import time
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen2.5-1.5B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float16, device_map="auto")

prompt = "请详细介绍什么是 Transformer 模型,包括它的核心思想、主要组成部分和应用场景。"
messages = [{"role": "user", "content": prompt}]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)
n_in = inputs["input_ids"].shape[1]

t0 = time.time()
out = model.generate(**inputs, max_new_tokens=200, do_sample=False)
t1 = time.time()
n_new = out[0].shape[0] - n_in
print(f"等待 {t1-t0:.2f}s 后,一次性返回全部 {n_new} 个 token")
```

```text
等待 2.99s 后,一次性返回全部 200 个 token
```

**这 2.99 秒里，用户看到的是空白。** 对单次对话还能忍，对 Agent 这种动辄十几秒的多步任务，几乎是不可接受的体验。

# 三、流式：逐 token 生成

流式的本质，是**不调用一次性的 `generate()`，而是自己控制生成循环**——每次只生成一个 token，立刻交给前端显示，再继续下一个。transformers 的 `past_key_values`（KV Cache，第一部分第15章讲原理，第二部分 10.2 节有实测）让这一步非常高效：

```python
input_ids = inputs["input_ids"]
past = None
generated = []
t_start = time.time()
first_token_time = None
for step in range(200):
    with torch.no_grad():
        out_i = model(input_ids=input_ids, past_key_values=past, use_cache=True)
    past = out_i.past_key_values
    next_id = out_i.logits[0, -1].argmax().item()
    if first_token_time is None:
        first_token_time = time.time() - t_start
    generated.append(next_id)
    if next_id == tokenizer.eos_token_id:
        break
    input_ids = torch.tensor([[next_id]], device=model.device)
    if step < 12 or step % 25 == 0:
        print(f"  token {step:3d}: {tokenizer.decode([next_id]):10s} 累计 {time.time()-t_start:.2f}s")
t_total = time.time() - t_start
print(f"首 token 延迟(TTFT): {first_token_time:.2f}s | 总耗时: {t_total:.2f}s | 共 {len(generated)} 个 token")
```

```text
  token   0: Transformer 累计 0.01s
  token   1:  �         累计 0.03s
  token   2: ��         累计 0.04s
  token   3: 型          累计 0.05s
  token   4: 是一种        累计 0.06s
  token   5: 基于         累计 0.08s
  ...
  token  50: 。          累计 0.63s
  token 100: ）          累计 1.25s
  token 150: 自          累计 1.87s
  token 175: 元素         累计 2.19s

首 token 延迟(TTFT): 0.01s | 总耗时: 2.48s | 共 200 个 token
```

**对比结论：**

| | 非流式 | 流式 |
|---|---|---|
| 用户看到第一个字 | 2.99s 后（一次性全出） | **0.01s 后** |
| 总耗时 | 2.99s | 2.48s |
| 体验 | 一片空白等 3 秒 | 打字机式实时输出 |

**两个值得注意的细节：**

1. **token 1、2 显示为 `�`**——这不是 bug，而是 BPE 的一个真实特性：中文一个字在 UTF-8 里占 3 个字节，BPE 词表会把它们拆成多个 token，单独解码时会出现"半个字"。**字符和 Token 并不对齐**（第一部分 2.5、2.6 节的 BPE 拆词也一样），前端展示时只需要把收到的 token 拼起来再渲染，就不会有问题；
2. 流式的总耗时（2.48s）甚至略低于非流式（2.99s）——因为手写循环省掉了 `generate()` 的额外开销。**流式不是"更慢的妥协"，它只是把同一个生成过程摊开到了时间轴上。**

# 四、生产形态：SSE 逐行推送

把上面的生成循环接到 HTTP 上，就是生产环境的标准做法——**SSE（Server-Sent Events）**：服务端保持一个 HTTP 长连接，每生成一个 token，就推送一行 `data: <内容>`，浏览器实时渲染。这就是 ChatGPT 官网打字机效果的底层协议：

```python
print("SSE 格式示例(前 8 个 token):")
for t_ in generated[:8]:
    print(f"data: {tokenizer.decode([t_])}")
    print()
```

```text
data: Transformer

data:  �

data: ��

data: 型

data: 是一种

data: 基于

data: 注意力

data: 机制
```

在 FastAPI 里实现它只需要把返回类型换成 `StreamingResponse`，把生成循环放进一个生成器（`yield` 每个 token）；LangGraph 也提供了 `stream()` 方法，可以在图执行的每一轮把增量状态推出来——**流式的数据源可以是"token 级"（LLM 生成），也可以是"步骤级"（Agent 每完成一步工具调用）**，后者对 Agent 尤其有价值：用户能看到"正在调用哪个工具、找到了什么"。

# 本实验总结

✅ 亲手对比了非流式与流式两种输出方式，测出真实数字：首 Token 延迟从 2.99s 降到 0.01s，总耗时基本不变 ✅ 理解了 TTFT（首 Token 延迟）是流式体验的关键指标 ✅ 用 `past_key_values` 手写了一个逐 token 生成循环 ✅ 见识了 BPE 切出"半个字"的真实现象 ✅ 了解了 SSE 协议与 FastAPI/LangGraph 的流式形态。一句话总结：**流式没有改变"生成什么"，只改变了"何时让你看到"——但对用户来说，这就是体验的全部差别。**

> 💡 **Insight：流式和可观测性是 Agent 体验的左右手——流式让用户"看得见正在发生什么"，Trace 让开发者"看得见刚刚发生了什么"。两者解决的都是同一件事：Agent 是个黑盒，而生产级 Agent 必须把它打开。**
