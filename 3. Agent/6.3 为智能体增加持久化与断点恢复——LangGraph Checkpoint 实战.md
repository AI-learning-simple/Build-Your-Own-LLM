# 6.3 为智能体增加持久化与断点恢复——LangGraph Checkpoint 实战

> **本节定位**：概念与副作用边界见第 6 章；这里用独立的 `run` / `resume` 进程验证图内状态留存。
>
> **硬件要求**：CPU 即可，不需要语言模型。本节使用确定性节点，先把模型不确定性从恢复实验中移除。
>
> **目标**：执行第一步 → 在已声明的边界协作暂停并退出进程 → 新进程重新构图与连接数据库 → 恢复剩余步骤。**受控暂停不是任意时刻强杀或断电测试**。

## 一、依赖与持久化口径

建议 Python 3.11+，在自己的实验环境安装：

```bash
pip install "langgraph>=1,<2" "langgraph-checkpoint-sqlite>=3,<4"
```

API 按 **2026-11-27 官方文档**核对：`SqliteSaver.from_conn_string()` 是上下文管理器；`durability="sync"` 在下一超级步开始前同步提交检查点。默认异步模式可能在进程崩溃时丢失最新检查点，不能把“收到一个 stream 事件”当作落盘证明。

- `sync`：推进下一步前等待检查点写入，增加同步开销。
- `async`：下一步运行同时写入，崩溃窗口更大。
- `exit`：退出时保存，不用于证明执行中途崩溃的逐步恢复。

写入持久性还受数据库、文件系统和硬件约束；`sync` 不是任意故障下绝不丢失数据的承诺。

## 二、完整示例：保存为 `checkpoint_demo.py`

以下是同一个脚本的全部内容，两种模式都独立创建图、重新打开同一路径的数据库，不依赖先前 Python 进程中的变量。数据库路径用绝对路径传入，避免工作目录变化读错文件。

```python
import argparse
from pathlib import Path
from typing import TypedDict

from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver

class TaskState(TypedDict):
    current_step: int
    results: list[str]

def first_node(state):
    print("执行 first")
    return {"current_step": 1, "results": state["results"] + ["第一步结果"]}

def second_node(state):
    print("执行 second；上一步：", state["results"][-1])
    return {"current_step": 2, "results": state["results"] + ["第二步结果"]}

def third_node(state):
    print("执行 third；已有步骤：", state["current_step"])
    return {"current_step": 3, "results": state["results"] + ["第三步结果"]}

def build_graph(checkpointer):
    builder = StateGraph(TaskState)
    builder.add_node("first", first_node)
    builder.add_node("second", second_node)
    builder.add_node("third", third_node)
    builder.add_edge(START, "first")
    builder.add_edge("first", "second")
    builder.add_edge("second", "third")
    builder.add_edge("third", END)
    # 静态断点：first 已完成、second 尚未开始时暂停。
    return builder.compile(checkpointer=checkpointer, interrupt_before=["second"])

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("mode", choices=["run", "resume"])
    parser.add_argument("--db", required=True)
    parser.add_argument("--thread", default="task-001")
    args = parser.parse_args()
    db_path = Path(args.db).expanduser().resolve()
    if not db_path.parent.is_dir():
        parser.error("数据库父目录不存在，请先选择已有目录")
    if args.mode == "resume" and not db_path.is_file():
        parser.error("数据库不存在，不能恢复")
    config = {"configurable": {"thread_id": args.thread}}

    with SqliteSaver.from_conn_string(str(db_path)) as saver:
        app = build_graph(saver)
        before = app.get_state(config)
        if args.mode == "run":
            if before.values:
                parser.error("该 thread 已存在；请用 resume 或选择新的 --thread，避免覆盖实验")
            app.invoke({"current_step": 0, "results": []}, config, durability="sync")
            snapshot = app.get_state(config)
            assert snapshot.values == {"current_step": 1, "results": ["第一步结果"]}
            assert snapshot.next == ("second",)
            print("已协作暂停：", snapshot.values, "下一节点：", snapshot.next)
        else:
            if not before.values:
                parser.error("该 thread 无检查点")
            print("新进程读取：", before.values, "下一节点：", before.next)
            if before.next:
                # 静态断点使用 None 继续；动态 interrupt() 的回答才使用 Command(resume=...)。
                app.invoke(None, config, durability="sync")
            final = app.get_state(config)
            assert final.values == {
                "current_step": 3,
                "results": ["第一步结果", "第二步结果", "第三步结果"],
            }
            assert final.next == ()
            print("完整性断言通过：", final.values)
    # 离开 with 后关闭连接，然后正常退出。下一条命令是一个独立 Python 进程。

if __name__ == "__main__":
    main()
```

## 三、用两个命令启动两个进程

先确认当前目录适合放实验数据库；下面使用同一绝对路径，两条命令分别启动 Python：

```bash
python checkpoint_demo.py run --db "$PWD/agent_checkpoints.db" --thread task-001
python checkpoint_demo.py resume --db "$PWD/agent_checkpoints.db" --thread task-001
```

预期第一条只执行 `first`，检查点中 `current_step=1`、`next=("second",)`，随后关闭数据库并正常退出。第二条新进程读到第一步结果，再执行 `second` 和 `third`；末尾断言检查状态完整性。再次 `resume` 已完成 thread 时不会重新执行节点。换新实验可使用新的 `--thread`，不用删除旧数据库。

这些是**可验证的预期与断言**，不是未经运行的真实日志。运行依赖缺失时应如实记录未实测，不能据此声称已经验证崩溃恢复。

## 四、到底验证了什么

本实验验证：磁盘检查点可跨正常退出的进程读取；恢复从声明断点继续；保存的第一步结果参与后续计算。它没有验证强杀发生在任意指令、磁盘故障、断电或并发写时的行为。

`invoke(None, config)` 表示继续该 thread 的未完成工作；若传新的初始输入，含义变成把新输入应用到状态并从入口执行，不是简单恢复。恢复还要求相同的图定义、兼容的状态 Schema、数据库路径和 thread ID；模型对象、函数代码和连接不会被检查点序列化，需要新进程重建。

## 五、副作用按“可能至少一次”设计

Checkpoint 保存的是图内状态，**不自动回滚外部世界，也不保证外部动作绝不重放**。如果节点已发送请求，但完成状态尚未可靠记录，恢复可能从该节点开头重跑。同一逻辑动作因此可能被尝试多次；这不是 exactly-once 保证。

- 为写操作使用稳定的业务幂等键，并让服务端持久化去重；不要每次重试生成新键。
- 超时后先查询操作状态；需要时用 outbox、补偿或人工对账协调图状态和业务状态。
- 把多个外部副作用拆成更小的节点/任务可缩小重放范围，但不能凭空消除故障窗口。
- 本例只有纯状态变换，没有外部写操作，因此无法证明副作用幂等。

## 实验边界与小结

SQLite Saver 面向轻量同步实验，不覆盖多副本恢复、租约、迁移或生产存储治理。`sync` 与明确断点使示例的保存时机可解释，真正的故障容错还需单独设计故障注入与业务幂等测试。
