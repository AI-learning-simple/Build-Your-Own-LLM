# 14.1 实现一个最小 Capability Registry——用事件驱动的方式理解 Agentic OS

> **本节目标**：第 14 章"Agentic OS"是全书最具前瞻性的一章——它提出未来的操作系统会围绕"Capability First"（能力优先）和"Event First"（事件优先）这两个设计原则重新组织，而不再是"人点击图标 → 打开应用"这种传统模式。这一节我们亲手实现一个最小化的 Capability Registry（能力注册中心）+ Event Bus（事件总线），模拟一个不需要人工点击、完全由事件驱动的迷你"Agentic OS"雏形。

## 一、传统模式：人点击，程序执行

```python
def traditional_click_handler(app_name):
    # 每个 App 都要等待人主动点击才会执行对应逻辑，这是延续了几十年的交互范式
    apps = {
        "邮件": lambda: print("打开邮件客户端，等待用户手动回复"),
        "日历": lambda: print("打开日历，等待用户手动添加日程"),
    }
    apps[app_name]()

traditional_click_handler("邮件")
```

这是我们最熟悉的模式：**人主动发起操作，应用被动响应**。第 14 章指出，随着 Agent 越来越普及，越来越多任务不再需要人工点击——真正触发操作的，变成了"事件"本身。

## 二、Capability Registry：把"能力"变成可以被发现的一等公民

```python
class Capability:
    def __init__(self, name, description, handler):
        self.name = name
        self.description = description
        self.handler = handler# 真正会被调用执行的函数

class CapabilityRegistry:
    def __init__(self):
        self.capabilities = {}       # 用名字索引所有已注册的能力

    def register(self, name, description, handler):
        # 任何一个函数都可以被注册成一个"能力"，Registry 不关心它内部具体做了什么
        self.capabilities[name] = Capability(name, description, handler)
        print(f"[Registry] 注册能力: {name} —— {description}")

    def find_by_keyword(self, keyword):
        # 最简单的能力发现方式：按描述里是否包含关键词匹配（真实系统通常用语义检索）
        return [c for c in self.capabilities.values() if keyword in c.description]

    def invoke(self, name, **kwargs):
        if name not in self.capabilities:
            return f"未找到能力: {name}"
        return self.capabilities[name].handler(**kwargs)

registry = CapabilityRegistry()
```

这里的关键区别是：**传统操作系统管理"应用程序"，Agentic OS 管理"能力"**。一个能力可能来自一个完整的 App，也可能只是一个函数、一个 MCP Server暴露的工具——对 Registry 而言，它们都是同样的"Capability"。

## 三、注册几个真实能力

```python
# world_state 模拟第 13 章提到的 Persistent World——所有能力共享的、持续存在的状态
world_state = {"emails": [], "calendar": [], "drafts": []}

def draft_reply(email_content):
    reply = f"感谢您的邮件，关于「{email_content[:20]}...」，我们会尽快处理。"
    world_state["drafts"].append(reply)
    return reply

def schedule_event(title, date):
    world_state["calendar"].append({"title": title, "date": date})
    return f"已添加日程: {title} @ {date}"

def summarize_document(text):
    return f"摘要: {text[:30]}..."

registry.register("draft_reply", "根据邮件内容自动起草回复", draft_reply)
registry.register("schedule_event", "在日历中添加一个新日程", schedule_event)
registry.register("summarize_document", "对长文档进行摘要", summarize_document)
```

## 四、Event Bus：事件优先，而不是人工触发

```python
class EventBus:
    def __init__(self, registry):
        self.registry = registry
        self.subscriptions = {}       # 记录"某类事件"应该触发哪些能力

    def subscribe(self, event_type, capability_name):
        # 订阅关系：当event_type 事件发生时，自动调用 capability_name这个能力
        self.subscriptions.setdefault(event_type, []).append(capability_name)
        print(f"[EventBus] 订阅:当 '{event_type}' 事件发生时，自动调用 '{capability_name}'")

    def publish(self, event_type, **payload):
        # 发布一个事件，EventBus 会自动查找所有订阅了这个事件的能力并依次调用
        print(f"\n[EventBus] 事件触发: {event_type} payload={payload}")
        handlers = self.subscriptions.get(event_type, [])
        results = []
        for cap_name in handlers:
            result = self.registry.invoke(cap_name, **payload)
            print(f"  -> 自动调用能力 '{cap_name}'，结果: {result}")
            results.append(result)
        return results

bus = EventBus(registry)
bus.subscribe("new_email", "draft_reply")
bus.subscribe("meeting_request", "schedule_event")
```

## 五、模拟一个完全不需要人工点击的世界

```python
# 直接发布事件，没有任何"人打开 App、点击按钮"的步骤
bus.publish("new_email", email_content="请问下周三是否可以安排一次产品评审会议？")
bus.publish("meeting_request", title="产品评审会议", date="下周三 14:00")

print("\n========== World State ==========")
print(world_state)
```

运行后你会看到：**没有任何一步是"人打开邮件客户端、手动点击回复"**——`new_email` 事件一发生，Registry 里注册的 `draft_reply` 能力就自动被调用，结果直接写入 `world_state`。这正是第 14 章说的"Event First"：系统不再等待人的操作，而是持续监听事件，自动匹配并调用相应能力。

## 六、加入多个 Agent，共享同一个 World State

```python
class SimpleAgent:
    def __init__(self, name, bus):
        self.name = name
        self.bus = bus       # 多个 Agent 实例共享同一个 EventBus（进而共享同一个 Registry 和 world_state）

    def on_event(self, event_type, **payload):
        print(f"[{self.name}] 感知到事件: {event_type}")
        return self.bus.publish(event_type, **payload)

research_agent = SimpleAgent("研究助理", bus)
schedule_agent = SimpleAgent("日程助理", bus)

research_agent.on_event("new_email", email_content="能帮我总结一下这份市场报告吗？")
schedule_agent.on_event("meeting_request", title="季度复盘", date="本月底")

print("\n========== 最终 World State（多个 Agent 共享）==========")
print(world_state)
```

两个不同的 Agent 实例（`research_agent`、`schedule_agent`）虽然各自"感知"了不同的事件，但它们**共享同一个 `world_state` 和同一个 `registry`**——这正是第 13 章 Persistent World 与第 14 章Capability Registry 结合起来的样子：能力是所有 Agent 共享的公共资源，世界状态是所有 Agent 共同读写的持久化存储。

## 七、这就是"Agentic OS"设想的最小雏形

把这几十行代码放大一万倍，再加上：真正的权限系统（不是所有 Agent 都能调用所有能力）、真正的调度器（复用 13.1 节写的调度器管理并发）、真正的持久化（`world_state` 换成数据库）、真正的能力发现（不再靠关键词匹配，而是用 Embedding 语义检索，就像 4.1 节的向量记忆），就基本得到了第 14 章所描绘的 Agentic OS 的核心骨架：**Capability Registry 让能力可以被发现和复用，Event Bus 让系统由事件驱动而不是人工点击，Persistent World 让状态在所有 Agent 之间共享和延续。**
